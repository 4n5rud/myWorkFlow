# 출시 전 성능 점검

> 목적은 **성능 향상**이다. 기능이 맞게 도는지는 E2E 점검이 보고, 이 문서는 **데이터가 많아졌을 때도 빠르고 안 죽는지**를 본다.
> 개발 중의 로컬 데이터는 수십 건이라 느린 쿼리가 드러나지 않는다. 부하 테스트를 하지 않으면 정확한 문제를 찾기 어렵기 때문에, **운영 규모의 데이터를 먼저 만들고** 그 위에서 점검한다.
> 운영과 스테이징 서버에서는 하지 않는다. 로컬이나 전용 점검 환경에서만 한다.

---

## 0. 언제, 누가

- **언제:** 기능이 거의 갈무리되고, 큰 구조 변경이 더 없을 때. 출시 1~2주 전이 좋다. 너무 이르면 코드가 바뀌어 다시 해야 한다.
- **누가:** 커맨드 센터가 배정하고, 서버 담당이 쿼리와 인덱스를, 웹과 앱 담당이 화면 쪽을 맡는다. 결과는 한 문서로 모은다.
- **산출물:** 병목 목록(느린 순), 고친 것과 전후 수치, 고치지 않기로 한 것과 이유.
- **저장 위치:** 6.1을 따른다.

---

## 1. 준비: 운영 규모 데이터부터 만든다

> 한 프로젝트의 웹 서비스는 브라우저 몇 개만 동시에 붙어도 로컬 컨테이너가 메모리 부족으로 꺼졌다.
> 데이터와 동시 접속이 적을 때는 보이지 않던 문제였다.

1. **규모를 정한다.** 출시 1년 뒤 예상치를 기준으로 한다. 모르면 발주사 기대치의 10배로 잡는다.
   - 예: 회원 10만, 주문 50만, 상품 1만, 알림 500만, 로그성 테이블은 그 이상
2. **시드 스크립트로 만든다.** 손으로 넣지 않는다. 다시 돌릴 수 있게 스크립트로 두고, 점검 전용 DB에서만 돌게 막는다(DB 이름 확인).
3. **분포를 현실처럼 만든다.** 균등하게 넣으면 문제가 숨는다.
   - 한 사용자에게 몰린 데이터(주문 5천 건인 회원, 찜 3천 개인 회원)
   - 한 날짜에 몰린 데이터(행사 첫날)
   - 아주 긴 글, 이미지 많은 글, 삭제되거나 숨김 처리된 행이 섞인 데이터
4. **기준 수치를 남긴다.** 고치기 전에 주요 화면과 API의 응답 시간을 재 둔다. 전후 비교가 없으면 개선을 증명할 수 없다.

---

## 2. 많은 데이터에서만 드러나는 엣지 케이스

데이터가 많을 때 기능이 깨지거나 느려지는 경우를 하나씩 확인한다.

| 점검 | 무엇을 보나 |
|---|---|
| 목록 끝까지 | 마지막 쪽, 1만 번째 쪽에서 응답 시간과 결과가 맞는가. OFFSET이 크면 느려진다 |
| 무제한 조회 | 페이지 없이 전체를 불러오는 API, 화면, 엑셀 내보내기가 있는가 |
| 한 사용자에게 몰림 | 주문 5천 건, 찜 3천 개인 사용자의 마이페이지와 장바구니 |
| 집계 | 대시보드 합계, 건수, 순위가 전체 테이블을 매번 훑는가 |
| 검색 | 앞뒤 % 검색(LIKE '%어%'), 정렬과 함께 쓰는 검색 |
| 일괄 작업 | 대량 발송, 일괄 지급, 정기 작업(크론)이 한 번에 몇 건을 메모리에 올리는가, 중간에 실패하면 어디까지 처리됐는가 |
| 동시 요청 | 같은 재고, 같은 쿠폰, 같은 응모에 동시에 들어올 때 잠금 대기가 길어지는가 |
| 긴 값 | 아주 긴 이름과 본문, 이모지, 많은 첨부가 목록 화면과 응답 크기를 키우는가 |
| 화면 | 목록 1천 줄을 한 번에 그리는가, 무한 스크롤이 쌓이며 메모리가 늘어나는가 |

## 3. 쿼리 전수 점검: 병목을 하나도 빼지 않고 찾는다

> "느린 것만 보자"고 하면 느린지 아직 모르는 쿼리를 놓친다. 그래서 **전부 목록으로 만든 뒤** 잰다.

### 3.1 목록 만들기

- 서버가 부르는 쿼리를 **API와 정기 작업 단위로 모두** 적는다(ORM 호출, 직접 쓴 SQL, 뷰).
- 화면 하나가 API를 몇 번 부르는지도 함께 적는다. 한 화면이 API를 10번 부르면 그것도 병목이다.

### 3.2 재기

- **느린 쿼리 기록을 켠다.** PostgreSQL은 `log_min_duration_statement`(예: 100ms)나 `pg_stat_statements`로 누적 시간이 큰 쿼리를 뽑는다.
- **실행 계획을 본다.** 의심 쿼리마다 `EXPLAIN (ANALYZE, BUFFERS)`를 돌려 다음을 확인한다.
  - 큰 테이블 전체 훑기(Seq Scan)
  - 예상 건수와 실제 건수의 큰 차이
  - 정렬이 메모리를 넘어 디스크로 감
  - 중첩 반복(Nested Loop)이 큰 테이블에 걸림
- **N+1을 찾는다.** 목록 하나를 그리는 데 같은 쿼리가 줄 수만큼 반복되는지 ORM 로그로 센다.

### 3.3 기준

| 구분 | 목표 (점검 환경, 운영 규모 데이터) |
|---|---|
| 일반 조회 API | p95 300ms 이하 |
| 목록과 검색 | p95 500ms 이하 |
| 쿼리 하나 | 100ms 이하. 넘으면 목록에 올린다 |
| 화면 첫 표시 | 2초 이하 |

기준은 프로젝트마다 조정한다. 숫자를 정하지 않으면 "빨라졌다"를 판단할 수 없으니, 점검 시작 전에 정해서 문서 맨 위에 적는다.

## 4. 고치는 순서: 쿼리, 인덱스, 캐시 순으로

비싼 수단일수록 뒤에 쓴다. 앞 단계로 풀리면 다음 단계로 가지 않는다.

### 4.1 쿼리부터 고친다

- 필요한 칸만 가져온다(`SELECT *`와 ORM의 전체 관계 불러오기를 줄인다).
- N+1은 한 번에 묶어 가져오기(IN 조회, JOIN, ORM의 include)로 바꾼다.
- 큰 OFFSET 페이지는 커서 방식(마지막 id 기준)으로 바꾼다.
- 매번 다시 세는 집계는 필요한 범위만 세거나, 4.3의 미리 계산으로 넘긴다.
- 일괄 작업은 묶음 단위(예: 1천 건)로 나눠 처리하고, 어디까지 했는지 기록한다.

### 4.2 인덱스를 단다

- **실행 계획에서 근거를 확인한 쿼리에만** 단다. "있으면 좋겠다"로 달지 않는다.
- WHERE, JOIN, ORDER BY에 함께 쓰는 칸은 순서를 맞춘 복합 인덱스 하나가 낱개 여럿보다 낫다.
- 상태값으로 늘 거르는 테이블은 부분 인덱스(예: 삭제되지 않은 행만)를 검토한다.
- 인덱스는 쓰기를 느리게 하고 공간을 쓴다. **쓰기가 많은 테이블은 꼭 필요한 것만** 단다.
- 단 뒤에 같은 쿼리의 실행 계획과 시간을 다시 재서 효과를 확인한다. 효과가 없으면 지운다.
- 큰 테이블에 인덱스를 만들 때 운영 반영은 잠금 없이 만드는 방식(`CREATE INDEX CONCURRENTLY`)을 쓴다.

### 4.3 캐시는 마지막에, 좁게

> 캐시는 빠르게 만들지만, 오래된 값을 보여 주는 버그와 지우기 규칙이라는 새 일을 만든다.

**캐시를 써도 되는 경우 (모두 맞을 때)**
- 자주 읽고 드물게 바뀐다(설정, 카테고리, 공지, 홈 구성, 집계 대시보드).
- 조금 오래된 값을 보여 줘도 문제가 없다(몇십 초에서 몇 분).
- 쿼리와 인덱스로 고쳐도 기준을 못 맞췄다.

**쓰지 않는 경우**
- 재고, 잔액, 쿠폰 수량, 권한처럼 틀리면 안 되는 값
- 사용자마다 다른 값이 많아 캐시가 거의 맞지 않는 경우
- 쿼리 하나만 고치면 되는 경우

**쓸 때 규칙**
- 가장 단순한 것부터: HTTP 캐시와 프레임워크 캐시(예: Next.js의 재검증), 그다음 서버 메모리, 그다음 Redis 같은 공유 캐시 순서로 검토한다.
- 캐시마다 **유효 시간과 지우는 시점**(무엇이 바뀌면 지우는가)을 코드 옆에 적는다.
- 집계는 캐시보다 미리 계산해 두는 테이블이나 정기 작업이 맞을 때가 많다.
- 새 캐시 서버나 큐를 들이는 것은 이 점검의 범위 밖이다. 필요하면 따로 결정을 받는다.

## 5. 부하 테스트

- **도구:** k6, autocannon 같은 도구로 주요 흐름을 시나리오로 만든다(로그인, 목록, 상세, 담기, 주문, 응모).
- **단계:** 평소 예상 동시 사용자에서 시작해, 행사 첫날 같은 최대치와 그 2배까지 단계적으로 올린다.
- **볼 것:** 응답 시간(p95, p99), 오류율, DB 연결 수와 대기, 서버 메모리와 CPU, 느린 쿼리 기록
- **멈추는 기준:** 오류율이 1%를 넘거나 p95가 기준의 3배를 넘으면 멈추고 원인을 찾는다.
- 개발 서버(핫 리로드 모드)로 부하를 주지 않는다. 운영과 같은 빌드로 띄운 점검 환경에서 한다. 개발 서버는 그 자체가 느리고 메모리를 많이 써서 수치가 의미 없다.

## 6. 보고 형식

### 6.1 저장 위치

- 성능 향상에 관한 리포트는 **해당 프로젝트 저장소의 `docs/성능향상/`** 에 모은다. 다른 폴더나 개인 메모에 흩어 두지 않는다.
- 성능 리포트는 커밋하는 프로젝트 문서라서, 커밋하지 않는 작업 산출물 폴더 `_작업/`이 아니라 `docs/성능향상/`에 둔다.
- 파일 이름은 `YYYY-MM-DD_간단한 내용.md`로 쓴다(띄어쓰기 허용). 예: `2026-11-03_주문 목록 쿼리.md`, `2026-11-05_부하 테스트 1차.md`
- 폴더 안에 `README.md` 를 두고, 리포트 목록과 각 리포트의 한 줄 요약, 상태(진행 중, 반영 완료, 레거시)를 적는다.
- 실행 계획 출력, 부하 테스트 결과, 시드 스크립트 설명처럼 근거가 되는 파일도 같은 폴더 아래(예: `docs/성능향상/근거/`)에 둔다. 운영 데이터나 개인정보가 들어간 출력은 넣지 않는다.
- 다시 점검해서 앞 리포트의 내용이 바뀌면, 앞 리포트 맨 위에 레거시 표시와 새 리포트 링크를 남긴다([[00 세션 공통 지침]] §14).

### 6.2 내용

맨 위에 기준 수치와 요약을 두고, 병목은 느린 순으로 적는다.

| 순위 | 위치(API, 화면, 작업) | 쿼리나 원인 | 고치기 전 | 고친 뒤 | 한 일 | 근거(실행 계획, 기록) |
|---|---|---|---|---|---|---|
| 1 | 관리자 주문 목록 | OFFSET 큰 페이지, 정렬 칸 인덱스 없음 | 2.4초 | 180ms | 커서 페이지, 복합 인덱스 | EXPLAIN 전후 첨부 |

- 고치지 않기로 한 것은 이유와 함께 따로 적는다(예: 하루 한 번 도는 관리자 작업이라 10초여도 괜찮음).
- 캐시를 단 곳은 유효 시간과 지우는 시점을 함께 적는다.
- 바꾼 설정, 인덱스, 시드 스크립트 위치를 적어서 다른 사람이 같은 점검을 다시 할 수 있게 한다.
- 문서 갱신 규칙([[00 세션 공통 지침]] §14)에 따라, 바뀐 쿼리와 인덱스는 관련 설계 문서에도 반영한다.

## 7. 체크리스트

**준비**
- [ ] 운영 규모와 기준 수치를 정했다
- [ ] 시드 스크립트로 몰린 분포까지 포함한 데이터를 만들었다 (점검 전용 DB)
- [ ] 고치기 전 기준 수치를 쟀다

**엣지 케이스**
- [ ] 목록 끝 쪽, 무제한 조회, 엑셀 내보내기
- [ ] 한 사용자에게 몰린 데이터, 한 날짜에 몰린 데이터
- [ ] 집계와 검색
- [ ] 일괄 작업과 정기 작업의 메모리와 중단 후 재개
- [ ] 동시 요청의 잠금 대기
- [ ] 긴 값과 큰 응답, 화면의 많은 줄

**쿼리 전수**
- [ ] API와 정기 작업의 쿼리 목록을 만들었다
- [ ] 느린 쿼리 기록과 누적 시간 상위 쿼리를 뽑았다
- [ ] 의심 쿼리마다 실행 계획을 봤다
- [ ] N+1을 셌다

**개선**
- [ ] 쿼리를 먼저 고쳤다
- [ ] 인덱스는 실행 계획 근거가 있는 것만 달고, 효과를 다시 쟀다
- [ ] 캐시는 쓸 수 있는 조건을 모두 만족하는 곳에만, 유효 시간과 지우는 시점을 적고 달았다

**부하**
- [ ] 운영과 같은 빌드로 단계별 부하를 줬다
- [ ] 오류율, 응답 시간, DB 연결, 메모리를 기록했다

**마무리**
- [ ] 보고서에 전후 수치와 고치지 않은 것의 이유를 적었다
- [ ] 리포트를 `docs/성능향상/`에 저장하고 README 목록을 갱신했다
- [ ] 바뀐 쿼리와 인덱스를 설계 문서에도 반영했다
