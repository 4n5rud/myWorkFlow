# 주간보고 검수

> 주간보고는 **고객이 읽는 문서**다. 한 주 동안 무엇을 했고 다음 주에 무엇을 할지가 고객 눈높이로 정확하게 드러나야 하고, 내부 사정이나 탓하는 말이 섞이면 안 된다.
> 이 문서는 쓰기 전에 할 일(1장), 다 쓴 뒤 검수할 일(2장), 검수 결과를 남기는 법(3장)으로 나뉜다.

관련 문서: [[05 쇠맛 줄이기]] (문장), [[08 보고 지침]] (사용자에게 하는 보고), [[09 커밋 메시지 규칙]]

---

## 한눈에 보기

| 순서 | 할 일 |
|---|---|
| 쓰기 전 | 그 주의 모든 커밋을 모아 "이번 주 변경 목록"을 만든다. 지난주 보고서와 WBS(작업 분류표)를 읽는다 |
| 쓴 뒤 | 아래 2장의 열네 가지를 하나씩 확인하고 고친다 |
| 끝 | 검수 결과(고친 것, 판단을 맡길 것)를 사용자에게 함께 보고한다 |

## 1. 쓰기 전에: 근거를 먼저 다 모은다

### 1.1 🔴 그 주의 모든 커밋을 먼저 파악한다

노트(주간목표, 날짜별 노트)는 빠진 날이 많다. 노트만 보고 쓰면 큰 작업이 빠지거나, 한 일을 못 한 일로 쓰게 된다. **보고서를 쓰기 전에 커밋부터 전부 본다.**

1. 그 프로젝트의 **모든 저장소**(서버, 앱, 관리자 웹, 문서 저장소, 서브모듈)를 빠짐없이 찾는다.
2. 저장소마다 원격을 받아 온 뒤(`git fetch`, 작업 폴더는 바꾸지 않는다) **금주 월요일부터 기준일까지 모든 브랜치의 커밋**을 본다. 작성자로 거르지 않는다. 함께 일하는 사람의 작업도 보고 대상일 수 있다.
   - 다른 사람이 커밋한 작업은 보고서 작성자가 함께한 일인지 확인한다. 함께한 일이 아니면 묶음 제목에 "(팀 작업)"을 붙이거나 뺀다. 작성자 본인 실적처럼 읽히게 쓰지 않는다(2026-11-06 사용자 결정).
   ```bash
   git -C <저장소> log --all --since="<금주 월요일> 00:00" --until="<기준일> 23:59" \
     --format='%h %ad %an %s' --date=short --no-merges
   ```
3. 커밋을 **기능 단위로 묶은 "이번 주 변경 목록"**을 만든다. 묶음마다 다음을 적는다.
   - 무엇이 바뀌었나(고객이 알아보는 기능 이름으로)
   - 상태: 합쳐짐(dev나 main에 들어감) / 작업 브랜치에만 있음 / 되돌림
   - 근거 커밋 몇 개와 저장소
4. 이 목록을 노트와 맞춰 본다. 노트에 있는데 커밋이 없는 일, 커밋은 있는데 노트에 없는 일을 따로 표시한다.

### 1.2 묶음 기준과 WBS를 정한다

- **묶음 제목과 요구사항 번호는 지난주 보고서(가장 최근 보고서)를 우선 따른다.** 고객은 지난주 보고서와 이어서 읽는다.
- WBS는 **진척률 대조와 "WBS 밖 일" 구분에만** 쓴다. 프로젝트 목록(`projects.md`)에 적힌 WBS 위치를 읽고, 항목마다 WBS의 어느 작업에 해당하는지 짝을 지어 진척률을 맞춰 본다.
- **WBS 체계가 아직 없거나 불완전한 프로젝트**는 보고에 "WBS 정리 필요"라고 적고, WBS 번호를 지어내지 않는다.

### 1.3 지난주 보고서를 읽는다

지난주 보고서의 **차주 계획**을 목록으로 만든다. 이번 주 보고서에서 이 항목들이 실적이나 차주 계획으로 다시 나와야 한다.

## 2. 다 쓴 뒤에: 열네 가지를 확인한다

| 번호 | 확인할 것 | 고치는 법 |
|---|---|---|
| 1 | **근거:** 항목마다 1.1의 변경 목록에 근거가 있는가. 변경 목록의 큰 묶음 중 보고서에 빠진 것이 있는가 | 근거 없는 항목은 지우거나 "확인 필요"로 남긴다. 빠진 큰 작업은 넣는다 |
| 2 | **상태:** 작업 브랜치에만 있는 일을 "완료"로 쓰지 않았는가 | 합쳐지지 않은 일은 "진행 중"이나 "검토 중"으로 쓴다 |
| 3 | **묶음과 WBS 정합:** 묶음 제목과 요구사항 번호가 지난주 보고서와 이어지는가. 진척률이 WBS와 같은가. WBS에 없는 일을 구분했는가 | 묶음 제목은 지난주 보고서를 따른다. WBS 밖의 일은 "추가 요청 대응"처럼 따로 묶는다 |
| 4 | **지난주 약속:** 지난주 차주 계획이 빠짐없이 다시 나오는가 | 빠진 항목은 실적, 진행 중, 차주 계획 중 하나로 넣는다. 미룬 일은 미룬 이유를 짧게 쓴다 |
| 5 | **공격적이거나 탓하는 표현:** 고객, 다른 업체, 디자이너, 기획 쪽을 탓하는 말이 없는가 ("회신이 없어서", "늦게 줘서", "잘못 요청해서", "자료 누락으로") | 사실과 대응과 예정으로 바꾼다. 예: "회신이 없어 못 했음" 대신 "결제 연동: 테스트 키를 받는 대로 연결 예정" |
| 6 | **내부 개발 용어:** 브랜치, 커밋, 머지, PR, 서브모듈, 워크트리, 리팩터, 크론, 배포 파이프라인, API 경로, 함수나 테이블 이름, 이슈 번호, 내부 문서 ID가 없는가 | 고객이 보는 기능 이름과 화면 이름으로 바꾼다. 꼭 필요한 기술 용어는 고객이 이미 쓰는 말만 쓴다 |
| 7 | **알릴 필요 없는 내부 사정:** 개발 도구, AI나 에이전트 사용, 로컬 개발 환경, 서버 구성, 라이브러리 이름, 시험 방식의 세부, 작업 방식 설명이 없는가 | 결과만 남긴다. 예: "자동 시험 1,800개를 돌려 통과" 정도는 괜찮지만 "어떤 도구로 어떻게 돌렸는지"는 쓰지 않는다 |
| 8 | **보안과 개인정보:** 키, 계정, 내부 주소, 고객 데이터, 취약점을 구체적으로 설명한 문장이 없는가 | 보안 작업은 "보안 보강", "개인정보 보호 강화"처럼 결과만 쓴다. 어떤 허점이 있었는지는 쓰지 않는다 |
| 9 | **과장과 단정:** 확인하지 않은 "완료", 추정을 단정한 문장, 근거 없는 숫자가 없는가 | 확인한 것만 완료로 쓴다. 숫자는 근거가 있는 것만 남긴다 |
| 10 | **약속처럼 읽히는 일정:** 차주 계획이 확정된 약속처럼 읽히지 않는가 | 조건이 걸린 일은 `［조건 후］`로 조건을 함께 쓴다. 날짜를 확정하지 않는다 |
| 11 | **민감한 주제:** 비용, 인력, 다른 고객사, 계약 범위 다툼이 섞이지 않았는가 | 지운다. 필요하면 보고서 밖에서 사용자에게 따로 알린다 |
| 12 | **문제와 지연을 쓰는 법:** 숨기지 않으면서 "무엇이, 왜(사실만), 어떻게 대응, 언제까지"로 썼는가 | 문제를 감추지도 키우지도 않는다. 원인은 탓이 아니라 사실로 쓴다 |
| 13 | **형식과 윤문:** 1쪽인가. (진행중) 표시 규칙(주간보고 스킬 3장의 금요일 당일 작업, 4장의 갱신)을 지켰는가. 묶음 제목이 지난주와 이어지는가. [[05 쇠맛 줄이기]] 기준으로 기계 말투와 금지 표기(가운뎃점, 엠대시, 꺾쇠 괄호)가 없고, 항목이 짧은 명사구인가 | 05 쇠맛 줄이기 8장 자기 점검을 돌린다 |
| 14 | **발송 상태:** 요청서, 확인 질문, 회신처럼 보낸 문서를 "전달함", "회신 대기"로 쓴 항목이 `_발신함/목록.md`에서 "발송됨"(사용자 확인)인가 | 발송 확인이 없으면 "작성 완료, 전달 준비"로 쓴다(주간보고만의 예외, [[13 보낼 문서와 발송 상태]] §4). 보고 끝에 사용자에게 보냈는지 묻는다 |

## 3. 검수 결과를 남긴다

보고서를 만든 뒤 사용자에게 하는 보고에 **검수 결과**를 붙인다.

- **고친 것:** 몇 번 항목에서 무엇을 고쳤는지 한 줄씩
- **판단을 맡길 것:** 넣을지 뺄지 작성자가 정하기 어려운 것(예: 보안 작업을 어느 수준까지 알릴지, WBS에 없는 일을 어떻게 묶을지)
- **근거를 못 찾은 것:** 노트에는 있는데 커밋이 없는 일, WBS 번호를 못 찾은 묶음

## 4. 하지 않는 것

- 검수하면서 사실, 수치, 날짜를 바꾸지 않는다. 표현만 고친다.
- 지난주 보고서나 이미 고객에게 낸 보고서를 고치지 않는다.
- 커밋은 검수와 사용자 확인이 끝난 뒤에 한다. 방법은 주간보고 스킬을 따른다.
