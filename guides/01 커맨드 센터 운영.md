# 커맨드 센터 운영

> 먼저 [[00 세션 공통 지침]]을 읽는다. 여기는 **조율하는 쪽**의 것만 적는다.
> 기획, 백엔드, 웹, 앱 세션 지침 넷은 *일하는 세션*의 것이고, 이 문서는 *배정하고 합치는 세션*의 것이다.
> 아래 규칙은 전부 실제 사고에서 나왔다. 일반론처럼 보이면 그건 요약이고, 원인이 된 사건을 같이 적었다.

| §8 통합 빌드는 커맨드 센터가 소유한다 | 통합 빌드는 커맨드 센터가 소유하고, **포인터 기준**으로 전체 게이트와 계약 드리프트 가드를 돌린다 |
| §9 배포 상태를 관리한다 | **"지금 테스트할 수 있나"를 물으면 실제 배포된 것과 `main`을 대조해서 답한다.** |

| §11 세션이 나를 정정하는 것이 정상이다 | **장려해야 한다.** **배정 전에 코드로 대조한다.** |
| §12 검증 비용을 나눈다: 작업자는 좁게, 전체 게이트는 한 번 | 작업자는 바꾼 모듈의 관련 테스트만 돌리고, 커맨드 센터가 합칠 때 전체 게이트를 한 번 돌린다 |
| §13 문서 갱신과 레거시 표시: 배정과 검수 때 넣을 것 | 규칙 원본은 [[00 세션 공통 지침]] §14. 여기는 배정 프롬프트에 넣고 검수 때 확인하는 것만 남겼다 |

## 1. 이 역할이 왜 필요한가

세션이 넷이면 **아무도 전체를 보지 못한다.** 각자 자기 저장소에서 초록불을 보는데 합치면 깨진다.

더 나쁜 것은 **한 세션의 산출물이 다음 세션에게 원본 명세로 보인다**는 점이다.

커맨드 센터가 하는 일은 **답을 만드는 것이 아니라 답이 원문에 있는지 확인하는 것**이다.
[[00 세션 공통 지침]] §2의 조율자 판이다.

**메인 세션이 직접 코드를 고치는 것은 예외다.** 메인이 고치기 시작하면 그동안 배정, 검수, 취합이 멈춘다. 코드 수정은 일꾼에게 맡긴다.

#### 사례

> 한 세션 문서가 어떤 식별자를 "사용자 속성의 기준값"이라고 적었다. 다음 세션이 그걸
> 인용해 DB 스키마 주석에 요구사항으로 박았다. 원문을 열어보니 그 식별자는 **관리자 웹의 권한
> 필터**였다. 사용자 테이블과 무관했다. 두 저장소 코드에 잘못된 전제가 굳은 뒤였다.

## 2. 🔴 물리적 격리: 세션마다 작업 폴더

### 폴더 하나에 `HEAD` 는 하나뿐이다

세 세션이 같은 체크아웃을 쓰면 A 의 `checkout` 이 B 의 미커밋 편집을 그 자리에서 지운다.
`add -A` 는 B 가 편집 중인 파일을 집어간다. **커밋 전이라 reflog 에도 없다.**

```bash
git worktree add -b <세션이름> <세션폴더>/<저장소> origin/main
```

이력은 한 벌을 공유한다. 세션마다 늘어나는 용량은 소스 파일뿐이다.

#### 사례

실제로 주인 없는 미커밋 **2,837줄**이 나왔다. 누가 썼는지 아무도 몰랐다. 보존 브랜치로
빼돌린 뒤에야 트리를 움직일 수 있었다.

### 🔴 서브모듈은 따라오지 않는다

`git worktree add`는 **서브모듈을 채우지 않는다.** 세션 폴더는 만들어졌는데 안이 비어 있고,
세션들은 밖의 공용 체크아웃으로 나가서 일한다. **겉보기엔 격리인데 실제로는 한 책상이다.**

```bash
cd <세션폴더> && git submodule update --init --recursive
git submodule foreach 'git fetch origin && git checkout main && git pull --ff-only'
cat <세션폴더>/<서브모듈>/.git   # worktrees/<id>/modules/... 면 격리됨
```

#### 사례

> ⚠ 나는 여기서 **"서브모듈 gitdir 은 공유되니 이 방법은 안 먹힌다"** 고 단정했다. 틀렸다.
> Git 은 워크트리마다 따로 만든다. 검증 없이 한 층만 보고 결론 냈다.

### 따라오지 않는 것 둘째

`.env`, 서명키, 로컬 설정 등 **gitignore 대상은 복사되지 않는다.** 없으면 빌드도 기동도 안 된다.
세션 폴더를 만들 때 함께 넣고, **어떤 파일이 필요한지 목록을 문서에 남긴다.**

### 🔴 작업 폴더는 `worktrees/<저장소>/<이름>` 한 곳에 모은다 (2026-10-29)

**위치**

```
work/<프로젝트>/
├─ <상위 저장소>/      # 기준 체크아웃. 사용자가 IDE로 보는 자리. 기본 브랜치(main, 없으면 master)에 두고 브랜치를 바꾸지 않는다
└─ worktrees/
   ├─ <저장소 A>/  dev  stg  prod  <작업이름>…
   ├─ <저장소 B>/  dev  stg  <작업이름>…
   └─ …
```

- 저장소는 프로젝트마다 다르다(예: 앱, 서버, 관리자 웹). 늘 있는 폴더도 그 저장소가 쓰는 브랜치만큼만 둔다.
- 상위 저장소는 기본 브랜치에서만 작업하므로([[00 세션 공통 지침]] §3) 상위 저장소용 작업 폴더를 `worktrees/` 안에 따로 만들지 않는다.
- 뿌리에 `wt-*`를 새로 만들지 않는다. `worktrees/` 밖에 작업 폴더를 두지 않는다.
- 저장소 이름은 폴더로, 작업 이름은 짧은 영문 한 단어로 짓는다(예: `worktrees/<저장소>/refund`).

> ⚠ 레거시 (2026-11-16): 예전 그림에는 상위 저장소의 작업 폴더 `worktrees/doc/dev`와 `worktrees/doc/<작업이름>`이 있었다. 2026-11-09부터 상위 저장소는 기본 브랜치에서만 작업하므로(00 §3) 상위 저장소용 dev 폴더와 작업 브랜치 폴더를 새로 만들지 않는다. 이미 있으면 진행 중인 작업을 합친 뒤 정리한다.

**늘 있는 폴더(지우지 않는다)**

| 폴더 | 브랜치 | 쓰임 |
|---|---|---|
| `<저장소>/dev` | `dev` | 리뷰 끝난 작업을 모으는 곳. 로컬 서버와 관리자 웹도 여기서 띄운다 |
| `<저장소>/stg` | 스테이징에 올린 커밋 | 스테이징 빌드와 대조 |
| `<저장소>/prod` | `prod` | 운영 빌드(앱이면 iOS 아카이브 포함) |
| `<저장소>/main`, `<저장소>/master`, `<저장소>/rel-*` | 같은 이름의 브랜치 | 기본 브랜치나 출시 브랜치를 따로 볼 때 |
| ~~`doc/dev`~~ | ~~`dev`~~ | 레거시. 위 레거시 표시를 본다 |

정리 훅은 이 폴더 이름(dev, stg, prod, main, master, rel-*)을 늘 있는 폴더로 보고 지우지 않는다.

- 🔴 **늘 있는 폴더에서는 브랜치를 바꾸지 않는다.** 작업 브랜치는 새 폴더를 파서 쓴다. 쓰기 전에 `git -C worktrees/<저장소>/dev branch --show-current`가 `dev`인지 본다.
  - 사례(레거시, 상위 저장소용 dev 폴더가 있던 때의 일이다. 규칙은 지금도 유효하다): 10/30 `doc/dev`가 다른 세션의 작업 브랜치로 바뀌어 있어서, dev에 상위 포인터를 올리려던 세션이 그 폴더를 쓸 수 없었다. 바뀐 걸 모르고 그 폴더에서 커밋했으면 남의 브랜치에 섞였다.

**만들 때**

```bash
cd <WORK_DIR>/<프로젝트>
git -C worktrees/<저장소>/dev fetch -q origin
git -C worktrees/<저장소>/dev worktree add -b fix/<이름> ../<이름> origin/dev   # worktrees/<저장소>/<이름>에 생김
```

- git 밖 키 파일과 로컬 설정은 따라오지 않는다(앞의 "따라오지 않는 것 둘째"). 같은 저장소의 dev 폴더에서 **복사**한다. 저장소마다 필요한 파일 목록은 프로젝트 문서에 적어 둔다.

**지울 때: 합친 날 바로**

`dev`에 합쳐지고 수정 중 파일이 없으면 그날 지운다. 휴지통으로 버리지 말고 git으로 지운다(그래야 저장소가 폴더가 없어진 걸 안다).

```bash
git -C worktrees/<저장소>/<이름> status --porcelain        # 비어 있어야 한다
git -C worktrees/<저장소>/<이름> branch -r --contains HEAD # 한 줄 이상 나와야 한다(커밋이 원격에 있음)
git -C worktrees/<저장소>/dev worktree remove ../<이름>
```

**자동 정리 (2026-11-04 추가):** 합친 작업 폴더는 세션을 시작하고 끝낼 때 전역 훅이 조건을 확인해 지운다. 지우는 조건, 미리 보기 방법, 남은 폴더를 판단하는 법은 [[10 자동 장치]] §3에 있다.

**옮길 때:** 폴더를 손으로 `mv` 하지 않는다. `git worktree move <옛 경로> <새 경로>`를 쓴다.

**세션에 알리기:** 작업 세션에 폴더를 배정할 때 "작업 폴더는 `worktrees/<저장소>/<이름>`" 한 줄을 같이 준다. 옛 `wt-*` 경로를 기억하는 세션은 새 경로로 바꾸게 한다.

#### 사례

작업마다 폴더를 파고 안 지웠더니 프로젝트 뿌리에 `wt-*` 폴더가 **86개** 쌓였다(10/26 정리 직후 다시 늘어 102개, 14개, 86개 순으로 기록됐다). 어느 게 지금 쓰는 폴더인지 사람도 세션도 헷갈렸다. 그래서 위치와 이름, 지우는 시점을 정했다.

### 격리로 안 풀리는 것은 조율로 푼다

개발 DB 하나, 포트, 실기기는 격리되지 않는다. `docker compose up`도 `adb install`도 한 번에 하나다.
**공유 자원을 건드리기 전에 통지**하는 규칙을 세운다. 한 세션이 시드를 재실행해 다른 세션이
쓰던 계정 상태를 바꿨는데, **사전 통지가 있었기 때문에** 문제가 되지 않았다.

## 3. 전달: `ok: true`는 전달이 아니다

세 세션에 공지를 보내고 "전달 완료"라고 보고했는데, 확인하니 아무도 안 읽고 있었다(`read=0`). 메시지를 넣었다는 것과 상대가 읽었다는 것은 다르다. 읽었는지 확인하고, 안 읽었으면 상대 터미널에 한 줄 넣는다.

자세한 규칙(메시지와 터미널 입력의 차이, `ok: true`와 `read=0`의 뜻, 긴 회신을 받는 법): [[00 세션 공통 지침]] §10

## 4. 루프

현황 취합, 사용자 보고, 태스크 분배, 완료 회신, 통합 빌드를 한 바퀴로 삼아 되풀이한다.

사용자는 직접 테스트하며 이슈를 준다. 그 이슈가 다음 라운드 태스크가 된다.

### 현황 요청은 형식을 고정한다

```
1. 지금 진행 중 (한 줄)
2. 남은 작업: 건명, 크기(S, M, L), 상태(착수 전, 진행 중, 막힘), 막혔다면 무엇에
3. 대기 중인 결정
4. 공유 자원 필요 여부와 시점
5. 넘겨야 할 것 / 받아야 할 것
```

**"상태는 추정 말고 실제로 확인한 것만"**을 반드시 넣는다. 이 한 줄 때문에 한 세션이 실제로
테스트를 돌려보고 답했고, 그 과정에서 자기 보고의 오류를 스스로 찾았다.

### 🔴 일꾼은 한 번에 4명까지 (2026-11-12)

메모리 부담 때문에 한 세션이 동시에 돌리는 서브에이전트는 기본 4명까지다. 프로젝트별로 다르게 설정할 수 있다([[10 자동 장치]]). 일을 덜 하는 것이 아니라 차례를 정하는 것이다.

- 일을 먼저 전부 쪼개 순서를 정한다(막힌 것 없는 것, 다른 일의 앞 단계인 것부터).
- 4명에게 맡기고, 하나가 끝났다는 알림이 오면 그 결과를 검수한 뒤 다음 일을 맡긴다. 메인은 그사이 검수와 다음 배정 준비를 한다.
- 5명째를 띄우면 훅(subagent-limit)이 막는다. 막히면 기다린다. 우회하지 않는다.
- 워크플로처럼 여러 에이전트를 한꺼번에 도는 도구도 동시 실행을 4명 안으로 잡는다.

### 🔴 일꾼은 이어 쓰고, 검수는 늘 새로 (2026-11-13)

일꾼을 쓰고 바로 버리면 다음 일꾼이 지침서, 코드, 앞 결과를 처음부터 다시 읽느라 시간과 비용이 든다. 끝난 일꾼에게는 `SendMessage`로 이어서 맡길 수 있고, 그 일꾼은 읽은 내용을 그대로 갖고 있다. 대화 앞부분이 캐시에 남아 있는 동안(약 1시간)은 다시 읽는 비용도 적다.

| 상황 | 방법 |
|---|---|
| 같은 화면이나 기능의 이어지는 일(리뷰 지적 반영, 추가 수정, 같은 범위의 다음 단계) | 그 일꾼을 이어서 쓴다 |
| 성격이 다른 일, 다른 저장소의 일 | 새 일꾼 |
| 코드 리뷰, 검수, 재리뷰 | 항상 새 일꾼. 자기가 만든 것을 자기가 검수하지 않는다 |
| 일꾼 대화가 길어졌을 때(약 1시간 넘게 쉼, 또는 큰 작업 2~3건 처리) | 인계 메모를 남기게 한 뒤 새 일꾼으로 교대 |

- **인계 문서:** 교대하거나 일을 끝낼 때 일꾼이 인계 문서를 남기고, 새 일꾼은 그것부터 읽는다. 위치와 담을 항목은 [[00 세션 공통 지침]] §8에 있다.
- **낡은 기억 조심:** 이어 맡길 때는 그사이 바뀐 것부터 확인하게 한다. 다른 일꾼의 커밋, 통합 브랜치의 변화, 같은 폴더에 커밋 안 된 변경이 대상이다. 이어 맡기는 메시지 첫 줄에 "먼저 git log와 git status로 그사이 바뀐 것을 확인하라"를 넣는다.
- 메인은 일꾼마다 무엇을 맡았는지(영역, 일꾼 이름) 기억해 두고, 같은 영역 일이 오면 그 일꾼에게 보낸다. 4명 제한은 일하는 동안만 센다. 대기 중인 일꾼은 자리를 차지하지 않는다.

#### 사례

> 2026-11-12에 같은 작업 폴더를 쓰던 두 일꾼이 서로의 커밋 안 된 변경을 지웠다. 그래서 이어 맡길 때는 같은 폴더의 커밋 안 된 변경까지 먼저 확인하게 한다.

### 배정할 때는 막힘 없는 것을 항상 하나 이상 함께 준다

그래야 대기가 생겨도 멈추지 않는다. 세션이 질문을 남기고 유휴로 들어가 아무도 모른 채 시간이
흐르는 일이 반복됐다. 규칙 넷을 준다:

1. 물어볼 것이 생기면 **즉시** 보낸다 (작업 끝날 때까지 모으지 않는다)
2. 보낸 뒤 **멈추지 않는다** (막힌 건은 두고 다음 것으로)
3. 대기에 들어가면 **그 사실을 알린다**: 무엇을 기다리는지, 그것만 오면 무엇이 풀리는지
4. 답이 안 오면 **재촉한다**

## 5. 🔴 "없다"는 주장은 찾은 범위까지만 참이다

**커맨드 센터가 가장 많이 틀린 지점.** 하루에 세 번 같은 실수를 했다.

- **자르지 않는다.** 전체 건수를 세서 보고한다
- **검색 범위를 함께 밝힌다**: "`planning/` 에서 0건" 과 "없다" 는 다른 말이다
- 부재를 근거로 승인할 때는 특히 그렇다. 존재를 놓치는 것보다 **부재를 잘못 단정하는 쪽이
  비싸다**. 전자는 나중에 발견되고 후자는 승인이 되어 나간다

#### 사례

> 검색 결과를 `| head -8` 로 자르고 "그런 코드는 없다"고 단언했다. 실제 51건이었고 잘린 뒤쪽에
> 쓰기 경로가 있었다. 그 판단으로 "머지해도 안전"이라 승인했고, **다른 세션이 잡지 않았으면
> 앱 빌드가 깨진 채 머지됐다.**

> 한 저장소만 뒤지고 "문서 어디에도 없다"고 했다. 다른 디렉터리에 있었다. 두 번.

## 6. 애매한 것의 결정권자는 사용자다

커맨드 센터도 **대신 정하지 않는다.**

| 커맨드 센터가 답한다 | 사용자가 정한다 |
|---|---|
| 원문에 답이 있는 것 (파일과 라인 인용 가능) | 원문에 답이 없는 것 |
| 사실 확인 (그 코드가 있나, 이게 깨지나) | 사용자 눈에 보이는 것 (문구, 화면, 흐름) |
| 기존 패턴과의 기계적 일관성 | 되돌리기 비싼 것 (스키마, 계약, 저장 형식) |
| 문서끼리 충돌할 때 어느 쪽이 유효한지 | 범위, 우선순위, 일정 |

경계가 애매하면 **올리는 쪽**을 택한다. "그건 알아서 하라"는 말을 듣는 비용보다, 정해진 줄
알았던 것이 나중에 뒤집히는 비용이 크다.

올릴 때는 **배경지식 없이 읽을 수 있게** 쓴다: 무엇을 정해야 하는지, 각 선택이 무엇을 잃는지,
정해지지 않으면 무엇이 막히는지. 한 번에 여러 건을 올리면 결정이 늦어진다. **막고 있는 것부터
하나씩.**

**사용자에게는 갈림길일 때만 묻는다.** "무엇을 먼저 할까요?"로 보고를 끝내지 않는다. 일의 순서는 메인이 정하고, 되돌리기 어려운 선택만 묻는다.

## 7. 태스크는 브랜치로 시작해서 서브모듈 갱신으로 끝난다

```bash
git switch -c feat/<이름> origin/main     # 1. 시작
# 2. 진행: 의미 있는 단위마다 커밋하고 푸시. 한 태스크를 한 커밋으로 몰지 않는다
# 3. 검사: 리뷰와 관련 테스트를 돌리고 결과를 사용자에게 보고, 승인을 받는다
git rebase origin/main && git switch main && git merge --no-ff feat/<이름>   # 4. 승인 뒤 머지
cd <슈퍼프로젝트> && git add <서브모듈> && git commit && git push            # 5. 여기까지 해야 끝
```

> **2026-11-04 바뀜:** 예전 순서에는 검사와 승인 단계가 없었다. 이제 보호 브랜치(main, dev, prod, staging 등)로 머지하거나 푸시하는 것은 3번 검사 결과를 사용자에게 보여 주고 승인을 받은 뒤에만 한다([[00 세션 공통 지침]] §8 브랜치 규칙). 작업 브랜치(2번)의 커밋과 푸시는 묻지 않는다.

5번은 상위 저장소의 기본 브랜치에서 하고, 보호 브랜치 푸시라 확인을 받는다. 연결하는 커밋은 서브모듈 main에 있는 커밋이어야 한다([[00 세션 공통 지침]] §3).

**5번이 조용히 빠진다.** 세 저장소 포인터가 전부 뒤처져 있었다. 각 저장소만 보면 최신인데
**슈퍼프로젝트를 클론한 사람은 옛 코드를 받는다.** 서브모듈 안에서는 보이지 않는다.

통합 빌드도 **포인터 기준**으로 돌려야 한다. 한 세션이 "포인터가 뒤처졌다"고 알려주지 않았으면
옛 코드로 빌드하고 "초록"이라 보고할 뻔했다.

## 8. 통합 빌드는 커맨드 센터가 소유한다

각 저장소가 초록이어도 합치면 깨진다. 머지된 뒤 도는 **사후 확인**이지만 계약 불일치는 여기서만
잡힌다.

1. 최신 pull (포인터 기준)
2. 저장소별 전체 게이트
3. 계약 드리프트 가드
4. 실제 기동과 스모크 테스트

#### 사례

실제로 잡은 것: 서버가 새 엔드포인트를 추가하고 **계약 파일을 같이 안 올려서**, 앱이 그 API 를
호출할 방법이 없는 상태. 두 세션이 서로를 기다릴 뻔했다.

### CI 가 없으면 로컬 게이트가 유일한 방어선

자동 검사가 꺼져 있으면 **테스트가 빨간 채로 머지된다.** e2e 2건이 실패한 채 들어갔고 다른
세션이 우연히 돌려보고서야 발견됐다. 테스트는 제대로 작동했고 아무도 안 봤을 뿐이다.

머지 전 게이트를 규칙으로 세우고 **저장소별 명령을 문서에 적어둔다.** 기억에 의존하면 빠진다.

QC 문서 맨 앞에 **"이건 결함이 아니다"** 목록을 두는 것이 특히 효과적이다: 죽은 아이콘,
미구현 버튼, mock 어댑터.

## 11. 세션이 나를 정정하는 것이 정상이다

근거를 들어 지시를 고친 세션이 여럿 있었고 **전부 그쪽이 맞았다.**

**장려해야 한다.** 지시를 그대로 따르는 세션만 있으면 커맨드 센터의 오류가 그대로 코드가 된다.
받은 보고도 같은 태도로 본다. **배정 전에 코드로 대조한다.**

#### 사례

| 내 지시 | 세션의 정정 |
|---|---|
| "A를 B로 교체하라" | "교체하면 A가 목록에서 빠진다. 명칭만 틀렸으니 정정하고 추가하는 것이 맞다" |
| "쓰기 경로 0건, 머지 안전" | "2건 있다. 지금 머지하면 빌드가 깨진다" |
| "권한 선언부터 새로 해야 하니 L" | (내가 정정) "이미 선언돼 있다. M 이다" |

## 12. 🔴 검증 비용을 나눈다: 작업자는 좁게, 전체 게이트는 한 번 (2026-10-30)

### 12.1 확인 실행을 줄인다

| 누가 | 무엇을 돌리나 |
|---|---|
| 작업자 | 바꾼 모듈의 **관련 테스트만**. 전체 스위트를 반복해서 돌리지 않는다 |
| 작업자 (일부러 깨뜨려 보기) | 그 수정을 지키는 **테스트 하나만** 다시 돌린다 |
| 커맨드 센터 | 합칠 때 **전체 게이트를 한 번** 돌린다(§8). 실패하면 그때 작업자에게 돌려보낸다 |

- 캐시를 무시하는 강제 재실행(`--rerun-tasks` 같은 것)은 쓰지 않는다. 메모리 부족으로 죽고 시간만 쓴다.
- 인프라성 일회 실패(컨테이너 연결 끊김, 메모리 부족)는 **실패한 클래스만** 한 번 다시 돌린다.
- 배정 프롬프트에 이 표를 그대로 넣는다. 넣지 않으면 작업자는 안전하게 하려고 전체를 돌린다.

### 12.2 리뷰 범위를 줄인다

- **재리뷰는 고친 부분만 본다.** 앞 회차에서 통과한 부분을 다시 검토하지 않는다(`git diff <앞 회차 끝>..HEAD`).
- **높음 이상만 합치기를 막는다.** 중간은 같은 작업에서 고칠지 판단하고, 낮음은 기록해 두고 다음 작업으로 넘긴다.
- 보안, 인증, 결제, 데이터 삭제처럼 되돌리기 비싼 변경은 예외로, 중간도 막을 수 있다.
- 리뷰어 프롬프트에 "이번에 볼 범위"와 "막는 기준"을 적는다. 적지 않으면 리뷰어는 전부를 다시 본다.

### 12.3 멈춘 작업자를 일찍 찾는다

- 작업자가 **"기다리는 중"만 반복하거나 오래 조용하면** 바로 확인한다. 작업 폴더의 `git status`, 최근 커밋 시각, 산출물 시각을 본다.
- 오지 않는 알림이나 이미 끝난 백그라운드 작업을 기다리는 것이 흔한 원인이다. 확인되면 "기다리지 말고 이어서 하라"고 보낸다.
- 검증자가 결론 없이 끝나면 결과 파일(테스트 결과 XML, 로그)을 직접 연다. **보고가 없다는 것을 통과로 읽지 않는다.**
- 공용 잠금(빌드 잠금 등)을 쓰는 작업이 여럿이면 순서를 정해 준다. 서로 기다리는 것도 멈춤이다.

#### 사례

> 한 프로젝트의 백엔드에서 작업 하나가 몇 시간씩 걸렸다. 원인은 코드가 아니라 확인 실행이었다.
> 작업자가 수정할 때마다 전체 테스트를 두 번씩 돌렸고, 일부러 깨뜨려 보는 확인도 전체로 돌렸고,
> 캐시를 무시하는 전체 재실행까지 했다. 빌드 잠금이 하나라 작업자 셋과 검증자가 서로를 기다렸다.
> 리뷰는 회차마다 처음부터 다시 봤고, 낮음 지적까지 막아서 같은 작업이 세 번 돌았다.
> 그 사이 작업자 하나는 오지 않는 알림을 기다리며 한 시간 넘게 멈춰 있었고 아무도 몰랐다.

## 14. 구조를 익히는 배정과 검수 (2026-11-16)

사용자가 승인만 하는 자리에서 구조를 판단하는 자리로 옮겨 가게 돕는다(00 §16).

### 14.1 배정 전 예측
- 여러 파일이나 구성 요소, 계약을 건드리는 큰 기능을 맡기기 전에, 사용자가 요청에 "예측:"으로 자기 안(어디를 어떻게 나눌지 두세 줄)을 적었으면 일꾼에게는 알리지 않고 따로 둔다.
- 결과 보고에 "예측과 실제 구조" 표를 붙여 같은 점과 다른 점, 다른 이유를 짧게 쓴다. 예측이 없으면 이 표는 생략한다. 따로 묻지 않는다.

### 14.2 검수할 때 묻는 구조 질문
일꾼 보고를 검수할 때 아래 다섯 가지에 답이 있는지 보고, 없으면 일꾼에게 다시 묻거나 사용자 보고에 "확인 못 함"으로 적는다.
1. 경계: 이 변경은 어느 구성 요소에 들어갔고, 경계를 넘는 곳(API, 이벤트, 공유 테이블)은 어디인가
2. 데이터 주인: 새로 쓰거나 바꾸는 데이터의 주인은 누구인가
3. 실패: 외부 연동이나 네트워크가 실패하면 사용자에게 무엇이 보이나
4. 바꾸기 비용: 나중에 이 결정을 되돌리려면 무엇을 고쳐야 하나
5. 다른 안: 고르지 않은 방법과 그 이유

## 부록: 옮겨 쓸 때 먼저 돌릴 진단

```bash
git worktree list                        # 세션들이 실제로 어느 폴더를 쓰는가
ls <세션폴더>/<서브모듈>                  # 서브모듈이면 비어 있을 수 있다
git ls-tree HEAD <서브모듈>               # vs git -C <서브모듈> rev-parse HEAD
git -C <저장소> status --porcelain        # 공용 폴더에 주인 없는 미커밋이 있는가
```

둘 이상이 같은 경로를 쓰면 해당된다. **마지막 항목에 주인 없는 변경이 있으면 먼저 보존
브랜치로 빼내고** 구조를 바꾼다. 순서를 바꾸면 그걸 잃는다.
