# 보고 지침

> 보고를 읽는 사람은 **이 대화와 코드, 이슈 목록을 한 번도 보지 않은 사람**이라고 가정한다.
> 읽는 사람이 보고만 읽고도 무슨 일이 있었는지, 어디에서 다시 확인할 수 있는지, 무엇을 결정하면 되는지 알 수 있어야 한다.

관련 문서: [[05 쇠맛 줄이기]]는 문장을 다듬는 기준이고, [[17 기술 문서 쓰기]]는 읽는 사람이 무엇을 하거나 알아내야 하는 글의 기준이다. 보고 틀은 이 문서가 원본이고, [[00 세션 공통 지침]] §8과 [[02 이슈 세션 운영]] §8은 이 문서를 가리킨다.

---

## 1. 결론을 맨 앞에 쓴다

첫 한두 줄에 결론을 쓴다. 읽는 사람이 거기에서 읽기를 멈춰도 상황을 알 수 있어야 한다.

- 작업이 끝났는지, 끝나지 않았는지, 일부만 끝났는지
- 사용자가 결정해야 할 일이 있는지

작업 과정과 시도한 방법, 배경 설명은 결론 뒤에 둔다. 읽는 사람에게 필요하지 않으면 쓰지 않는다.

## 2. 🔴 작업자만 아는 말을 쓰지 않는다

아래 표의 왼쪽 표현은 본문에 쓰지 않는다. 꼭 필요하면 기능 이름으로 먼저 설명하고, **괄호 안에 참고로만** 붙인다.

| 쓰지 않는 표현 | 대신 쓰는 표현 |
|---|---|
| 이슈 번호와 문서 ID (`#142`, `ISSUE-118`, `REQ-00`) | 어떤 문제인지 설명하는 한 문장 |
| 함수, 변수, 파일, 클래스 이름 (`rewardGranted`, `useAuthStore`) | 사용자 눈에 보이는 기능 이름과 화면 이름 |
| 브랜치, 커밋, 워크트리, 세션, 에이전트 이름 | "수정한 코드", "다른 작업"처럼 하는 역할을 드러내는 말 |
| "앞에서 말한 그거", "아까 그 문제", "그 화면" | 가리키는 대상의 이름을 다시 부른다 |
| 이 대화 안에서만 정한 줄임말 | 처음 읽는 사람도 알 수 있게 풀어 쓴다 |

**나쁜 예**

> 이슈 #12에 해당하는 `rewardGranted` 누락은 `Service.finish()`에서 플래그를 안 세워서였고, REQ-1 반영 후 해결됐습니다.

**좋은 예**

> 참여를 끝낸 사용자가 보상을 받지 못하던 문제를 고쳤습니다. 참여가 끝났다는 표시를 서버에 저장하지 않고 있었던 것이 원인이었습니다. (참고: 이슈 #12)

## 3. 문제를 보고할 때는 육하원칙과 재현 방법을 쓴다

| 항목 | 쓰는 내용 |
|---|---|
| **누가** | 어떤 사용자에게 일어났는지 (일반 회원, 관리자, 비회원 등) |
| **언제** | 어떤 조건이나 시점에 일어났는지 (첫 로그인 직후, 자정이 지난 뒤, 쿠폰이 0장일 때) |
| **어디서** | 어느 앱의 어느 화면에서 일어났는지, 그리고 그 화면까지 가는 경로 (홈에서 이벤트를 거쳐 상세로) |
| **무엇을** | 사용자가 어떤 행동을 했는지 |
| **어떻게** | 실제로 일어난 결과와, 원래 일어나야 했던 결과 |
| **왜** | 원인. **확인한 원인**과 **추정한 원인**을 나누어 쓴다 |

그다음 **재현 방법**을 쓴다.

```
재현 방법
  조건 : 일반 회원 계정, 저장한 배송지가 2개 이상
  1. 앱에 로그인한다
  2. 홈에서 마이페이지를 거쳐 배송지 바꾸기로 들어간다
  3. 다른 배송지를 고른다
  기대 결과 : 주문서에 고른 배송지가 보인다
  실제 결과 : 주문서에 이전 배송지가 그대로 보인다
  빈도 : 매번 일어난다 (3번 시도해서 3번 모두)
```

- 재현하지 못했으면 **재현하지 못했다고 쓰고**, 어떤 방법으로 시도했는지도 함께 쓴다.
- 원인을 아직 모르면 "원인을 확인하는 중"이라고 쓰고, 원인을 지어내지 않는다.

## 4. 작업 결과를 보고할 때

1. **무엇이 바뀌었는지**를 사용자 눈에 보이는 변화로 쓴다.
2. **직접 확인하는 방법**을 쓴다. 어느 화면에서 무엇을 누르면 무엇이 보이는지, 읽는 사람이 그대로 따라 할 수 있게 쓴다.
3. **확인한 내용**에는 실제로 돌려 본 것만 쓴다. 돌려 보지 않은 것은 "확인하지 않음"이라고 쓴다.
4. **하지 못한 일과 남은 일**을 숨기지 않고 쓴다.
5. **구조 메모(코드나 구조를 바꾼 작업일 때, 세 줄 이내):** 이 변경이 기대는 스택 독립 개념(예: 상태 관리, 트랜잭션, 재시도), 같은 개념이 다른 스택에서 어떻게 생겼는지 한 줄, 이 변경에서 틀리기 쉬운 지점 하나. 사용자가 구조를 익히게 하려는 메모라 짧게 쓴다(00 §16). 다른 스택 비교는 틀리기 쉬우니 확실하지 않으면 쓰지 않는다.

## 5. 결정을 요청하거나 방안을 제시할 때

- 무엇을 정해야 하는지 한 문장으로 쓴다.
- 선택지마다 **그 안을 고르면 어떻게 되는지** 쓴다.
- 권하는 안과 그 이유를 쓴다.
- 작업 순서처럼 작업자가 정해도 되는 일은 묻지 않는다.

### 🔴 가장 안전한 정석 방안을 항상 함께 낸다 (2026-11-04 사용자 지시)

방안을 제시할 때는 지금 바로 할 수 있는 안만 내지 않는다. **변경이 크거나 구조를 바꿔야 하더라도, 가장 안전하고 업계에서 정석으로 통하는 방안(best practice)을 함께 낸다.** 작은 안만 보여 주면, 사용자는 더 나은 길이 있다는 것을 모른 채 결정하게 된다.

- 정석 방안에는 무엇이 바뀌는지, 드는 비용(시간, 영향 범위, 되돌리기 어려운 정도), 왜 가장 안전한지를 쓴다.
- 정석 방안을 권하지 않는다면 그 이유(지금 비용이 너무 크다, 다음 출시 뒤로 미루는 편이 낫다 등)를 쓴다.
- 정석 방안이 지금 안과 같으면 "이 안이 정석이다"라고 한 줄로 밝힌다.
- 정석이라고 말하려면 근거(공식 문서, 널리 쓰이는 관례, 실제 사고 사례)를 붙인다. 근거가 없으면 정석이라고 부르지 않는다.

## 6. 보내기 전에 점검한다

- [ ] 첫 두 줄만 읽어도 결론을 알 수 있는가
- [ ] 이 대화를 보지 않은 사람도 이해할 수 있는가
- [ ] 이슈 번호, 영어 식별자, 브랜치 이름이 본문에 남아 있지 않은가 (괄호 안의 참고 표기는 괜찮다)
- [ ] 문제 보고라면 누가, 언제, 어디서, 무엇을, 어떻게, 왜가 모두 들어 있는가
- [ ] 재현 방법이 있는가, 없다면 재현하지 못한 이유가 있는가
- [ ] 확인한 내용과 추정한 내용이 나뉘어 있는가
- [ ] [[05 쇠맛 줄이기]] 8장 자기 점검을 했는가 (특히 가운뎃점, 엠대시, 꺾쇠 괄호를 쓰지 않았는가). 읽는 사람이 무엇을 하거나 알아내야 하는 보고면 [[17 기술 문서 쓰기]]도 따랐는가
