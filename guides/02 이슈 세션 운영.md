# 이슈 세션 운영

> 먼저 [[00 세션 공통 지침]]을 읽는다. 여기는 **이슈를 맡는 쪽**의 것만 적는다.
> 배정하고 합치는 쪽은 [[01 커맨드 센터 운영]].

---

## 1. 🔴 저장소로 나누지 않고 이슈로 나눈다

**이것이 이전 모델과 갈리는 지점이다.**

[[기획 세션 지침]], [[백엔드 세션 지침]], [[웹 세션 지침]], [[앱 세션 지침]] 넷은
**저장소별로 세션을 나누던 시절**의 구조다. 그 문서들의 도메인 지식은 그대로 유효하지만,
**"내 저장소만 고친다"는 경계는 더 이상 쓰지 않는다.**

> **왜 바꿨나.** 증상은 한 화면에서 보이는데 원인이 다른 저장소에 있는 일이 잦다.
> 저장소로 나누면 *"우리 쪽은 정상"*이 세 번 돌아오고 **아무도 안 고친다.**
> 실제로 이미지가 전부 안 보이던 건은 **앱에서 보였고 원인은 서버의 주소 조립**이었다.

이슈 세션은 앱, 서버, 관리자를 **다 열고 끝까지 간다.** 넷은 이제 **그 영역을 건드릴 때
펴 보는 함정 모음**이다.

⚠ 옛 규칙 *"범위 밖 저장소는 읽되 고치지 않는다"*는 폐기됐다([[00 세션 공통 지침]] §3). 대신 **무엇을 맡았는지는 여전히 사용자 지시에서 확인**한다.
이슈를 맡았다고 그 김에 눈에 띈 다른 것까지 고치지 않는다.

---

## 2. 절차

1. 이슈를 받는다.
2. 화면 문제인지 가른다. 화면 문제면 목업부터 만들고(§3), 아니면 원인을 코드로 찾는다(§4).
3. 수정방안을 사용자에게 올린다.
4. 🔴 **검토와 승인을 받는다. 여기서 반드시 멈춘다.**
5. 고치고, 검증하고, 더블체크(§5)한 뒤 보고한다.

### 🔴 승인 전에 고치지 않는다

원인을 찾았다고 바로 손대지 않는다.

**왜.** 고칠 방법이 하나인 경우는 드물고, 어느 쪽을 고르냐가 **명세 변경, 클라이언트 확인, 다른
화면 영향**을 부른다. 먼저 고쳐 놓고 보고하면 사용자는 **이미 벌어진 일을 되돌릴지**를
판단하게 된다. 즉 선택지가 줄어든 뒤에 묻는 셈이다.

예외는 **명백한 오타와 깨진 빌드** 정도고, 그것도 보고에 적는다.

### 🔴 의도부터 검증한다

기능을 제안하거나 구현하거나 보고할 때, **그 기능이 의도(누가, 어떤 상황에서, 왜 쓰는가)에 맞는지**를 가장 먼저 확인하고 근거와 함께 쓴다. "API가 있다", "시험이 통과한다", "화면이 돈다"는 그다음이다.

- 의도의 출처를 인용한다: 고객의 원안, 미팅 기록, 화면 구조(IA) 문서.
- **API가 살아 있어도, 그 화면을 쓰는 사람의 관점이 다르면 의도 위반이다.** 예: 관리자용 화면에 일반 사용자용 자가 점검 기능이 그대로 남아 있는 경우.
- 근거가 없으면 "추정"으로 표시하고 고객에게 확인할 질문으로 남긴다.

> 실제 사고: 서버에 API가 있다는 이유로 우선순위를 정했다가, 실제 사용자 설문에서 수요가 없던 기능을 1순위로 올렸다.

### 🔴 범위 밖 기존 동작이 바뀌면 반영하기 전에 보고한다

작업자나 리뷰어가 낸 수정이 **이번 작업 밖의 기존 화면 동작**(캐시, 조회 방식, 정렬 등)을 바꾸면, 반영하기 전에 무엇이 바뀌는지와 되돌리는 선택지를 사용자에게 먼저 보고한다. 리뷰 지적을 반영하는 것이라도 같다.

> 실제 사고: 리뷰 지적(중복 제공자)을 반영하면서 기존 화면의 조회에 캐시를 붙였다. 결과는 유지했지만, 성능 개선은 따로 점검하고 검수받기로 한 절차를 건너뛴 것이 문제였다.

## 3. 화면 문제일 때는 목업이 먼저다

목업은 "버튼이 이렇게 생겼다"를 보여 주는 그림이 아니라 **판단을 받기 위한 문서**다.
셋이 빠지면 다시 만들게 된다.

### ① 거기까지 가는 동선과, 그 자리가 왜 문제인지

버튼만 떼어 놓고 보여 주면 보는 사람이 상황을 복원할 수 없다.

> 예: 지도에서 핀을 누르고, 미니카드에서 "자세히"를 눌러 들어간 화면의 하단 고정 바.
> *"하단에 늘 떠 있고 엄지가 닿는 자리라 습관적으로 눌린다"*까지 적는다.

### ② 지금 화면을 정확히

🔴 **눈대중으로 그리지 않는다.** 색, 치수, 문구를 **테마 파일과 구현에서 실제 값으로 옮긴다.**

> **실제 사고.** 손으로 대충 그린 상자에 이모지를 얹어 올렸다가 품질 때문에
> 한 번에 반려됐다. 확정 디자인 HTML 에서 프레임 폭, 글꼴, 팔레트, 아이콘 경로를 그대로
> 가져오자 통과했다. **들이는 시간은 비슷하고 결과가 갈린다.**

### ③ 바뀌는 것과 그대로인 것을 항목으로

"좋아졌다"가 아니라 "이 줄이 이렇게 바뀐다"로 쓴다.

```
=  화면 구성과 색은 그대로
+  ON일 때 글자가 "찜 13"에서 "찜 취소"로 바뀐다
+  버튼 안에 가장 긴 문구만큼 자리를 미리 잡는다(폭 고정)
```

### ④ 경계 상황을 같이 그린다 (경계 상황 목록의 원본)

평범한 예시 데이터만 그리지 않는다. 목업마다 **경계 상황 표**를 넣고, 가장 까다로운 경우는 화면에 직접 그린다. 다른 지침서는 경계 상황을 이 절로 가리킨다.

- 항목이 아주 많을 때(최대치), 1개일 때, 0개일 때, 값이 비어 있을 때, 일부 또는 전체 조회 실패
- 긴 이름, 알 수 없는 값, 권한 없는 사용자
- 큰 글씨: 기기 글자 크기 1.3배와 200%
- 가장 좁은 화면 폭: 앱은 360dp, 웹은 그 프로젝트가 정한 최소 폭

구현을 맡길 때도 경계 처리와 그 시험을 지시에 적는다.

> 실제 사고: 사람 이름 아래에 받은 배지를 나열한 목업에서 "배지를 아주 많이 받은 사람은 어떻게 보이냐"는 지적을 받았다. 실제 최대치는 23개였다.

### ⑤ 판단용 목업은 Claude Design 아티팩트로 빠르게 만든다 (2026-11-16 바뀜)

목업은 사용자가 방안을 비교하고 구현 계획을 세우는 판단 자료다. 고객에게 보이지 않으므로 **실제 앱과 똑같을 필요가 없다.** 속도와 비교가 쉬운 것을 우선한다.

- **도구:** claude.ai의 Design 아티팩트(화면 여러 장을 캔버스에 나란히 놓는 판)로 만든다. Artifact 도구에서 `action: "quickstart"`, `intent: "design"`으로 시작한다. 처음에는 비공개다.
- **단위:** 요청 한 건에 아티팩트 하나. 이름은 `YYYY-MM-DD <프로젝트> <주제>`. 만들면 프로젝트 `_작업/목업 목록.md`에 날짜, 주제, 링크, 상태(검토 전, 승인, 반려)를 한 줄 적는다.
- **수준:** 와이어프레임 수준이면 된다. 배치, 흐름, 바뀌는 것과 그대로인 것(③), 경계 상황(④)이 보이면 충분하다. 색과 글자는 프로젝트 기준 값을 대강 따르되 아이콘과 로고를 똑같이 맞추느라 시간을 쓰지 않는다.
- **빨리 만드는 법:** 지금 화면(②)을 캡처해 옆에 두고, 바뀌는 곳만 그린다. 안이 여럿이면 A안, B안을 한 캔버스에 나란히 둔다.
- **검토:** 사용자가 캔버스에 남긴 댓글을 읽고 반영한다(ArtifactComments). 승인된 안으로 구현 계획을 세운다.
- **로컬 HTML은 예비:** 아티팩트를 쓸 수 없을 때만 `_작업/`에 `.html`로 만들어 `open`으로 연다. 이미 있는 HTML 목업은 그 자리에 둔다.

### ⑥ 고객에게 보여 줄 목업만 실제 앱과 똑같이 (판단용 목업에는 적용하지 않음)

- 하단 내비게이션 바, 로고와 앱바, 메뉴 아이콘, 탭 이미지, 칩 색까지 **실제 화면과 같게** 그린다. 아이콘을 글자로 대신하지 않는다. 실제 에셋 경로를 쓰고, 기존 목업 HTML이 있으면 새로 그리지 않고 재사용한다.
- 긴 화면은 잘라 보이거나 여러 장으로 쪼개지 않는다. **세로로 긴 화면 한 장**에 위에서 아래까지 그린다.
- 스크린샷에 오류나 "불러올 수 없습니다"가 찍히면 쓰지 않고, 코드의 정상 상태를 그린다.
- 고객용 문서에는 내부 표현(목업 데이터, 실기기 확인 상태, 내부 구조, 과장된 말)을 넣지 않는다. [[05 쇠맛 줄이기]]를 따른다.
- 검수 때는 실제 기기 화면과 나란히 놓고 비교한다.

> 실제 사고: 고객 보고서의 목업에서 메뉴 아이콘이 빠지고, 홈 화면이 중간만 보이고, 오류 화면이 찍힌 스크린샷이 섞여 "고객이 오해하겠다"는 지적을 받았다.

### 그 밖에

- **가능하면 눌러 볼 수 있게.** 정지 화면으로는 느낌이 전달되지 않는다.
- **안이 여럿이면 권하지 않는 안도 제대로 만든다.** 약하게 만들어 놓고 비교하면 그건 비교가 아니다.

## 4. 화면 문제가 아닐 때: 원인 찾기

**증상이 아니라 원인을 고친다.** 원인을 못 찾았으면 아직 수정방안이 아니다.

### 🔴 사용자가 부르는 이름이 아니라 뜨는 물건을 본다

> **실제 사고.** 사용자가 *"뒤틀린 토스트"*라고 해서 토스트 코드를 팠다. 토스트는 좌우 여백이
> 고정이라 **구조적으로 정사각형이 못 되는** 물건이었다. 실제로 뜨던 것은 팝업이었고,
> 그걸 확정하는 데 위젯 하나 띄워 재보면 됐다.

사용자는 눈에 보이는 것을 편한 말로 부른다. **무엇이 뜨는지부터 코드로 확정**하고 시작한다.

### 그리고

- 재현한다. 안 되면 **로그와 데이터로 증거를 모은다.** 추측으로 고치지 않는다.
- 여러 겹(앱, 게이트웨이, 서버, DB)이면 **어느 경계에서 끊기는지**부터 잰다.
- 🔴 **남이 준 진단을 그대로 옮기지 않는다.** 숫자든 *"이럴 수 있다"*는 서술이든
  **직접 확인한 것만** 보고에 넣는다. 숫자는 다시 재면서 **서술은 안 재보고 넘기는** 실수가 잦다.
- 🔴 **"아직 안 됐다"는 서술을 믿지 않는다.** [[00 세션 공통 지침]] §2의 이슈 세션 판이다.
  남은 작업이나 미구현을 말하기 전에 **코드로 확인한다.**

### 보고에 담을 것

```
증상        무엇이 어떻게 보이는가
재현        어떤 조건에서 나는가 (안 되면 "재현 못 함"이라고 쓴다)
원인        어느 기능의 무엇 때문인가 (파일:줄은 괄호 참고나 인계 문서에)
영향 범위    이 원인이 건드리는 다른 화면과 기능
수정방안     둘 이상이면 장단점과 권장안
확인 필요    명세 변경이나 클라이언트 확인이 걸리는지
```

보고의 틀과 쓰는 말은 [[08 보고 지침]]을 따른다.

## 5. 더블체크: 자기 말을 자기가 검증하지 않는다

고친 뒤 **코드리뷰 에이전트를 따로 띄워** 자기 변경을 보게 한다.

- 리뷰에 **"내가 틀렸을 법한 곳"** 을 지목해서 준다. 막연히 "봐 줘" 하면 칭찬만 돌아온다.
- 리뷰가 준 지적도 **그대로 믿지 않는다.** 직접 재보고 사실인 것만 고친다.

> **실제로 잡았다.** 팝업 부품을 새로 만들고 시험 9건을 붙여 초록을 확인한 뒤 올렸는데,
> 리뷰가 **`AlertDialog`가 해 주던 본문 스크롤을 안 물려받았다**는 것을 짚었다. 재보니
> 글꼴 배율 3.0× 에서 **버튼이 화면 밖으로** 나갔고, 하필 그 팝업은 뒤로 닫기도 막혀 있어
> **앱을 죽여야 빠져나오는** 상태였다.

## 6. 🔴 "고쳤다"는 화면을 보고 말한다

이 항목 하나가 나머지를 지탱한다.

> **실제 사고.** 팝업이 정사각형으로 뭉친다는 지적에 **제목을 넣고** 고쳤다고 보고했다.
> *"제목이 없으면 최소폭으로 쪼그라든다"*는 설명은 사실이었지만 **원인이 아니었고**,
> 사용자가 보는 것은 하나도 안 달라졌다. 진짜 원인은 버튼 줄이 세로로 접히는 것이었다.
>
> **위젯을 띄워 치수를 재는 데 시험 하나와 1분이 들었다.** 처음에 했으면 반나절이 없었다.

- **그럴듯한 설명이 붙는 변경일수록 재본다.** 설명이 그럴듯하면 확인을 건너뛰게 되고,
  바로 거기서 *"고쳤다는데 그대로"*가 난다.
- **배치와 성능은 규칙 시험으로 안 잡힌다.** 부품 각각은 옳은데 **만나는 자리**에서만 틀어지기
  때문이다. 실제로 띄워서 **치수를 재거나 시간을 재야** 한다.
- **가드를 만들면 일부러 깨뜨려 본다.** 안 잡히는 가드는 없는 것보다 나쁘다.
  "통과했다"는 말이 붙기 때문이다.
- **캡처는 실패할 때만 남긴다.** 글자, 상태, API 응답으로 판정되는 통과 항목은 캡처하지 않고, 실패했거나 확인이 필요하거나 애매할 때만 남긴다. 결과 표의 캡처 칸은 통과면 비운다. 예외로 글자 넘침, 아이콘 위치, 레이아웃처럼 **눈으로만 판정할 수 있는 확인**은 근거로 캡처를 남긴다. 요청서가 단계마다 캡처를 요구하면(시연 기록 등) 요청서를 따른다.

### 프레임워크 부품을 손수 만든 것으로 갈아탈 때

그 부품이 **조용히 해 주던 일부터 세어 본다.** 눈에 띄는 기능만 옮기고 나머지를 잃기 쉽고,
그건 문서가 아니라 **극단값을 넣어 보면** 나온다.

## 7. 빌드와 배포에서 이슈 세션이 당한 것

**산출물을 열어서 확인한다.** 넣으려던 것이 아니라 나온 것을 보고, 그 확인을 스크립트로 박아 둔다. 자세한 함정(빌드 인자 손 조립, 플랫폼마다 다른 키 경로, 청소가 지우는 남의 산출물, iOS 권한 사유문)과 사례는 [[앱 세션 지침]] §5에 있다.

## 8. 연락과 보고

[[00 세션 공통 지침]] §10을 따른다. 이슈 세션에서 특히 걸리는 것 둘:

- **넘기는 문서는 푸시한 뒤에 알린다.** 워크트리는 격리돼 있어 밀기 전에는 상대에게 없다.
- **사용자에게는 번호, ID, 코드 용어를 쓰지 않는다.** 기능 이름으로 말한다.
  특히 **"남은 일" 목록에서 새기 쉽다.** 줄이 짧을수록 이름을 쓴다.

### 사용자가 열어 둔 디렉터리에서 브랜치를 옮기지 않는다

> **실제 사고.** 사용자가 안드로이드 스튜디오로 열어 두고 실기기 핫리로드에 쓰는 폴더에서
> 브랜치를 갈아탔다. **보고 있던 코드가 발밑에서 바뀌었다.**

고쳐야 하면 **워크트리를 판다.** 워크트리에는 gitignore 대상(빌드 키 정의 파일과 SDK 링크)이
따라오지 않으니 같이 넣어 준다.

## 인계 문서에 꼭 담을 것

공통 항목(가장 크게 당한 것과 재현 방법, 안 하기로 한 것과 이유, 확인하지 못한 것 등)은 [[00 세션 공통 지침]] §8을 따른다. 이슈 세션은 아래를 더한다.

```
[ ] 승인 대기 중인 수정방안과 무엇을 기다리는지
[ ] 목업 링크와 그 승인 상태
[ ] 🔴 고쳤다고 말했지만 화면으로 확인 못 한 것 (가장 위험하다)
[ ] 산출물 검사에서 통과시킨 범위 (무엇을 실제로 열어 봤나)
```
