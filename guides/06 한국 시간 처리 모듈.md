# 한국 시간 처리 모듈

> 서비스 기준은 한국(Asia/Seoul)인데, 운영 서버와 DB와 컨테이너는 UTC로 도는 경우가 많다.
> 개발 PC는 한국 시간이라서 날짜를 서버 지역 시간으로 잘라도 로컬 테스트는 **우연히 통과한다.**
> 그래서 이 오류는 운영에 올라간 뒤 한국 시간 0시부터 9시 사이에만 드러난다.
> 이 문서는 실제 프로젝트에서 찾은 오류와, 다른 프로젝트에서 구현할 모듈 구성을 정리한 것이다.

---

## 1. 원칙 다섯 가지

1. **저장과 전송은 절대 시각(UTC)으로 한다.** API 응답은 `2026-10-30T01:20:00.000Z` 같은 오프셋이 붙은 ISO 문자열로 준다. DB 시각 칸은 시간대를 담는 형식(`timestamptz`)을 쓴다.
2. **한국 날짜가 필요한 계산과 표시는 공통 모듈 하나에서만 한다.** "오늘", "어제", "올해", "N일 남음", 접수번호의 날짜, 하루 한 번 제한, 요일, 기간 필터가 여기에 해당한다.
3. **흐른 시간으로 세는 기한은 시간대와 무관하다.** 7일 자동 확정, 10분 선점, 48시간 제안, 90일 보관은 `지금 시각 - 시작 시각`으로 세면 되고, 날짜로 바꾸지 않는다. 날짜 기준 기한("판매 기한 남은 날")만 한국 날짜로 계산한다.
4. **날짜만 있는 값은 시각으로 바꾸지 않는다.** "2026-10-05" 같은 달력 날짜(DB `date` 칸, 예약 희망일)는 문자열 그대로 다룬다. 시각으로 읽어서 +9시간을 하면 하루가 밀린다.
5. **강제 장치를 둔다.** 모듈 밖에서 지역 시간대 API를 쓰면 lint가 막고, 테스트는 기본을 UTC로 돌린다.

## 2. 실제로 찾은 오류 (한 서비스에서 찾은 실제 사례)

| 어디서 | 무엇이 잘못됐나 | 증상 |
|---|---|---|
| 관리자 내려받기(CSV) | 시각을 `toISOString()` 그대로 씀 | 한국 시각보다 9시간 이르게 찍힘, 한국 0~9시 기록은 날짜가 전날 |
| 대시보드 "예약일 지남" | DB 날짜 칸 값(UTC 자정)을 기준 시각으로 그대로 씀 | 다음 날 한국 0~9시에 "0일 지남", 정렬도 틀림 |
| 관리자 상품 등록 "마감일" | 시각 문자열 앞 10자를 잘라 날짜로 씀 | 한국 0~9시에 공개한 상품의 마감일이 하루 이르게 보임 |
| 앱 주문일, 배송 시각, 반품 기한, 후기 날짜 | `.toLocal()`로 폰 시간대 변환 | 해외나 시간대가 다른 폰에서 다른 시각, 날짜 어긋남 |
| 앱 연도 필터 상한, 연도 목록 | `DateTime.now().year` | 1월 1일 한국 0~9시에 작년으로 나올 수 있음 |
| 앱 알림함 날짜 빼기 | 지역 시간 날짜끼리 뺄셈 | 서머타임 지역 폰에서 하루 어긋남 |

### 자주 틀리는 코드 모양

| 하면 안 되는 것 | 이유 | 대신 |
|---|---|---|
| `date.getDate()`, `getHours()`, `getDay()`, `getFullYear()`, `setHours(0,0,0,0)` | 서버나 기기의 지역 시간대를 따른다 | 공통 모듈의 한국 날짜 함수 |
| `date.toISOString().slice(0, 10)` | UTC 날짜다. 한국 0~9시는 전날 | `koreaDate(date)` |
| `kstDayStart(d).toISOString().slice(0, 10)`처럼 한국 자정의 UTC 시각을 자름 | 한국 자정은 UTC로 전날 15시라서, 이렇게 자르면 시각과 상관없이 **언제나** 전날이 된다 | 오프셋을 더한 뒤 자르거나 `koreaDate(date)` |
| `new Date('2026-10-30')` | UTC 자정으로 읽힌다 | 한국 0시는 `new Date('2026-10-30T00:00:00+09:00')` |
| `new Date(2026, 9, 30)` | 지역 시간대 자정 | 위와 같음 |
| `toLocaleDateString()`, `toLocaleString()`(날짜) | 기기 시간대 | `timeZone: 'Asia/Seoul'`을 지정한 공통 포매터 |
| Flutter `.toLocal()`, `DateTime.now().day` | 폰 시간대 | `koreaClock(at)`, `koreaToday()` |
| 크론에 시간대 미지정 | "매일 0:30"이 UTC 0:30(한국 9:30)에 돈다 | 크론 등록 함수 하나에서 한국 시간대 지정 |
| SQL `now()::date`, `date_trunc('day', ...)`, `CURRENT_DATE` | DB 세션 시간대를 따른다 | `AT TIME ZONE 'Asia/Seoul'`을 명시하거나 앱에서 한국 날짜 범위를 계산해 넘긴다 |

### 한국 자정을 UTC로 자른 사례

한국 자정의 UTC 시각을 주는 함수의 결과를 그대로 잘라 날짜를 만들었다.

```
kstDayStart(d).toISOString().slice(0,10)   // 하루 전 날짜가 나온다
```

한국 자정은 UTC로 전날 15시다. 그래서 위 표의 다른 줄처럼 한국 0~9시에만 틀리는 것이 아니라 **언제나** 전날이 된다. 이 날짜로 공휴일을 찾았더니 매칭이 통째로 실패했고, 그 결과 기록을 4일 일찍 파기할 뻔했다. 날짜 경계는 사용자의 달력 날짜와 같아야 한다. **오프셋을 더한 뒤 자른다.** 고친 뒤 테스트가 빨개졌는데, 틀린 쪽은 테스트 기대값이었다([[03 코딩 규칙]] §5).

### 앱 DB 연결의 세션 시간대 (실제 사례: Prisma 드라이버 어댑터)

- **하면 안 되는 것:** 앱 DB 연결의 세션 시간대를 DB 기본값에 맡긴다. 실제 사례는 Prisma 드라이버 어댑터 `@prisma/adapter-pg`였다.
- **이유:** 어댑터가 시각을 오프셋 없는 UTC 문자열로 보내고, 읽은 오프셋을 `+00:00`으로 바꿔 끼운다. DB 세션이 `Asia/Seoul`이면 저장은 9시간 이르게, DB `now()`는 9시간 늦게 읽힌다. 앱이 쓰고 읽으면 상쇄돼 화면에는 안 보이고 DB 직접 조회에서만 보인다. e2e만 세션을 UTC로 고정하면 오히려 가려진다.
- **대신:** 앱 연결 문자열에 접속 옵션 `options=-c TimeZone=UTC`를 코드로 붙인다(기존 options 뒤에). 회귀 테스트는 세션을 일부러 `Asia/Seoul`로 적고 epoch로 비교한다. 연결 풀러(PgBouncer)를 두면 DB 쪽 `timezone='UTC'`도 맞춘다.

## 3. 모듈 구성 (아래 함수 목록을 보고 프로젝트에 구현한다)

가져다 쓸 원본 코드는 따로 없다. 아래 함수 목록과 구현 요점을 보고 프로젝트마다 구현한다.

### 3-1. 서버 (TypeScript, NestJS 기준) `src/common/utils/korea-time.ts`

| 함수 | 하는 일 |
|---|---|
| `SERVICE_TIME_ZONE` | `'Asia/Seoul'` 상수 |
| `KOREA_DATE` | `YYYY-MM-DD` 형식 검사 정규식(쿼리 검증용) |
| `koreaDate(date)` | 절대 시각을 한국 날짜 `"2026-09-28"`로 |
| `koreaDayRange(ymd)` | 한국 날짜의 [그날 0시, 다음 날 0시) 시각. 기간 필터에 쓴다 |
| `addKoreaDays(ymd, n)` | 한국 날짜에 n일 더하기 |
| `koreaDateTime(date)` | `"2026-10-02 00:30:00"`. 사람이 읽는 파일(CSV)용 |
| `koreaYmdCompact(date)` | `"260928"`. 접수번호 앞머리 |
| `yearInKorea(date)` | 한국 연도 |
| `koreaDayIndex(date)` | 한국 날짜를 정수 날수로. 날짜끼리 뺄 때 양쪽에 같이 쓴다 |
| `ymdWeekday(ymd)` | 한국 날짜의 요일(0=일) |
| `dateColumnToYmd(col)` | DB 날짜 칸(UTC 자정으로 옴)을 `"YYYY-MM-DD"`로. **한국 시각으로 바꾸지 않는다** |
| `ymdToDateColumn(ymd)` | 반대 방향. 날짜 칸에 저장하거나 비교할 값 |

구현 요점:
- 포매터는 `new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul', year: 'numeric', month: '2-digit', day: '2-digit' })`를 모듈 안에서 한 번만 만든다. `en-CA`가 `YYYY-MM-DD` 형식을 준다.
- 한국 0시는 `new Date(\`${ymd}T00:00:00+09:00\`)`로 만든다. 한국은 서머타임이 없어 하루는 늘 24시간이다.
- 날짜 산술(날수, 요일)은 "그 날짜의 UTC 자정"을 바탕으로 하고, 이 값을 시각으로 쓰지 않는다.

예약 작업:
- 데코레이터 하나로 시간대를 고정한다: `KoreaCron(job) => Cron(job.cron, { name: job.name, timeZone: SERVICE_TIME_ZONE })`.
- 작업 이름과 주기는 목록 파일 한 곳(`scheduled-jobs.ts`)에 두고, 테스트로 "목록의 모든 작업이 한국 시간대로 등록됐는지" 확인한다.

### 3-2. 웹 (TypeScript, Next/React) `src/lib/korea-time.ts`

| 함수 | 예시 |
|---|---|
| `relativeDateTime(v)` | `"오늘 09:21"`, `"어제 16:02"`, `"8.18 14:20"`, 다른 해면 `"2025.8.18 14:20"` |
| `relativeDate(v)` | `"오늘"`, `"어제"`, `"내일"`, `"8.18"` |
| `stampDateTime(v)` | `"2026. 08. 19 09:42"` |
| `clockTime(v)` | `"09:42"` |
| `koreaDateString(v)` | `"2026-09-12"`(기간 필터, 날짜 칸) |
| `koreaMonthDay(v)` | `"6.17"` |
| `koreaDaysBetween(a, b)` | 한국 날짜 차이(일) |
| `addKoreaDays(ymd, n)` | 한국 날짜 ± n일 |
| `koreaYear()` | 한국 연도 |

구현 요점:
- `Intl.DateTimeFormat('en-US', { timeZone: 'Asia/Seoul', ..., hourCycle: 'h23' }).formatToParts()`로 한국 연월일시 부품을 꺼내고, 화면 형식은 부품으로 조립한다.
- 입력이 `"2026-10-02"`처럼 날짜만 있는 문자열이면 이미 한국 날짜로 보고 부품으로 나눈다(시각으로 읽지 않는다).
- 화면에서는 `format.ts`가 다시 내보내게 해서 import 경로를 하나로 둔다.

### 3-3. 앱 (Flutter, Dart) `lib/shared/format/korea_time.dart`

| 함수 | 하는 일 |
|---|---|
| `parseServerTime(raw)` | 서버 ISO 문자열을 절대 시각(UTC)으로. 모델은 이 값을 들고 `.toLocal()` 하지 않는다 |
| `koreaClock(at)` | 절대 시각에 +9시간. 필드(year, month, hour)가 한국 값인 표시 전용 값 |
| `koreaDaysBetween(a, b)` | 한국 날짜 차이(일) |
| `koreaToday()` | 한국 오늘(달력 계산용). 절대 시각 함수에 다시 넣지 않는다 |
| `koreaYear()` | 한국 연도 |
| `koreaDotDate`, `koreaDashDate`, `koreaSpacedDate`, `koreaSlashDate`, `koreaMonthDay`, `koreaHm` 등 | 화면 형식별 표기 |

구현 요점:
- 한국은 서머타임이 없으므로 `Duration(hours: 9)` 고정 변환이 맞다. 시간대 패키지를 새로 들일 필요가 없다.
- `koreaClock`으로 만든 값은 표시와 날짜 계산에만 쓰고, 다시 비교하거나 저장하지 않는다(+9시간이 두 번 붙는다).

## 4. 강제 장치 (새 프로젝트에 같이 넣는다)

| 대상 | 장치 | 막는 것 |
|---|---|---|
| 서버 | lint 규칙(oxlint면 자체 플러그인, ESLint면 `no-restricted-syntax`) | 모듈 밖의 지역 시간 Date 메서드, `toISOString()` 뒤 자르기, `Intl.DateTimeFormat` 직접 생성, 오프셋 없는 날짜 문자열, `@Cron` 직접 사용 |
| 웹 | ESLint `no-restricted-syntax` | 도우미 밖의 `Intl.DateTimeFormat`, `getHours` 같은 지역 부품, 시각 문자열 자르기, 기기 시간대 표기 |
| 앱 | 가드 테스트(`test/shared/format/korea_time_guard_test.dart`) | `lib`에서 `.toLocal()`, 직접 +9시간, `DateTime.now().year`, `DateFormat`, 문자열 안의 시각 직접 조립 |
| 테스트 | 기본 시간대 UTC 고정(`vitest.config`에 `process.env.TZ ??= 'UTC'`) | 한국 PC에서 우연히 통과하는 날짜 오류 |

주의할 한계:
- lint는 변수 이름으로 날짜인지 판단하는 경우가 있어, 날짜 변수 이름이 엉뚱하면 놓친다. 금액 `toLocaleString('ko-KR')`은 막지 않도록 규칙을 좁힌다.
- lint 플러그인이 실험 기능이면 버전이 오를 때 조용히 꺼질 수 있다. "잡혀야 할 예시"와 "통과해야 할 예시"로 규칙 자체를 확인하는 테스트를 같이 둔다.
- Flutter는 `analysis_options.yaml`로 특정 API를 금지하기 어렵다. 가드 테스트로 대신한다.

## 5. 테스트에 꼭 넣을 경계 사례

- 한국 0시~9시(UTC로 전날 15:00~23:59)에 만든 기록의 날짜, 접수번호, "오늘/어제" 판단
- 1월 1일 한국 0~9시의 "올해"
- 달 넘김, 해 넘김에서 `addKoreaDays`, `koreaDaysBetween`
- DB 날짜 칸 왕복(`ymdToDateColumn`으로 바꿔 저장하고, 조회해서 `dateColumnToYmd`로 되돌림)이 같은 날짜인지
- 크론 목록의 모든 작업이 한국 시간대로 등록됐는지
- 웹과 앱에 같은 숫자 사례를 넣어 표시가 서로 같은지

테스트는 기본 UTC로 돌리고, 필요하면 `TZ=Asia/Seoul`로 한 번 더 돌려 비교한다.

## 7. 외부 연동 때 조심할 것

- 택배사, 결제사 응답에 **오프셋 없는 시각**(`2026-10-30 14:20:00`)이 오면 한국 시각으로 읽는다(`+09:00`을 붙여 파싱). 그대로 읽으면 UTC 서버에서 9시간 어긋나고, 그 시각에 걸린 자동 구매 확정과 반품 마감도 같이 밀린다.
- 외부로 날짜를 보낼 때(예약 희망일 등)는 상대 문서가 요구하는 형식과 시간대를 확인하고, 한국 날짜 문자열로 보낸다.
- 서버 로그 시각은 프로세스 시간대를 따른다. 동작에는 영향이 없지만, 운영 로그를 볼 때 UTC인지 한국 시각인지 먼저 확인한다.
