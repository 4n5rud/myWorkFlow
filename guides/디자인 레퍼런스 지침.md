# 디자인 레퍼런스 지침

> 이 문서는 디자인 레퍼런스 사이트에서 실제 앱 화면을 찾아 모으고, 공통 모듈을 뽑아 정의하고, 그 모듈로 우리 화면을 디자인하는 작업의 순서와 기준을 정한다.
> 세션이나 서브에이전트에게 디자인 일을 맡길 때는 이 문서를 먼저 읽히고, 맨 아래 [[#7. 서브에이전트 지시 틀]]을 그대로 붙여 넣는다.

---

## 0. 한 줄 요약

**감으로 그리지 않는다.** 같은 화면을 실제 앱 여러 개에서 찾아 나란히 놓고, 반복되는 구조를 공통 모듈로 정의한 뒤, 우리 데이터와 우리 규칙에 맞춰 그린다.

---

## 1. 레퍼런스 사이트

두 사이트 모두 국내 서비스의 실제 화면을 모아 둔 곳이다. 성격이 달라서 함께 쓴다.

### 1-1. wwit (What Was IT): https://wwit.design/

국내 모바일 앱 화면을 **화면 종류**와 **부품**으로 나눠 모아 두었다. "이런 화면은 보통 어떻게 생겼나"를 볼 때 먼저 연다.

| 묶음 | 주소 형식 | 항목 |
|---|---|---|
| 패턴(화면 종류) | `/pattern/{이름}` | splash, signin, signup, onboarding, home, search, notification, select, loading, success, cart, order, list, review, password, t&c, mypage, setting |
| 컴포넌트(부품) | `/component/{이름}` | input, tab, bottomsheet, popup, chart |
| 분야 | `/tag/{이름}` | life, finance, commerce, realestate, delivery, entertainment, mobility |
| 앱 하나 | `/{연}/{월}/{일}/{앱 이름}/` | 그 앱의 화면 묶음 |

- 패턴 페이지는 여러 앱의 같은 종류 화면을 격자로 보여 준다. 화면마다 설명 글은 없다.
- 로그인 없이 볼 수 있었다(확인한 날짜는 8장).

### 1-2. 디자이너스 (Designus): https://ko.designus.design/

국내 서비스를 **서비스 단위**로 모으고, 앱과 웹과 스토어를 나눠 둔다. 한 서비스의 흐름 전체를 이어서 볼 때와, 다른 디자이너들의 투표와 의견을 볼 때 쓴다.

| 묶음 | 주소 형식 | 내용 |
|---|---|---|
| 앱 레퍼런스 | 메뉴 "앱 레퍼런스" | 모바일 앱 화면 |
| 웹 레퍼런스 | 메뉴 "웹 레퍼런스" | 웹사이트 화면 |
| 스토어 레퍼런스 | 메뉴 "스토어 레퍼런스" | 쇼핑, 매장 화면 |
| 서비스 하나 | `/reference/service/{번호}` | 예: 올리브영은 `/reference/service/95` |
| 토픽 | `/topic/{번호}` | 디자인 선택지를 두고 투표와 댓글을 모은 글 |

- 목록에 필터(컴포넌트, 패턴) 탭이 있지만 자바스크립트로만 동작한다(주소창에 물음표로 붙는 조건이 없다). 헤드리스 크롬으로 주소만 바꿔서는 못 켠다. 직접 눌러야 한다(8장).
- 메인 페이지와 `/reference/service/{번호}` 서비스 상세 페이지는 **로그인 없이 볼 수 있었다**(예: 올리브영 95번, 당근마켓 26번). 다만 확인한 두 서비스(올리브영, 당근마켓) 모두 온보딩, 회원가입, 홈 화면만 올라와 있고 **마이페이지 화면은 카탈로그에 없었다**. 서비스마다 올라온 화면 종류가 다르므로, 마이페이지가 필요하면 wwit.design을 먼저 쓴다(확인한 날짜는 8장).
- 로그인과 회원가입 메뉴가 있어서 다른 화면(개인화된 상세 등)은 로그인해야 보일 수 있다. **로그인이 필요하면 멈추고 사용자에게 묻는다.** 계정을 만들거나 대신 로그인하지 않는다.

### 1-3. 사이트를 읽는 방법

- 두 사이트 모두 화면 그림이 핵심이라, 글만 가져오는 도구(WebFetch 등)로는 그림을 볼 수 없다.
- 그림을 봐야 할 때는 브라우저로 열거나, 헤드리스 크롬으로 페이지를 캡처해서 본다. 아래 크롬 경로는 macOS 기준 예다.
  ```
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
    --hide-scrollbars --window-size=1440,3000 --virtual-time-budget=8000 \
    --screenshot=<저장 경로>.png "<주소>"
  ```
- 그림이 늦게 뜨면 `--virtual-time-budget`을 늘린다. 그래도 비어 있으면 그 사실을 보고하고, 비어 있는 캡처를 근거로 쓰지 않는다.

## 2. 작업 순서

### 2-1. 질문을 먼저 정한다

무엇을 찾을지 한 문장으로 적고 시작한다. 질문이 흐리면 모으는 화면도 흐려진다.

- 좋은 질문: "구매 완료 화면처럼 받은 결과를 보여 주고 다음 할 일(주소 입력)을 시키는 화면은 어떻게 배치하나"
- 흐린 질문: "예쁜 상세 화면 찾기"

질문에는 다음을 함께 적는다.
- 우리 화면 이름과 지금 화면 캡처
- 그 화면에 들어가는 **실제 데이터 목록**(서버가 주는 값만)
- 지금 화면이 무엇이 불편한지(사용자가 한 말을 그대로)

### 2-2. 모은다

- **최소 6개 앱, 두 사이트 모두에서** 모은다. 한 앱이나 한 사이트에서만 모으면 그 회사의 스타일을 공통 패턴으로 착각한다.
- 같은 패턴 페이지(예: `/pattern/order`)에서 먼저 넓게 보고, 마음에 드는 앱은 앱 페이지로 들어가 앞뒤 흐름을 함께 본다.
- 분야는 섞는다. 금융 앱의 단단한 구조와 커머스 앱의 가벼운 구조를 같이 봐야 공통점이 드러난다.
- 하나를 모을 때마다 아래 네 가지를 기록한다.

| 기록 | 예 |
|---|---|
| 출처 주소 | `https://wwit.design/pattern/order` |
| 앱 이름과 화면 이름 | 토스, 송금 완료 |
| 캡처 파일 | `_작업/레퍼런스/<주제>/toss_송금완료.png` |
| 왜 골랐나 (한 줄) | 결과를 큰 숫자 하나로 보여 주고 단추를 아래에 붙였다 |

- 캡처는 **내부 참고용**이다. 우리 문서와 목업 안에서만 쓰고, 발주사 문서나 외부 공유물에 그대로 넣지 않는다. 출처는 항상 남긴다.

### 2-3. 뜯어 본다

모은 화면을 한 줄로 나란히 놓고, 같은 자리에 무엇이 오는지 표로 뜯는다.

| 자리 | 앱 A | 앱 B | 앱 C | 공통점 |
|---|---|---|---|---|
| 맨 위 | 큰 사진 | 큰 사진 | 아이콘과 제목 | 무엇인지 먼저 보여 줌 |
| 가운데 | 정보 표 | 정보 표 | 진행 단계 | 상태를 줄로 나눔 |
| 맨 아래 | 붙은 단추 | 붙은 단추 | 붙은 단추 | 할 일은 하나, 아래에 고정 |

- 볼 것: 배치 순서, 크기 비율, 여백, 글자 위계(제목, 본문, 보조), 색을 쓰는 곳, 상태(빈 값, 로딩, 오류, 완료), 단추 개수와 자리
- **세 개 이상의 앱에서 반복되는 것**만 공통점으로 적는다. 한 곳에만 있는 것은 "특이점" 칸에 따로 적는다.

### 2-4. 공통 모듈로 정의한다

반복되는 구조를 우리 앱의 부품으로 정의한다. 정의서는 [[#6. 공통 모듈 정의서 틀]]을 따른다.

- 이름은 하는 일로 짓는다(예: "상품 줄", "상품 썸네일", "배송 단계"). 생김새로 짓지 않는다.
- 이미 있는 모듈과 겹치면 새로 만들지 않고 넓힌다. 먼저 앱 저장소의 공통 위젯 폴더(예: Flutter `lib/core/widgets`)와 기존 정의서를 확인한다.
- 크기, 여백, 둥글기, 글자 크기는 숫자로 적는다. "적당히", "넉넉히"처럼 쓰지 않는다.
- 경계 상황(개수, 빈 값, 긴 값, 큰 글자, 가장 좁은 화면 폭)에서 어떻게 보이는지 정의한다. 자세한 규칙: [[02 이슈 세션 운영]] §3 ④.

### 2-5. 우리 화면을 디자인한다

- 목업은 와이어프레임이 아니라 출시 화면 수준으로 만든다. 실제 기기 캡처 위에 바꾸는 부분만 새로 그린다.
- 레퍼런스의 모양을 그대로 베끼지 않는다. 뽑은 공통 구조에 **우리 데이터**와 **우리 규칙**(아래 3장)을 입힌다.
- 안은 2~4개 만든다. 맨 왼쪽에 "지금" 화면을 두고, 비교하는 부분만 바꾸고 배치는 같게 둔다. 추천안 하나에 이유를 한 줄 붙인다.
- 각 안 아래에 **근거 레퍼런스**를 작게 단다(예: "토스 송금 완료, 배민 주문 상세와 같은 구조").

### 2-6. 보고하고 정한다

- 목업을 브라우저로 열고, 사용자에게 안별 차이를 표 하나로 보고한다.
- 사용자가 고르기 전에는 구현하지 않는다. 고른 뒤에는 모듈 정의서를 확정하고 구현을 맡긴다.

## 3. 우리 규칙 (레퍼런스보다 우선)

레퍼런스가 아무리 좋아도 아래 규칙과 부딪히면 규칙을 따른다.

| 규칙 | 내용 |
|---|---|
| 데이터에 있는 것만 그린다 | 서버가 주지 않는 값(아이콘, 색, 숫자)을 지어내지 않는다. 없으면 자리 표시로 두고 "서버 값 필요"라고 적는다 |
| 프로젝트가 정한 금지 색을 지킨다 | 프로젝트마다 쓰지 않기로 한 색(예: 테마의 옅은 강조색 바탕)과 강조, 선택 색 규칙이 있으면 그것을 따른다. 정한 것이 없으면 디자인 시안의 색만 쓴다 |
| 배치로 설명한다 | 늘 떠 있는 설명 문장을 붙이지 않는다. 순서, 묶음, 크기로 읽히게 한다. 입력 오류 안내, 안내 상자, 불러오는 중 안내 한 줄은 예외다 |
| 문장부호 | 화면 문구는 [[05 쇠맛 줄이기]]의 문장부호 규칙을 따른다. 항목을 잇지 말고 줄이나 칸으로 나눈다 |
| 장식 그림은 아껴 쓴다 | 3D 아이콘 같은 장식 그림은 프로젝트가 정한 자리에만 쓴다. 사진이 있는 자리에는 넣지 않는다. 없는 그림을 다른 그림으로 대신하지 않는다 |
| 반복 장식 애니메이션 금지 | 상태 점, 배지, 핀은 고정한다. 반복 움직임은 로딩 표시에만 쓴다 |
| 경계 상황을 기본으로 | 개수가 바뀌는 것은 경계 상황까지 설계한다. 자세한 규칙: [[02 이슈 세션 운영]] §3 ④ |
| 시각은 KST | 날짜와 시간 문구는 한국 시간 기준이다 |

## 4. 결과물을 두는 곳

| 결과물 | 위치 |
|---|---|
| 레퍼런스 캡처와 출처 기록 | 프로젝트 `_작업/레퍼런스/{주제}/`. 커밋하지 않는다(`.gitignore`에 넣는다) |
| 뜯어 본 표 | 목업 HTML 안의 "레퍼런스" 구역 |
| 공통 모듈 정의서 | 프로젝트 문서 저장소(예: `docs/디자인/공통모듈/{모듈 이름}.md`) |
| 목업 | 프로젝트 `_작업/{주제}.html`, 헤드리스 크롬으로 PNG도 함께 |
| 확정된 모듈 정의 | 앱 저장소 문서(통일 정의서)에도 같은 내용으로 반영 |

산출물 위치의 공통 규칙은 [[00 세션 공통 지침]] §15를 따른다.

## 5. 점검표

보고하기 전에 하나씩 확인한다.

- [ ] 질문을 한 문장으로 적었다
- [ ] 6개 이상의 앱을 두 사이트 모두에서 모았고, 출처를 다 남겼다
- [ ] 세 곳 이상에서 반복되는 것만 공통점으로 적었다
- [ ] 이미 있는 모듈과 겹치는지 확인했다
- [ ] 숫자(크기, 여백, 둥글기, 글자 크기)로 정의했다
- [ ] 경계 상황을 정의했다([[02 이슈 세션 운영]] §3 ④)
- [ ] 화면에 서버가 주지 않는 값이 없다
- [ ] 프로젝트가 금지한 색, 금지 문장부호(05), 늘 떠 있는 설명 문장, 반복 애니메이션이 없다
- [ ] 장식 그림은 프로젝트가 정한 자리에만 있다
- [ ] "지금" 화면과 같은 배치로 비교했고, 추천 이유가 한 줄 있다
- [ ] 레퍼런스 캡처가 외부 공유물에 들어가지 않았다
