> 여러 AI 세션이 병렬로 도는 구조에서, **실제로 사고가 났던 것만** 모았다.
> 어느 모델로 굴리든 여기는 공통이다.

## 1. 🔴 시작하기 전에 내 체크아웃이 최신인지 본다

**가장 먼저 할 일이고, 안 하면 나머지가 전부 무의미해진다.**

```bash
git fetch --all --prune
git log -1 --format="%h %ad %s" --date=short          # 내 HEAD
git rev-list --count HEAD..origin/main                # 몇 커밋 뒤처졌나
```

- `git log`가 그럴듯하게 나온다고 최신이 아니다. **반드시 origin과 비교한다.**
- 브랜치가 엉뚱한 걸 추적하고 있으면 `git status`의 ahead/behind 신호가 통째로 거짓이 된다. 추적 대상도 확인한다.
- 세션 시작 훅이 뒤처짐을 알려 주지만, 추적 브랜치가 맞는지는 직접 본다.
- 워크트리를 쓰는 저장소면 `git worktree list`로 **다른 세션이 어느 커밋에 있는지**도 같이 본다.

#### 사례

> **실제 사고**: 기획 세션이 이 확인을 건너뛰고 작업했다. 워크트리가 **수백 커밋(몇 주) 뒤처져** 있었는데
> `git log -20`만 보고 "이게 최신"이라고 가정했다. 그 상태로 산출물 정합성을 전수 점검해
> **불일치 여러 건 보고서**를 냈는데, 최신 기준으로 다시 보니 그중 다수가 **이미 몇 주 전에 처리된 것**이었다.
> 그대로 다른 세션에 전달됐으면 끝난 일을 다시 시킬 뻔했다.

## 2. 🔴 문서와 주석을 근거로 삼지 않는다

> **근거는 계약(OpenAPI), DTO, 라이브 라우트, 실제 데이터다. 주석과 문서는 근거가 아니라 단서다.**
> 그리고 **코드를 바꿨으면 그 위 주석도 같은 커밋에서 바꾼다.**

#### 사례

**세 세션이 같은 날 전부 이것에 당했다.**

| 세션 | 무엇을 믿었나 | 실제 |
|---|---|---|
| 앱 | `TODO(api)`: *"서버에 없다"* | **다섯 개가 이미 서버에 있었다.** 그중 하나 때문에 **참여를 마친 사용자가 보상을 못 받고 있었다**(자세한 대응: [[앱 세션 지침]] §1) |
| 어드민 | 함수 위 주석: *"쿠폰을 무시한다"* | 구현은 진작 반영돼 있었고 **주석만 그 시절에 멈춰** 있었다. 확인하는 데 시간을 썼다 |
| 백엔드 | 다른 세션의 요청서: *"에러 코드가 없다"* | **요청서가 커밋되기 전에 이미 발번**돼 있었다 |

## 3. 담당 범위를 넘지 않는다

- 담당은 **프로젝트가 아니라 세션에 붙는다.** 이 문서를 읽었다고 자기 범위로 삼지 않는다.
  **자기 범위는 그 세션의 사용자 지시에서 확인한다.** 이건 어떤 모델에서도 바뀌지 않는다.
- 서브모듈 포인터를 조심한다. `git add -A`가 **남의 세션 체크아웃을 내 커밋에 끌어들인다.**
  부모 저장소에서는 **경로를 명시해 스테이징**한다.
  - 사례: 실제로 그렇게 앱 서브모듈 포인터가 백엔드 세션 커밋에 두 번 딸려 들어갔다.
- **상위 저장소(서브모듈을 묶는 저장소)는 기본 브랜치에서만 작업한다. 기능 브랜치는 서브모듈에서 나눈다(2026-11-09 사용자 결정).** 상위 저장소에는 서브모듈 연결과 공통 문서만 있어서, 여기서 브랜치를 나누면 어느 상위 브랜치가 어느 서브모듈 커밋을 가리키는지 갈라지고 합칠 때 연결이 충돌한다.
  - 기본 브랜치는 main이고, main이 없으면 master다. 이 컴퓨터의 원격 기본 브랜치 기록(`origin/HEAD`)은 낡아 있을 수 있으니 서버 설정을 기준으로 본다(`git remote set-head origin -a`로 갱신).
  - 이미 상위에서 진행 중인 브랜치는 끝내고 합친다. 새 작업부터 이 규칙을 따른다. 세션 시작 훅이 상위 저장소가 기본 브랜치가 아니면 알린다(막지는 않음).
  - 상위 저장소 기본 브랜치 푸시는 보호 브랜치 규칙(§8)대로 매번 확인을 받는다. 올리기 전 서브모듈 연결이 각 서브모듈 main에 있는 커밋인지 전역 푸시 훅이 검사한다(아니면 막고, 뒤처지면 경고).

## 4. 🔴 자격증명은 저장소에 값으로 남기지 않는다

키, 토큰, 비밀번호는 문서에 적어야 해도 라벨만 남기고 값은 가린다. 커밋 전에 비밀값이 섞이지 않았는지 확인하고, 이미 원격에 올라갔으면 먼저 재발급(무효화)을 요청한 뒤 파일과 이력을 정리한다.

자세한 규칙: [[15 비밀값 커밋 금지]] §3, §6

## 5. 자리를 만들었으면 쓰는 쪽을 같은 커밋에 붙인다

못 붙이면 **문서에 🔴로 적고 다음 세션이 보게 한다.** 조용히 두지 않는다.

#### 사례

> **실제 사고 2건**: 표, 인덱스, 모듈까지 다 만들고 **INSERT 한 줄이 없었다.**
> 다른 하나는 쓰기만 붙고 **읽는 쪽이 하나도 없었다.**
> 둘 다 *"스위치가 꺼져 있어서 지금은 차이가 없다"*는 이유로 넘어간 것이었다.
> **차이가 없는 게 아니라 아직 안 드러난 것**이고, 켜는 순간 *"쌓이는 줄 알았다"*로 터진다.

## 6. 되돌릴 수 없는 것은 승인받고 한다

- 데이터 파기, 계정, 키체인, 인증서, 푸시 알림 발송, 배포는 **뭐가 남는지 먼저 말하고 승인**받는다.
- 남에게 문서를 보내는 일은 Claude가 하지 않는다. 보내는 사람은 언제나 사용자다([[13 보낼 문서와 발송 상태]]).
- 파괴적 스위치는 **기본 꺼짐**으로 두고, 켜는 조건을 문서에 적는다.
- 시키더라도 마찬가지다.

## 7. 검증 결과를 과신하지 않는다

- **"통과"가 무엇을 실제로 봤는지** 한 번은 확인한다. SKIP은 통과가 아니다.
- 테스트가 빨갛다고 코드부터 고치지 않는다. 자세한 규칙: [[03 코딩 규칙]] §5

#### 사례

> 검증 스크립트 6종이 "전부 통과"로 보고되고 있었는데, 실제로 **도는 건 1개**였다.
> 나머지 5개는 입력 파일이 저장소에 없어 **조용히 SKIP**하고 있었다.

## 8. 커밋과 소통 규약

- 커밋에 **AI 서명, co-author, 생성도구 표기 금지.** 커밋 메시지 형식은 [[09 커밋 메시지 규칙]]을 따른다.
- 사용자에게 말할 때 **내부 문서 ID를 쓰지 않는다**(`ISSUE-118`, `REQ-00` 같은 것). 그건 문서와 커밋용이다. 보고의 틀은 [[08 보고 지침]]을 따른다.

### 브랜치 규칙 (2026-11-04, 이 절이 원본)

- **보호 브랜치**는 dev, develop, main, master, prod, production, staging, stg다.
- **작업 브랜치**(기능, 수정, 핫픽스)는 보호 브랜치에서 갈라 만들고(`feature/`, `fix/`, `hotfix/` 등), 묻지 않고 커밋하고 푸시한다. PR을 만드는 것도 묻지 않는다.
- 보호 브랜치에서 직접 커밋하지 않는다.
- 보호 브랜치로 푸시하거나 머지하는 것은 검사(코드 리뷰와 관련 테스트) 결과와 "어느 브랜치를 어디로 합칠지"를 사용자에게 보여 주고 승인받은 뒤에만 한다.
- 프로젝트 CLAUDE.md나 프로젝트 메모리에 보호 브랜치에 대해 더 엄격한 규칙(예: 머지 자체 금지)이 있으면 그쪽을 따른다. 프로젝트별로 확인 없이 허용하는 예외는 [[10 자동 장치]] §2에 있다.
- **장치:** Claude 세션의 명령은 훅(guard)이 확인을 받게 한다. 보호 브랜치로 향하는 푸시와 보호 브랜치 위의 머지(`git merge`, `gh pr merge`, `glab mr merge`)마다 사용자에게 묻는다. 사용자가 터미널에서 직접 하는 푸시는 막지 않는다.
- **이유:** 작업 브랜치는 되돌리기 쉽고 서로 영향이 적다. 보호 브랜치에 들어가는 순간부터 다른 사람과 배포에 영향이 가므로, 그때만 사람이 검사 결과를 보고 정한다.
- 서브모듈을 쓰는 저장소의 작업 순서는 [[01 커맨드 센터 운영]] §7에 있다.

### 인계 문서 (이 절이 원본)

세션을 마칠 때, 일꾼을 교대할 때, 대화가 압축됐을 때 **인계 문서**를 남긴다. 다음 세션이 *그 파일만 읽고 이어서 시작할 수 있게* 쓴다.

- **위치:** 프로젝트 문서 저장소의 `_작업/인계/YYYY-MM-DD_주제.md`(§15).
- **역할 나누기:** 남은 일은 `_할일/할 일.md`에, 맥락(함정, 막힌 것, 안 하기로 한 것과 이유)은 인계 문서에 둔다. 인계 문서에는 남은 일 목록을 따로 두지 않고 `할 일.md`를 가리킨다([[14 할 일과 끝낸 일]]).
- **공통 항목:**
  1. 오늘 한 일과 바꾼 파일
  2. 🔴 가장 크게 당한 것과 그 재현 방법
  3. 막혀 있는 것, 남에게 물어 놓은 것
  4. 함정
  5. 안 하기로 한 것과 이유
  6. 확인하지 못한 것
  7. 다음에 할 일(남은 일은 `할 일.md`를 가리킨다)
- 역할별 문서의 "인계 문서에 꼭 담을 것"에는 이 공통 항목 말고 그 역할에만 있는 항목을 적는다.

## 9. 번호와 ID가 세션끼리 겹친다

여러 세션이 병렬로 돌면 **같은 번호를 동시에 가져간다.** 실제로 **하루에 다섯 번** 났다.

```bash
git pull
ls <문서디렉터리>/ | grep -oE 'PREFIX-[0-9]+' | sort -u | tail -3   # 미커밋 파일까지 잡힌다
```

- **인덱스 파일만 보면 부족하다**. 커밋 안 된 남의 작업은 거기 없다. **디스크를 본다.**
- 충돌하면 **먼저 자리를 잡은 쪽이 지키고** 나중 것이 옮긴다.
- ⚠ **번호를 문자열 일괄치환으로 옮기지 않는다.** 한 번 그렇게 했다가 **남의 인덱스 행까지 바꿨다.**
  내용으로 특정해 바꾸고 **바꾼 건수를 세어 기대값과 맞는지 확인**한다.
- ID를 짓는 규칙은 [[기획 세션 지침]] §5에 있다.

> ⚠ 레거시 (2026-09-15): 옛 해법 "세션별 번호대 분할(예: 백엔드 150번대, 기획 200번대)"은 세션을 역할로 나누던 시절의 것이다. 지금은 세션이 이슈 단위로 나뉘어 역할별 번호대가 맞지 않는다. 발번이 자주 겹치면 그 프로젝트에 맞는 방법을 사용자에게 제안한다.

## 10. 세션끼리 사람을 거치지 않고 직접 주고받는다

사람이 문서를 손으로 나르면 **그 사람이 병목이 되고, 오래된 판본이 전달된다.**
실제로 그렇게 돌다가 하루에 여러 번 어긋났다.

### 세 갈래를 구분한다

| | 도구 | 남나 | 쓰임 |
|---|---|---|---|
| **알림** | Orca 세션 간 메시지 `orca orchestration send --to <받는쪽> --subject "…" --body "…"`, 또는 상대 터미널에 한 줄 넣기 | △ 받는 쪽 수신함에만 남음 | "글 남겼습니다" 한 줄 |
| **유통** | 공유 디렉터리(git 밖) | △ | 커밋 없이 즉시 오감 |
| **기록** | 저장소(`docs/…`) | ✓ 영구 | **확정된 것만** 커밋 |

> ⚠ **알림은 기록이 아니다.** 어떤 도구로 보내든 상대 에이전트에게 닿을 뿐이고, 사용자가 보는 기록이 아니다.
> 내용은 반드시 파일에 남기고, 알림에는 경로만 쓴다. 자세한 사용법은 Orca의 orchestration 스킬을 따른다.
>
> **레거시 (2026-11-05 바뀜):** 예전에는 `ao send --session <id>`와 `ao session ls`를 썼다. 지금 이 Mac에는 `ao` 명령이 없고 세션은 Orca로 운영한다. 옛 문서에 `ao` 표기가 남아 있으면 Orca 메시지로 읽는다.

### 🔴 보냈다고 전달된 것이 아니다

| 경로 | 성질 |
|---|---|
| Orca 세션 간 메시지 | 상대 수신함에 넣을 뿐이다. **상대가 조회해야 닿는다** |
| 상대 터미널에 직접 입력 | 상대 세션의 다음 프롬프트로 들어간다. **확실히 읽힌다** |

- **메시지만 보내고 전달됐다고 하지 않는다.** 읽었는지 확인하고, 안 읽었으면 상대 터미널에 한 줄 넣는다.
- 메시지 명령이 돌려주는 `ok: true`는 상대 수신함에 넣는 데 성공했다는 뜻일 뿐이다. 상대 수신함의 읽음 수(`read`)가 0이면 아무도 안 읽은 것이다.
- 긴 내용은 파일이나 메시지로 보내고, 알림은 터미널로 한다. 둘을 같이 쓴다.
- **받을 때도 터미널로만 받지 않는다.** 터미널 스크롤백은 밀려서, 긴 회신을 터미널로만 받으면 앞부분이 사라진다. 긴 회신은 파일이나 메시지로 받는다.

#### 사례

> 세 세션에 공지를 보내고 "전달 완료"라고 보고했는데, 확인하니 `read=0`이었다. 아무도 안 읽고 있었다.
> 다른 날에는 두 세션의 "남은 작업 목록"을 터미널 회신으로만 받았다가, 스크롤백이 밀려 앞부분을 잃고 다시 요청했다.

### 한 줄 도구

프로젝트마다 공유 디렉터리에 둔다(예: `_공유/말하기.sh`):

```bash
./말하기.sh <받는쪽> "<내용>" [문서경로]
```

한 번에 셋을 한다. **기록에 덧붙여 쓰고(append), 상대 터미널에 알리고, 넘긴 문서가 원격 기본 브랜치에 있는지 확인한다.** 문서가 원격에 없으면 상대 워크트리에서 안 보인다고 경고한다. 이 도구에는 상태판 기능이 없다. 상태판을 두는 프로젝트는 생성기를 따로 돌린다.

- **append로 쓴다.** 여러 세션이 동시에 써도 안 깨진다.
  HTML이나 JSON을 통째로 다시 쓰게 하면 서로 덮어써서 깨진다.
- **상대가 작업 중이면 알림을 보내지 않고 기록만 남긴다.**
  작업 중인 에이전트에 끼어들면 하던 일이 흐트러진다. 상대 상태를 Orca에서 확인하고 보낸다.

### 상태판

사용자가 **파일 하나만 보면** 전체가 보이게 한다.

```
세션 카드    누가 무엇을 맡고 지금 무엇을 하는지
막힌 것      누가 누구를 기다리는지, 며칠째인지 (해결되면 지운다)
대화         채팅 형태로 계속 쌓임 (고정 높이 스크롤이라 페이지는 안 길어진다)
최근 완료    최대 5건, 넘으면 오래된 것부터 지운다
```

- 데이터(JSON, JSONL)와 화면(HTML)을 **분리하고 생성기로 잇는다.** 세션은 데이터만 고친다.
- 데이터를 HTML 안에 박아 넣으면 `file://`로 열어도 동작한다(fetch는 CORS에 막힌다).
- **자기 줄만 고친다.** 남의 줄을 건드리지 않는다.

### 🔴 가장 흔한 함정: 내 워크트리에만 있는 것을 넘긴다

- **"했습니다"라고 알리기 전에 상대가 실제로 볼 수 있는지 확인한다.**
  워크트리는 격리돼 있어 **커밋과 푸시 전에는 안 보인다.**
- 아직 못 푸시했으면 **그 사실을 알림에 함께 적는다**: *"아직 내 워크트리에만 있습니다"*.
- 상대가 **생성물**(자동 생성 상수, 계약 클라이언트 등)을 쓰는 구조면 원본을 받기 전엔
  아무것도 못 한다. 그런 의존은 알림에 명시한다.

### 셸 스크립트 주의

**변수명에 한글을 쓰지 않는다.** bash는 ASCII 식별자만 받는다.
`bash -n` 문법 검사로는 **안 잡히고** 실행할 때 `command not found`로 터진다.
문서와 주석은 한글로 쓰되 식별자는 ASCII로 둔다.

#### 사례

> **실제 사고**: 기획이 에러 코드를 발번하고 "쓰세요"라고 알렸는데,
> **커밋과 푸시를 안 해서 상대 워크트리에는 그 코드가 없었다.** 상대는 그 파일에서
> 상수를 자동 생성하는 구조라 **손으로 넣을 수도 없어 그대로 막혔다.**

## 11. 🔴 한글 파일 이름: `core.quotepath`를 끈다

**설정이 켜져 있으면 한글 파일 이름이 8진수로 이스케이프돼 검색에 아예 안 잡힌다.**

- 전역 git 설정(`core.quotepath false`)은 설치 스크립트가 넣는다(사용자가 설치할 때 한 번). Claude 세션은 전역 git 설정을 바꿀 수 없다(훅이 `git config --global` 쓰기를 막는다).
- 확인: `git config --get core.quotepath`가 `false`면 된다.
- 안 되어 있으면 명령마다 `git -c core.quotepath=off`를 붙이고, 사용자에게 설치 스크립트를 다시 돌려 달라고 알린다.

```
git ls-tree -r --name-only origin/main | grep 회신   # 0건
git log --name-only                                          # "docs/_\354\236\221..." 로 보임
```

전달 문서가 **전부 한글 이름**인 프로젝트에서는 이 설정 하나로 **동료 세션의 문서가 통째로
안 보인다.** 어느 날 세션 셋이 서로 "끝났다"를 여러 번 놓쳤고, 그중 상당수가
이것 때문이었다.

**증상이 이렇게 나타난다**: 상대가 "문서에 답 남겼다"는데 나는 그 파일을 못 찾는다.
그러면 상대가 안 했다고 판단하고 같은 질문을 다시 한다. 상대는 세 번째 같은 답을 적는다.

경로를 알면 이렇게 열 수는 있다(설정과 무관):

```bash
git show origin/main:"docs/_작업/<한글 이름>.md"
```

## 12. 헛기다림: "아직 안 됐다"보다 "됐는데 안 닿았다"가 훨씬 많다

원인 셋, 대응 셋:

1. **결정을 닫고 그 결정이 적힌 자리를 안 고쳤다.**
   대응: 결정을 내리는 것과 결정이 적힌 자리를 고치는 것은 **별개 작업**이다.
   후자를 빠뜨리면 결정을 안 내린 것과 같다. `status`, 주석, 미결정 표를 같이 닫는다.
2. **알림이 작업 중인 상대에게 제때 닿지 않는다.**
   대응: **답은 저장소에 문서로, 메시지엔 경로만.** 순서는 문서 푸시, 상태판 갱신,
   상대가 쉬는 중인지 확인, 짧은 메시지다(§10).
3. **`core.quotepath`** (§11).

> **"됐다"를 주장할 때는 검증 명령을 같이 준다.** 말로 "있습니다" 하지 말고
> `git show origin/main:<경로> | grep -c <값>`처럼 **상대가 직접 확인할 한 줄**을 준다.
> 저장소가 답하게 하면 왕복이 끝난다.

> ⚠ **세는 방법도 틀릴 수 있다.** `grep -c reward`는 `rewardType`
> 까지 세어 "아직 남았다"로 보이게 한다. 접두어가 겹치는 이름은 `grep -vE "(Type|Id)"`
> 로 걸러서 센다.

#### 사례

하루에 여러 번 났고 **한 번도 미완성이 아니었다.**

| 기다린 것 | 실제 |
|---|---|
| 확정 문서 3건 | 끝난 작업, `status`를 안 닫음 |
| 전용 표 재작업 | 이미 푸시됨 |
| 서버 잠금 가드 | 이미 푸시됨 |
| 계약 파일의 새 필드 | 이미 계약에 있음 (두 커밋에 나뉘어 들어가 한쪽만 보면 없어 보임) |
| 판정 규칙과 연결 필드 | 이미 확정되고 전파됨 |
| 어드민 폼 제거 신호 | 이미 완료됨 |

## 14. 🔴 문서 갱신과 레거시 표시 (2026-11-02, 2026-11-16 01 13장에서 옮김)

공유 저장소의 문서는 다른 세션과 다른 사람도 읽고 그대로 믿는다. 그래서 바뀌면 같은 작업에서 문서도 고치고, 이유를 적고, 낡은 것은 레거시로 표시한다. 배정과 검수 때 이 규칙을 넣는 방법은 [[01 커맨드 센터 운영]] §13.5에 있다.

### 14.1 바뀌면 같은 작업 안에서 문서도 갱신한다

- 코드, 결정, 일정이 바뀌면 그 내용을 적어 둔 문서(트래커, 결정 기록, 요청서 대응 문서, 체크리스트, README, 전달 문서)를 **같은 작업에서 함께 고친다.** "나중에 문서 정리"로 미루지 않는다.
- 고친 문서는 코드와 같이 커밋한다. 코드만 합치고 문서를 빠뜨리면 그 작업은 끝난 것이 아니다.
- 성능 리포트는 프로젝트 저장소의 `docs/성능향상/`에 쓴다([[07 출시 전 성능 점검]]).

### 14.2 갱신했으면 이유를 적는다

- 문서를 고칠 때는 **날짜, 무엇을 바꿨는지, 왜 바꿨는지, 근거**(커밋, 결정한 사람이나 회의, 받은 요청서)를 함께 적는다.
- 앞의 내용은 지우지 않는다. 취소선으로 남기거나 문서 아래 "변경 이력"에 옮겨서, 무엇이 언제 왜 바뀌었는지 따라갈 수 있게 한다.
- 예: `~~미적용~~ 구현됨 (2026-10-26, 커밋 abc1234, 점검에서 확인)`

### 14.3 낡은 것은 "레거시"라고 표시한다

- 더 이상 유효하지 않은 이슈, 문서, 결정, 목업, 코드 경로에는 **레거시 표시**를 붙인다. 지우지 않고 남겨 둘 때 특히 그렇다.
- 표시에는 네 가지를 함께 적는다.
  1. 레거시가 된 날짜
  2. 이유(다른 방식으로 바뀜, 요구가 취소됨, 이미 해결됨 등)
  3. 지금 봐야 할 문서나 이슈의 링크
  4. 아직 남은 영향이 있으면 그 내용
- 위치는 다른 사람이 처음 보는 곳에 둔다.
  - 문서: 맨 위 첫 줄 (예: `> ⚠ 레거시 (2026-11-02): 결정 D24로 바뀜. 최신 문서는 [[…]]`)
  - 트래커와 이슈: 상태 칸에 "레거시", 제목 앞에 `[레거시]`
  - 코드: 해당 함수나 파일 머리 주석
- 레거시 표시 없이 낡은 문서를 그대로 두지 않는다. 읽는 사람은 그것이 낡았는지 알 방법이 없다.
- 작업 범위 안에서 낡았는데 표시가 없는 문서가 보이면 함께 표시한다.

### 14.4 문서 이름은 "날짜_간단한 내용"으로 짓는다 (2026-11-02)

- 새로 만드는 문서(리포트, 요청서, 점검 결과, 전달 문서, 회의 기록, 인계 문서)는 파일 이름을 **`YYYY-MM-DD_간단한 내용.md`** 로 짓는다. 띄어쓰기를 써도 된다.
  - 예: `2026-11-03_쿠폰 수정삭제 점검결과.md`, `2026-11-05_주문목록 쿼리 개선.md`
- 날짜를 **맨 앞에** 둔다. 그래야 폴더에서 이름순으로 정렬했을 때 날짜순이 되고, 맨 아래가 가장 최신이 된다. 날짜를 뒤에 붙이면(`점검결과_20261103.md`) 같은 주제끼리만 모이고 최신을 찾기 어렵다.
- 같은 날 같은 주제로 여러 번 쓰면 `_2차`, `_3차`를 붙인다. 예: `2026-11-03_쿠폰 점검결과_2차.md`
- 간단한 내용은 무엇에 관한 문서인지 바로 알 수 있게 쓴다. "정리", "메모", "무제"처럼 내용이 드러나지 않는 이름은 쓰지 않는다.
- 같은 주제의 새 문서를 쓰면, 앞 문서 맨 위에 레거시 표시와 새 문서 링크를 남긴다(14.3). 읽는 사람이 날짜와 레거시 표시만 보고 최신 문서를 찾을 수 있어야 한다.
- 이미 있는 문서의 이름은 링크가 깨질 수 있으니 한꺼번에 바꾸지 않는다. 새로 만드는 문서부터 적용하고, 바꿀 때는 링크도 함께 고친다.

#### 사례

> 저장소는 나 혼자 쓰지 않는다. 다른 세션과 다른 사람이 같은 문서를 읽고 그대로 믿는다.
> 한 프로젝트의 엣지케이스 점검(2026-10-26)에서, 트래커에 "미적용"으로 적힌 결정 두 건이 코드에는 이미 구현돼 있었다.
> 문서만 본 점검 담당은 이 두 건을 "아직 안 된 일"로 다시 보고할 뻔했다. 문서가 코드보다 늦게 따라가면,
> 그 문서를 읽는 사람이 낡은 상태를 사실로 받아들이게 된다.

## 15. 🔴 작업 산출물은 프로젝트 `_작업/`에 (2026-11-13)

세션 임시 폴더(scratchpad)는 세션이 끊기면 사라지고, 사용자가 중간에 열어 볼 수 없다. 산출물이 여러 곳에 흩어지면 다른 사람이 이어받지 못한다.

- 보고서, 설계서, 목업, 요청서와 그 초안은 **처음부터** 그 프로젝트 문서 저장소의 `_작업/`에 만든다. 보내기 전 초안이어도 여기에 둔다.
- 보낼 문서는 `_발신함/`에 둔다([[13 보낼 문서와 발송 상태]]).
- 인계 문서는 `_작업/인계/`에 둔다(§8).
- 임시 폴더에는 도구를 돌리려고 잠깐 쓰는 파일(캡처 확인용 사진, 로그, 스크립트)만 둔다.
- 이미 있는 목업과 요청서는 링크와 이력이 깨지지 않게 그 자리에 둔다. 새로 만드는 것만 `_작업/`에 만든다.
- 그 저장소가 원격에 올라가는 곳이면 `.gitignore`에 `_작업/`을 넣어 올라가지 않게 한다.
- **장치:** 훅이 임시 폴더에 HTML, PDF, 오피스 문서를 만들려 하면 막고, md, txt, csv는 알림만 한다.
- **사례 (2026-11-13):** 한 세션이 "보내기 전 문서"를 "어디에도 저장하지 말라"로 잘못 읽고 설계서를 임시 폴더에서만 만들어, 세션이 끝나면 사라질 뻔했다. "발송 전"은 상태 표시일 뿐 저장 위치와는 상관없다.

## 16. 구조를 익히는 장치 (2026-11-16)

사용자가 코드를 직접 보지 않고 일하는 시간이 길어, AI가 멈췄을 때도 프로젝트를 이해하고 기본 대응을 할 수 있게 일하는 흐름 안에서 구조를 익히게 한다. 따로 공부 시간을 잡지 않고, 이미 하는 일에 붙인다.

- **구조 지도와 런북:** 프로젝트마다 `_작업/구조/구조 지도.md`와 `런북.md`를 둔다(`4n5rud-arch` 스킬이 만들고 갱신). 구조를 바꾼 작업은 끝날 때 구조 지도의 해당 칸도 고친다.
- **보고에 구조 메모:** 코드나 구조를 바꾼 작업 결과 보고에는 08 §4의 "구조 메모"를 붙인다.
- **장애 패턴 노트:** 버그나 장애를 해결하면 하네스 저장소의 `learning/장애 패턴.md` 맨 위에 세 줄(계층, 원인, 패턴)을 더한다. 프로젝트 이름은 써도 되지만 비밀값과 고객 개인정보는 쓰지 않는다. 노트 보관함 `학습/`에 사본이 맞춰진다.
- **배정 전 예측과 구조 질문:** 커맨드 센터 쪽 규칙은 01 §14.
