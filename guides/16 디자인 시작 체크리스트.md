# 디자인 시작 체크리스트

> 새 프로젝트에서 디자인을 시작할 때 **무엇을 받고, 피그마에 무엇을 어떤 순서로 만들고, 넘기기 전에 무엇을 확인하는지** 하나씩 체크하는 문서다. 성격이 다른 두 프로젝트(모바일 앱 프로젝트, 쇼핑몰 프로젝트)에서 공통으로 쓴 구성을 뽑고, 두 곳 검수에서 실제로 걸린 문제를 점검 항목으로 바꿨다.
> 피그마 디자인 규칙의 **원본은 이 문서**다. 함께 읽을 문서: 레퍼런스를 모으고 공통 모듈을 뽑는 방법은 `디자인 레퍼런스 지침.md`, 피그마 컴포넌트의 개념과 속성 네 가지, 피그마 MCP 작업 메모는 `디자인 시스템 지침.md`에 있다. 이 문서는 프로젝트 하나를 시작해서 넘길 때까지 빠뜨리지 않도록 **체크하는 목록**이다.

---

## 0. 원칙 여섯 가지

1. **화면부터 그리지 않는다.** 기초 값, 컴포넌트, 패턴, 흐름, 화면 순서로 쌓는다. 화면은 컴포넌트 인스턴스와 변수만으로 조립한다.
2. **원문에 있는 것만 그린다.** 화면 목록, 문구, 숫자, 효능이나 비교 주장은 기획서, 설계서, 고객 원고에서만 가져온다. 이 문서에 있는 화면이라도 기획에 없으면 만들지 않는다. 근거가 없는 값은 지어내지 않고 "미정"으로 적은 뒤 보고한다.
3. **상태까지 그려야 끝난 것이다.** 화면마다 6장의 상태를 함께 그린다. 경계 상황 자세한 규칙: `02 이슈 세션 운영.md` §3 ④.
4. **값은 한 곳에서만 정한다.** 색, 간격, 둥글기, 크기는 변수에, 글자는 글자 스타일에 둔다. 견본 글자와 설명에 숫자를 따로 적었다면 변수를 바꿀 때 같이 고친다.
5. **고객이 보는 것과 작업 자료를 나눈다.** 작업 메모, 생성 도구 이름, 치수 메모는 고객 공유 페이지에 남기지 않는다.
6. **정한 것을 함부로 뒤집지 않는다.** 따르는 순서는 고객 확정 사항(와이어프레임 포함), 사용자(PM) 결정, 프로젝트 디자인 규칙이다. 외부 레퍼런스는 방향을 바꾸는 근거로 쓰지 않는다. 고객 요청으로 이미 정한 배치나 모양을 바꾸기 전에는 예전 요청과 피드백 기록부터 찾고, 부딪치면 바꾸기 전에 사용자에게 확인한다.

이 문서의 숫자는 두 프로젝트에서 쓴 **예시 값**이다. 고객 시안이나 BI 가이드에 정한 값이 있으면 그것을 따르고, 없을 때만 출발점으로 쓴다.

## 2. 파일 구성

### 2-1. 파일을 둘로 나눈다

| 파일 | 담는 것 | 규칙 |
|---|---|---|
| 설계 파일(와이어프레임) | 화면 배치와 요소 순서, 흐름, 공통 UI 치수 | 고객에게 보낸 설계의 그림이다. 디자인 작업 중에는 **읽기만** 한다 |
| 디자인 파일(시안) | 색, 글자, 사진, 간격, 모양을 입힌 화면 | 설계 파일의 배치를 바꾸지 않는다. 바꿔야 할 것 같으면 바꾸지 말고 보고한다 |

피그마 디자인 파일이 있는 프로젝트에서는 **피그마가 디자인의 원본**이다. HTML 목업은 빠르게 비교하고 판단을 받는 보조 자료로만 쓰고(`02 이슈 세션 운영.md` §3), 정한 내용은 피그마에 반영한다. HTML을 고쳐 피그마로 다시 옮기는 방식은 쓰지 않는다.

작은 프로젝트는 한 파일로 시작해도 된다. 고객에게 설계를 한 번 보냈다면 그 판은 따로 떼어 둔다.

|---|---|---|---|

| 03 | 패턴 | 컴포넌트를 묶은 반복 구조와 규격 카드 | [ ] |
| 04 | 흐름도 | 기호, 범례, 기능별 판단과 분기 | [ ] |

| 07 | 상태와 오류 화면 | 오류 페이지, 알림 띠와 토스트, 불러오는 중, 빈 상태와 개수, 품절과 확인창, 옆 메뉴 | [ ] |

- [ ] 페이지를 끼워 넣거나 번호를 바꾸면 00 안내 표도 같이 고쳤다.

### 2-3. 프로젝트 디자인 규칙 폴더

피그마와 별도로, 그 프로젝트에서 정한 값과 결정을 글로 남기는 폴더를 프로젝트 문서 저장소에 둔다(예: `디자인/디자인 규칙/`). 파일 이름만 정하고, 안의 내용은 그 프로젝트에서 실제로 정한 것만 적는다(이 문서의 예시를 옮겨 적지 않는다).

| 파일 | 담는 것 |
|---|---|
| `README.md` | 기준(무엇이 원본인지), 우선순위, 갱신 방법 |
| `01_페이지 구성.md` | 피그마 페이지 구조와 배치 규칙 |
| `02_기초 토큰.md` | 색, 글자, 간격, 둥글기, 그림자, 레이아웃 |
| `03_아이콘과 일러스트.md` | 아이콘과 그림 규칙 |
| `04_컴포넌트.md` | 컴포넌트 목록과 상태 |
| `05_패턴.md` | 반복 구조와 고르는 기준 |
| `06_흐름과 분기.md` | 화면 이동과 예외 |
| `07_문구.md` | 말투, 금지 표현, 숫자와 단위 표기 |
| `08_검수 체크리스트.md` | 고친 뒤 돌리는 검사 |

새로 정한 규칙에는 날짜와 근거(누가, 왜)를 붙이고, 바뀐 규칙은 지우지 않고 "(YYYY-MM-DD 변경)"으로 남긴다(`00 세션 공통 지침.md` §14). 지금 규칙과 지난 개수, 노드 번호 같은 이력은 한 줄에 섞지 않는다.

- [ ] 상태나 등급은 **색만으로 구분하지 않고** 글자와 함께 쓴다.

### 3-2. 변수

| 컬렉션 | 담는 것 | 체크 |
|---|---|---|
| 기본값(Primitives) | 색 단계(`color/blue/50~900`, `color/gray/0~900`, 상태 색, 투명도 색) | [ ] |
| 의미(Semantic) | 기본값을 가리키는 별칭: `text/*`, `bg/*`(canvas, subtle, brand, overlay, scrim 등), `border/*`(default, strong, focus, danger), `icon/*`, `action/*`이나 눌림 색, `feedback/*` | [ ] |
| 치수(Scale) | `space/*`, `radius/*`, `size/*`(누름 영역 최소 44, 버튼 높이 L, M, S, 헤더, 하단 탭, 아이콘 16, 20, 24), `stroke/icon` | [ ] |
| 테마(있을 때) | 템플릿이나 브랜드마다 바뀌는 값만(3-3) | [ ] |
| 도메인(있을 때) | 상품별 색처럼 화면 일부에만 쓰는 값 | [ ] |

- [ ] 화면과 컴포넌트는 **의미 변수만** 연결한다. 기본값 변수를 직접 쓰지 않는다.
- [ ] 변수 이름은 개발 코드의 토큰 이름과 같게 짓고, 변수의 코드 문법(code syntax)에 웹 이름을 적는다(예: `color/text/primary`는 `--color-text-primary`).
- [ ] 글자 스타일은 `역할/크기 굵기`(예: `Body/15 Regular`)나 `type/역할`(예: `type/body`) 가운데 하나로 통일한다. 스타일마다 크기, 굵기, 줄 높이, 자간을 모두 넣는다.
- [ ] 효과 스타일은 그림자 단계만 둔다(`shadow/sm, md, lg` 등).
- [ ] 레퍼런스 파일에서 따라온 남의 변수, 글자 스타일, 효과는 지웠다.

### 3-3. 테마 모드 (여러 브랜드나 템플릿이 쓰는 틀일 때)

예: 한 쇼핑몰 프로젝트는 서로 다른 화면 유형 셋을 하나의 테마 컬렉션 모드로 만들었다.

- [ ] 바뀌는 값만 테마로 뺀다: 헤더 바탕과 글자, 검색 칸, 로고 심볼, 첫 화면 바탕, 하단 탭 지금 칸, 탭 지시선, 고른 칩, 사진 둥글기.
- [ ] 화면 프레임마다 테마 모드를 **명시**한다(기본값에 기대지 않는다).
- [ ] 01에 변수와 모드를 가로세로로 놓은 표를 두고, 02에 테마 비교 섹션을 둔다.
- [ ] 템플릿끼리 같은 규칙이 다르게 적용되지 않았는지 본다(사례는 부록).
- [ ] 정석은 템플릿마다 다른 예시 로고와 포인트 색을 입혀 "다른 몰"로 보이게 하는 것이다. 헤더를 가리면 같아 보이는 템플릿은 차이가 부족하다.

### 3-4. 접근성 점검 표

01 끝에 표를 두고, 크게 고칠 때마다 다시 잰 숫자를 덧붙인다(처음, 다시 점검, 마무리 꼴).

| 항목 | 기준 |
|---|---|
| 글자 대비 | 4.5:1, 큰 글자(24px 이상 또는 18.66px 이상 굵게) 3:1. **고른 칸, 연한 색 면, 사진 위 글자**도 잰다 |
| 아이콘과 그래프 | 뜻을 전하는 것은 3:1 |
| 누름 영역 | 가로세로 44 이상. 작은 버튼과 글자 링크는 투명 누름 영역으로 감싼다 |
| 포커스 표시 | 3:1 이상(사례는 부록) |
| 스크린 리더 이름 | 아이콘만 있는 단추와 그림에 읽어 줄 이름을 컴포넌트 설명에 적음 |
| 비활성 | 비활성 요소 자체는 예외지만, 왜 못 쓰는지 알려 주는 글(품절 배지 등)은 4.5:1 |
| 글자 확대 | 기기 글자 200%에서 잘리지 않게 글자 칸 높이를 내용에 맞춤 |
| 토큰 밖 색, 스타일 미연결 | 개수를 세고 남은 것은 예외 이유(브랜드 규정 색, 그래프 전용)를 적음 |

## 4. 02 컴포넌트

머리에 쓰는 법을 적는다: **화면은 이 컴포넌트를 조립해서만 만든다. 새 모양이 필요하면 여기에 변형을 추가한다.**

### 4-1. 만드는 규칙

- [ ] 이름은 `분류/이름`(Input/Button, Nav/Header, Info/Badge, Card/Product, Feedback/Toast, Admin/Stat Card). 안에서만 쓰는 부품은 앞에 `_`를 붙인다(`Nav/_Bottom Nav Item`).
- [ ] 컴포넌트마다 **설명(description)** 을 한 줄 넣는다: 무엇이고 어디에 쓰는지, 지킬 규칙(예: "한 화면에 주 단추는 하나만").
- [ ] 변형 속성은 `이름=값`으로, 글자와 켜고 끄기와 바꿔 끼우기는 컴포넌트 속성으로 만든다. 안쪽 인스턴스(단추, 배지, 사진)는 바깥에서 바꿀 수 있게 노출한다.
- [ ] 누를 수 있는 것은 기본, 눌림, 비활성, 포커스를 모두 만든다. 단추는 로딩까지. 없는 상태는 설명에 "(눌림 없음)"처럼 적는다.
- [ ] 선택형(칩, 탭, 체크박스, 라디오, 토글, 선택지, 선택 카드)은 켜짐과 꺼짐을 상태마다 만든다.
- [ ] 입력은 기본, 포커스, 입력됨, 오류(테두리와 안내 한 줄), 비활성.
- [ ] 두 화면 이상에 나오는 묶음(카드, 표 줄, 배너, 하단 단추 바)은 반드시 컴포넌트로 만든다. 복제한 프레임으로 쓰지 않는다.
- [ ] 한 화면에만 나오는 구역은 인스턴스와 변수만 써서 묶은 프레임을 허용한다. 두 번째로 쓰게 되면 그때 컴포넌트로 옮긴다.
- [ ] 컴포넌트는 변수와 스타일만 써서 만들고, 자동 레이아웃(Auto layout)을 기본으로 쓴다.
- [ ] 인스턴스를 분리(Detach)하지 않는다. 분리해야 할 것 같으면 원본에 변형이나 속성을 더한다. 속성 만드는 자세한 규칙은 `디자인 시스템 지침.md` 5장.
- [ ] 아이콘은 벡터로, 이름과 크기(24, 20, 16)를 변형으로 묶거나 이름별 단독 컴포넌트로 만든다.
- [ ] 🔴 아이콘을 연한 색 원, 둥근 사각, 그라데이션 바탕에 넣어 감싸는 장식을 쓰지 않는다(2026-11-16 사용자 지시). 생성형 화면에서 흔히 보이는 모양이라 화면이 기계로 만든 것처럼 보인다. 빈 상태, 오류, 안내, 설문 질문, 선택 카드, 바로가기 모두 같다. 아이콘은 바탕 없이 두고 크기, 굵기, 색으로 위계를 준다. 꼭 면이 필요하면 아이콘이 아니라 카드나 구역 전체에 면을 준다.
- [ ] 머리글에 적은 개수(컴포넌트 수, 변형 수)를 실제와 맞춘다.

### 4-2. 공통 목록

두 프로젝트 모두 쓴 것이다. 기획에 해당 기능이 있으면 만든다.

**기초**: 사진 자리(둥글기 변형), 로고 자리, 구분 띠

**입력과 선택**
- [ ] 단추: 종류(주, 보조, 테두리, 글자, 위험), 크기(L, M, S), 상태(기본, 눌림, 비활성, 포커스, 로딩)를 모두 조합
- [ ] 입력 칸, 선택 상자
- [ ] 체크박스, 라디오, 토글
- [ ] 칩, 선택지와 선택 카드
- [ ] 수량 조절(최소일 때 빼기 비활성)
- [ ] 하단 행동 단추 줄(단추 하나, 금액과 단추, 찜과 단추, 단추 둘, 품절)
- [ ] 소셜 로그인 단추(브랜드 규정 색 그대로)

**탐색**
- [ ] 헤더(메인, 가운데 로고, 검색 포함, 하위 화면 뒤로와 제목, 설문이나 단계 화면). 오른쪽 동작은 하나
- [ ] 하단 탭(지금 칸별 변형, 지금 칸은 면 아이콘과 포인트 색)
- [ ] 탭, 넘기는 탭 막대, 칩 줄, 정렬 막대, 바로가기 아이콘 줄
- [ ] 옆 메뉴(서랍)
- [ ] 푸터(회사 정보)

**정보 표시**
- [ ] 배지(브랜드, 회색, 오류, 성공, 주의, 진함), 태그(누를 수 없음)
- [ ] 섹션 제목(한 줄, 두 줄, 더 보기, 강조 줄)
- [ ] 목록 줄(뒤쪽: 화살표, 값, 토글, 단추), 묶음 제목
- [ ] 알림 줄(안 읽음, 읽음)
- [ ] 접기와 펼치기

**알림과 겹침**
- [ ] 돌림 표시(크기, 색), 뼈대(스켈레톤: 카드, 목록 줄, 상세 모양)
- [ ] 토스트(성공, 되돌리기), 알림 띠(헤더 아래, 오류와 안내)
- [ ] 확인창(일반, 위험), 바텀시트
- [ ] 빈 상태 블록(빈 화면과 오류 화면이 같이 씀)
- [ ] 상태 표시줄과 홈 표시줄(앱일 때)

**그 밖에 필요할 때** (기획에 쓰는 화면이 있으면 만든다)
- [ ] 입력: 떠 있는 버튼, 비밀번호 입력, 검색 입력, 여러 줄 입력, 슬라이더, 날짜와 시간 고르기
- [ ] 탐색: 경로 표시(Breadcrumb), 쪽 넘기기(Pagination), 단계 표시(Stepper)
- [ ] 정보 표시: 아바타, 도움말 풍선(Tooltip)
- [ ] 알림과 겹침: 팝오버, 진행 막대

**도메인 묶음** (프로젝트마다 바뀜. 핵심 화면 하나를 그려 보며 뽑는다)
- 모바일 앱 프로젝트: 핵심 결과 카드, 등급 배지, 회차 비교, 그래프, 도메인 공식 아이콘, 챗봇 입력창과 추천 질문
- 쇼핑몰 프로젝트: 상품 카드(2열, 가로, 큰 카드, 정사각), 메인 배너(유형별), 장바구니 상품 줄, 상세 정보 머리, 사진 순서 표시, 상세 구간 제목, 단계, 상품 정보 표 줄, 구성 카드, 설문 진행과 질문과 선택지, 추천 카드

**관리자** (관리자 화면이 있을 때)
- [ ] 왼쪽 메뉴와 메뉴 한 칸, 상단 바(PC, 휴대폰), 휴대폰 옆 메뉴
- [ ] 숫자 카드, 묶음 상자와 제목, 목록 한 줄
- [ ] 표 상자와 표 한 줄(머리, 줄, 상태 글자 색), 휴대폰용 주문 카드

## 5. 03 패턴

패턴마다 옆에 **규격 카드**를 둔다. 칸은 구성 요소, 여백과 치수(치수선 그림), 쓰는 곳, 쓰지 말 것이다.

| 패턴 | 쓰는 곳 | 쓰지 말 것 |
|---|---|---|
| 안내 상자(정보, 주의, 성공) | 진행 전에 알아야 할 한두 문장 | 개발자용 설명, 세 문장 이상 |
| 바텀시트 | 화면을 떠나지 않고 한 가지 고르기 | OS 권한 창 흉내, 버튼 셋 이상, 긴 약관 |
| 토스트 | 방금 한 행동의 결과(저장했어요, 지웠어요). 하단 영역 위 16, 3초 | 되돌릴 수 없는 행동 확인, 두 줄 넘는 글 |
| 알림 띠 | 화면을 보는 동안 계속 알아야 할 오류나 안내 | 지나가는 완료 알림 |
| 확인창 | 잃는 것이 있는 행동 직전(지우기, 탈퇴, 나가기). 실행 단추는 동사 | "확인", "예" 단추, 바깥 누름으로 닫기 |
| 빈 상태 | 목록이나 기록이 0개 | 단추 2개 이상, 하단 단추와 같은 행동 반복, 오류 상황 |
| 뼈대 | 처음 불러올 때 | 실제와 다른 블록 모양, 블록 안 글자, 반짝임 |
| 글머리 목록 | 동의, 탈퇴 안내의 짧은 나열 | 순서 있는 단계, 누를 수 있는 항목 |
| 권한 줄 | 기기 권한과 알림 켜고 끄기 | 실제 권한과 다른 토글 상태 |

### 5-1. 알림 방식 고르기

| 상황 | 쓰는 패턴 | 사라짐 | 단추 |
|---|---|---|---|
| 화면을 보는 동안 계속 알아야 할 정보나 주의 | 안내 상자(화면 안) | 안 사라짐 | 없음(링크 하나까지) |
| 지금 행동을 이끄는 알림(새 결과 도착, 다음 할 일 시기) | 알림 띠(화면 위쪽) | 처리하면 사라짐 | 띠 전체를 누르면 이동 |
| 사용자가 한 행동의 결과 확인(저장, 복사, 초대 보냄) | 토스트 | 3초 뒤 자동 | 하나까지(되돌리기) |
| 되돌릴 수 없거나 잃는 것이 있는 행동 직전 | 확인창(가운데) | 단추로만 닫힘 | 둘: 취소(보조), 실행(주, 지우는 행동은 위험 단추) |
| 짧은 설명이 필요한 결정 하나 | 바텀시트 | 단추, 바깥 누름, 아래로 밀기 | 둘까지 |
| 화면 내용 전체를 대신해야 함(결과 없음, 오류, 준비 중) | 상태 화면 | 상태가 바뀌면 | 하나나 둘 |

- 확인창은 제목을 질문으로 쓰고("공유를 해제할까요?"), 본문에 잃는 것을 한 줄로 적고, 실행 단추는 동사로 쓴다("해제하기").
- 한 화면에 안내 상자는 둘까지 둔다. 셋 이상이면 내용을 줄이거나 화면을 나눈다.
- 안내 상자 종류: 정보(기능과 처리 방식 설명), 주의(되돌릴 수 없는 결과, 만료 임박, 개인정보 노출 위험), 성공(완료 뒤에도 화면에 남겨야 하는 결과. 잠깐 알리면 되는 완료는 토스트).
- **바텀시트와 새 화면:** 바텀시트는 결정 하나, 본문 세 줄 이하, 단추 둘 이하, 선택지 다섯 개 이하일 때만 쓴다. 그보다 많거나, 입력 칸이 둘 이상이거나, 스크롤이 필요하면 새 화면으로 만든다.

## 6. 상태 기준

### 6-1. 불러오기와 오류

새 프로젝트도 이 표를 먼저 정한다. 시간 값은 서버 쪽과 합의한다.

| 상황 | 보여 줄 것 |
|---|---|
| 응답 0.3초 미만 | 아무것도 표시하지 않음(깜빡임 방지) |
| 0.3초 넘음 | 뼈대 |
| 3초 넘음 | 뼈대와 안내 한 줄 |
| 10초 넘음 | 시간 초과 오류 |
| 단추를 눌러 처리 중 | 그 단추만 로딩, 다시 누를 수 없음 |
| 인터넷 없음 | 처음 여는 화면은 오류 화면, 보던 화면의 새로고침이면 토스트나 알림 띠 |
| 서버 오류 | 오류 화면("잠시 문제가 생겼어요" 꼴)과 다시 시도 |
| 없는 페이지, 만료, 삭제 | "찾을 수 없어요" 화면과 홈으로 |
| 권한 없음 | "볼 수 없어요" 화면 |
| 서비스 점검 | 점검 중 화면(웹, 쇼핑몰) |
| 로그인 만료 | 확인창, 단추 하나(로그인하기) |
| 입력 오류 | 입력 칸 오류 상태 |

오류 문구에는 오류 코드, 영어, 기술 용어, 사용자 탓 문장을 쓰지 않는다. 아래는 해요체로 쓴 문구 견본이다. 프로젝트 말투에 맞춰 고쳐 쓴다.

| 상황 | 제목 | 설명 | 단추 |
|---|---|---|---|

## 8. 06 화면

화면 하나를 **컴포넌트 하나**로 만들고, 이름은 "화면 이름, 상태"(예: "장바구니, 빈 상태")로 짓는다. 프레임은 폭 고정, 세로 자동 레이아웃(높이는 내용에 맞춤), 바탕은 의미 변수, 테마가 있으면 모드를 명시한다.

화면 페이지 배치:
- [ ] 흐름 단위로 줄을 나누고, 줄 제목은 줄 맨 왼쪽 위에 글자 하나로 둔다.
- [ ] 상태 화면(확인창, 빈 화면, 오류, 로딩, 토스트)은 그 화면 바로 오른쪽에 둔다.
- [ ] 화면 이름은 프레임 이름에만 쓴다. 같은 글자를 프레임 위에 따로 또 달지 않는다(겹쳐 보인다).
- [ ] 메모 카드는 그 화면 바로 아래에 두고, 종류는 범위 밖 기능, 문구 승인 필요, 정책 확정 필요, 흐름 넷으로만 쓴다.
- [ ] 화면 밖에 떠 있는 선이나 도형이 없다. 섹션 바탕은 앱 바탕과 다른 중립 회색으로 둔다.

### 8-1. 기기별 프레임

- [ ] 휴대폰 기준 폭(예: 375나 360)과 좌우 여백
- [ ] 태블릿과 PC 기준 화면(반응형 웹이면 메인 화면 하나라도)
- [ ] 관리자 PC와 관리자 휴대폰(관리자가 있을 때)
- [ ] 바깥 프레임이 안쪽 내용보다 짧아 아래가 잘리지 않았다(사례는 부록)

### 8-2. 화면 묶음

기획서에 기능이 있을 때만 그린다.

**공통**: 로그인, 가입 약관, 본인 확인, 계정 만들기, 첫 질문(온보딩), 계정 복구, 개인정보처리방침, 홈(데이터 없음, 있음), 알림 내역과 상세, 마이페이지, 내 정보, 로그인 수단 관리, 문의와 도움말, 회원 탈퇴, 기기 권한과 알림 설정

**앱 도메인 기능** (모바일 앱 프로젝트 예): 핵심 기능 입력(QR 스캔, 직접 입력), 진행 중, 완료, 결과 목록과 상세와 그래프, 공유하기와 공유 관리, 공유받은 결과, 챗봇과 정보 처리 동의, 기록과 관리

**쇼핑몰** (쇼핑몰 프로젝트 예): 메인(유형별), 상품 목록(유형별), 상품 상세(유형별), 장바구니, 마이페이지(주문 내역, 내 정보), 설문 단계와 추천 결과, 메인 배너, 상세페이지와 썸네일

**관리자**: 운영자 메인(PC, 휴대폰), 통합 관리자 메인

**상태 화면**(07 페이지): 6장 기준표와 6-2 목록

### 8-3. 고객이 고를 시안

- [ ] 시안을 둘 이상 내면 그 위에 차이를 짚은 비교 판을 두고, 00 안내에 고를 기한을 **실제 날짜**로 적는다(사례는 부록).
- [ ] 템플릿처럼 셋 다 쓰는 틀이면 고르는 것이 아니라고 안내한다.

## 9. 사진과 문구

### 9-1. 사진

- [ ] 상품과 실물은 고객 사진을 쓴다. 사진마다 **이름과 내용이 맞는지** 확대해 본다(사례는 부록).
- [ ] 생성 이미지는 실물이 없는 연출에만 쓰고, AI 티가 나지 않아야 한다. 사람 얼굴과 글자가 든 생성 이미지는 쓰지 않는다. 재료나 음식은 실제 모양과 맞는지 원본 크기로 확인한다.
- [ ] 같은 대상을 화면마다 다른 사진으로 보여 주지 않는다(제품 사진과 공장 사진 섞기 등). 짝 표를 정해 둔다.
- [ ] 카드 크기에서 무엇인지 알아볼 수 있는지 본다. 여백 많은 사진을 맞춤(FIT)으로 넣으면 작게 떠 보인다.
- [ ] 자신 없는 자리는 회색 자리로 두고 보고한다.
- [ ] 쓴 사진의 출처(고객 원본, 생성)를 작업 자료에 남긴다.

### 9-2. 문구

- [ ] 사용자 화면 문구는 짧은 해요체로 쓰고, 한 문장에 한 가지만 담는다. 메모체(~함, ~음, 별표 메모)는 화면에 쓰지 않는다.
- [ ] 와이어프레임, 검토자, 개발자에게 하는 말을 화면에 남기지 않는다(예: "검토용", "예시입니다", "실제 문자는 발송되지 않습니다", "정책 검토 초안"). 정책이 아직 정해지지 않았으면 화면에서 빼고 "정책 확정 필요" 메모로 옮긴다.
- [ ] 설계서와 고객 원문 그대로 쓴다. 원문에 없는 숫자, 효능, 비교표를 넣지 않는다(사례는 부록).
- [ ] 같은 표, 같은 개념은 화면끼리 같은 이름으로 쓴다("성분, 함량"과 "항목, 값" 섞지 않기).
- [ ] 화면 문구는 `05 쇠맛 줄이기.md`의 문장부호 규칙을 따른다.
- [ ] 한국어 여러 줄은 낱말 단위로 줄을 바꾼다(피그마는 글자 단위로 꺾는다).
- [ ] 날짜와 개인 값은 자리 표시로 통일한다(0000.00.00, 00.00, OO점, OOO 님).
- [ ] "제목 자리", "운영자 이름" 같은 작업용 자리 표시 글이 남지 않았는지 글자 검색으로 확인한다.
- [ ] 의료, 법무, 금융 문구는 08 개발 전달의 "문구 승인 필요"에 올린다.

### 9-3. 디자인 파일 표기

- [ ] 변수 이름과 색 코드는 01 기초 페이지에만 쓴다. 다른 페이지의 설명, 규격 카드, 메모, 범례는 "본문 15 회색 700", "흰색과 옅은 그림자", "모서리 8"처럼 한글로 푼다.
- [ ] 코드 이름, 파일 경로, 노드 번호, AI 모델 이름, 내부 검사 번호는 디자인 파일에 쓰지 않는다. 08 개발 전달 페이지만 예외다.
- [ ] 레이어 이름은 한글로 역할을 쓴다(링크, 글자, 묶음, 제목, 머리, 그림, 모양). 영어 키가 필요하면 컴포넌트 설명 칸에만 둔다.

### 9-4. 🔴 생성형(AI) 화면처럼 보이지 않게 (2026-11-16 사용자 지적 모음)

고객이 준 레퍼런스를 따르지 않고 "흔한 기본 모양"으로 그리면 화면이 기계로 만든 것처럼 보인다. 아래는 실제로 지적받은 모양이다. 레퍼런스에 같은 모양이 있을 때만 쓴다.

- [ ] **레퍼런스부터 정리한다.** 팝업, 확인창, 알림 띠, 토스트, 프로모션 띠, 안내 상자, 카드는 그리기 전에 레퍼런스 사이트들이 같은 자리를 어떻게 처리하는지(가운데 창인지 아래 시트인지, 면을 쓰는지 선을 쓰는지, 둥글기, 그림자, 단추 모양) 정리해 두고 그 근거로 그린다. 근거 없이 정한 것은 "우리 판단"으로 적는다.
- [ ] 아이콘을 연한 색 원, 둥근 사각, 그라데이션 바탕에 감싸지 않는다(4-1).
- [ ] **연한 색 둥근 카드에 작은 색 꼬리글, 굵은 제목, 오른쪽 아이콘을 얹은 띠**를 기본으로 쓰지 않는다(예: "혜택 안내 / 처음이라면 먼저 써 보세요 / 선물 아이콘"). 모든 칸을 같은 연한 면 카드로 감싸지 않는다.
- [ ] **확인창 기본 모양**(큰 둥근 흰 카드, 굵은 두 줄 제목, 꽉 찬 알약 단추 두 개, 넓은 빨강 면 단추)을 레퍼런스 확인 없이 쓰지 않는다.
- [ ] **오류 띠**를 분홍 바탕, 원 안 느낌표, 빨간 "다시 시도"로 기본 처리하지 않는다.
- [ ] **빨강은 오류와 위험(지우기, 나가기)에만** 쓴다. 혜택 안내 같은 일반 안내 띠에 빨간 글자나 분홍 면을 쓰지 않는다.
- [ ] 뜻 없는 장식 아이콘을 줄마다 붙이지 않는다. 같은 모양 블록을 반복해 화면을 채우지 않는다.
- [ ] 메모와 주석의 **이름표에 내용을 그대로 다시 쓰지 않는다.** 피그마 섹션으로 만든 메모는 섹션 이름(내용 전문)이 카드 위에 한 번 더 보이므로 프레임으로 만들거나 이름을 짧게 둔다.
- [ ] 메모 카드는 연한 파랑 카드에 파란 "메모" 꼬리글을 얹지 않고, 선 하나와 회색 글 같은 단순한 주석 꼴로 한 가지 모양만 쓴다.
- [ ] **덜 만든 것처럼 보이는 상태로 넘기지 않는다.** 03 패턴, 04 흐름도, 05 화면 흐름을 제목만 둔 빈 페이지로 두지 않는다. 관리자 화면 숫자를 모두 0과 000,000원으로 두지 않고 앞뒤가 맞는 예시 숫자를 넣은 뒤 "예시 숫자입니다" 메모를 단다. 설문처럼 질문과 입력 칸만 있는 화면은 진행 단계 글자와 선택 카드로 위계를 준다.
- [ ] **사진과 문구가 박힌 부품을 만들지 않는다.** 배너, 카드 부품은 틀과 사진 자리만 두고, 사진과 문구는 인스턴스에서 채운다(4-1).
- [ ] 글 줄바꿈: 어절 중간 줄바꿈, 한두 글자만 남는 외톨이 줄, 뜻 덩어리를 가르는 제목 줄바꿈이 없는지 본다. 휴대폰 본문 한 줄 20~28자, PC 본문 40~45자 안팎으로 글 폭을 둔다.
- [ ] 본문에 줄바꿈 문자를 넣어 360 폭에 맞추지 않는다. 실제 기기 폭(320~430)에서는 같은 자리에서 끊기지 않는다. 본문은 글 상자 폭(태블릿과 PC는 최대 560 안팎)으로 접고, 개발 전달에 어절 단위 접기(word-break: keep-all)를 적는다. 줄바꿈 문자는 뜻 단위로 끊어야 하는 제목에만 쓴다. 같은 문단을 화면마다 따로 들고 있지 말고 부품 글 속성으로 한 곳에서 고치게 한다.

## 10. 고객 공유와 개발 전달

### 10-1. 고객에게 보내기 전

- [ ] 00 안내를 고객 말로 다시 썼다: 무엇을 바탕으로 만들었는지, 고를 것과 기한, 검토 기간, 페이지 구성, 반영하지 않은 레퍼런스와 그 이유

- [ ] 예시 색과 실제 색을 구분해 적었다(예: "유형별 청록과 보라는 몰마다 바꾸는 예시 색")
- [ ] 고객과 이미 공유한 페이지(비교 시안 등)는 고치지 않는다. 원본 시안은 기록으로 두고, 고칠 때는 복사본에서 고친다
- [ ] 공유 자료에서는 "후보", "확정안" 대신 "시안"이라고 부른다
- [ ] 보내는 일은 사용자가 한다(지침서 13). 발송 전 상태로 둔다

### 10-2. 08 개발 전달

- [ ] 메모를 세 열로 모았다: 범위 밖 기능(넣으려면 범위 협의), 문구 승인 필요(지금 문구와 바꿀 문구), 정책 확정 필요(화면은 임시 중립 문구)
- [ ] 메모마다 출처(화면, 의견)를 적었고, 같은 메모를 복사해 여러 번 두지 않았다
- [ ] 정책 확정 항목을 할 일과 기획 결정 목록에 옮겼다
- [ ] 컴포넌트 속성표(이름, 변형, 글자 속성, 노출한 안쪽 인스턴스)를 개발자용으로 남겼다

### 10-3. 라이브러리 발행 (사용자가 직접)

피그마 작업 도구로는 라이브러리를 발행할 수 없다. 사용자가 피그마 앱에서 발행하도록 순서와 켤 것, 끌 것을 적어 건넨다.
- [ ] 파일이 팀 프로젝트 안에 있다(개인 드래프트에서는 팀 라이브러리로 발행되지 않는다).
- [ ] 켤 것: 컴포넌트와 패턴, 아이콘 세트, **의미 변수 컬렉션만**(기본값 변수는 발행에서 숨김), 글자 스타일, 효과 스타일.
- [ ] 끌 것: 화면 컴포넌트, 흐름도, 화면 흐름, 개발 전달 페이지의 일반 프레임, 쓰지 않는 옛 컴포넌트.
- [ ] 발행 설명 칸에 날짜와 바뀐 것을 한 줄로 적는다.

## 11. 검수

### 11-1. 검수 방법

- [ ] 만든 일꾼이 아닌 **새 일꾼**이 한다(지침서 01). 파일은 읽기만 한다.
- [ ] 이미 정한 것(고객 결정, 사용자 결정)을 검수 안내에 적어 다시 지적하지 않게 한다.
- [ ] 인계 메모의 말을 믿지 않고 화면으로 확인한다.
- [ ] 등급: 높음(설계서나 원문과 사실이 다름, 고객이 바로 지적할 것), 보통(화면이나 템플릿끼리 어긋남, 읽기 어려움), 낮음(다듬을 거리).
- [ ] 결과는 `_작업/최종점검/디자인/<범위>.md`에 "번호, 페이지와 프레임, 문제, 근거, 등급, 고칠 방법" 표로 남긴다.
- [ ] 관점을 나눠 여러 번 본다: 설계서와 원고 대조, 대비와 품질, 사진, 레퍼런스와 계약 범위, 고객 처지(처음 보는 사람)
- [ ] 독립 검수에서 고칠 것이 0건일 때 끝났다고 보고한다.

### 11-2. 마무리 점검표

**구조**
- [ ] 00 안내의 페이지 표와 실제 페이지가 같다
- [ ] 01 견본 글자(HEX, 별칭)가 실제 변수 값과 같다
- [ ] 01, 02, 03의 같은 값(아이콘 선 굵기, 하단 탭 글자, 헤더 높이, 섹션 간격, 등급 순서)이 서로 같다
- [ ] 레퍼런스에서 따라온 변수, 스타일, 컴포넌트가 없다
- [ ] 브랜드 색과 글꼴이 고객 BI 가이드 값과 같다. 근거 없는 색을 지어내지 않았다
- [ ] 글자 스타일에 크기, 굵기, 줄 높이, 자간이 다 있다
- [ ] 변수 이름이 코드 토큰 이름과 맞는다

**화면**
- [ ] 모든 글자가 등록한 글자 스타일, 모든 색과 간격이 변수에 연결돼 있다(예외는 이유를 적음)
- [ ] 분리(Detach)한 인스턴스가 없다
- [ ] 두 화면 이상에 나오는 묶음이 모두 컴포넌트 인스턴스다
- [ ] 헤더와 하단 탭이 원래 높이다(세로 HUG에 잘라 내기를 켜면 눌려 보인다. 사례는 부록)
- [ ] 바깥 프레임이 안쪽 내용을 자르지 않는다
- [ ] 모든 글자가 부모 칸 안쪽 여백 안에 있다(넘침, 잘림, 말줄임 0). 글자가 든 칸에 고정 높이가 없다
- [ ] 앞 아이콘의 가운데와 첫 줄 글자의 가운데가 1px 안으로 맞는다
- [ ] 요소끼리 겹치는 곳이 없고, 화면 프레임 밖에 떠 있는 요소가 없다
- [ ] 화면이 길어지면 하단 탭과 홈 표시줄이 맨 아래로 따라 내려간다
- [ ] 6-2 상태와 6-1 오류 화면이 다 있다. 03 빈 상태 문구마다 화면이 있다
- [ ] 04 판단마다 양쪽 화면이 있거나 "화면 없음"으로 표시돼 할 일에 올라 있다
- [ ] 테마 모드마다 같은 규칙이 같게 적용됐다

**접근성**
- [ ] 3-4 표의 숫자를 다시 쟀다. 고른 칸, 연한 면, 사진 위 글자를 빠뜨리지 않았다
- [ ] 누를 수 있는 것은 모두 44 이상이다

**고친 뒤**
- [ ] 한 화면에서 고친 문제는 같은 패턴을 모든 화면에서 찾아 함께 고쳤다
- [ ] 크기를 재려고 만든 복제본을 지웠다(도구가 중간에 멈추면 페이지에 남는다)
- [ ] 바뀐 것(화면, 전과 후)을 프로젝트의 변경 기록에 적고, 바뀐 화면을 스크린샷으로 확인했다

## 12. 작업 순서와 일꾼 배정

1. 1장 자료를 받고, 기획서에서 화면 목록과 핵심 데이터를 뽑는다.
2. 2장대로 파일과 페이지를 만들고 00 안내를 채운다.
3. 01 기초: 톤앤매너, 기본값 변수, 의미 변수, 치수, 테마, 글자 스타일 순서로.
4. 02 컴포넌트: 공통 목록을 상태 변형까지. 도메인 묶음은 핵심 화면 하나를 그려 보며 뽑는다.
5. 03 패턴과 6장 상태 기준을 정한다.
6. 04 흐름도를 그린다.
7. 06 화면과 07 상태 화면을 그린다. 일꾼 여럿이 나눠 그리면 **페이지나 섹션 단위로 담당을 나누고, 남의 페이지는 읽기만** 하게 한다. 컴포넌트를 고칠 일이 생기면 고치지 말고 보고하게 한다.
8. 05 화면 흐름을 만들고 "화면 없음"을 할 일로 올린다.
9. 3-4 접근성 점검을 돌린다.
10. 11장 검수(새 일꾼), 고침, 10장 고객 공유와 개발 전달 순서로.

일꾼에게 맡길 때는 공통 안내 한 장을 만들어 붙인다. 넣을 것: 파일 키와 읽기 전용 파일, 먼저 읽을 문서(이 지침서, 설계서, 레퍼런스 기준표, BI), 원칙(배치 그대로, 원문 그대로, 변수와 스타일만), 변수와 컴포넌트 이름표, 담당 페이지와 좌표, 사진 규칙, 기록 위치(`_작업/figma/<담당>/`, 길어지면 `_작업/인계/디자인_<담당>.md`), 보고 항목(만든 것, 쓴 사진, 비워 둔 값, 설계와 달라진 점, 스크린샷 확인 결과, 확인하지 못한 것).
