# 커밋 메시지 규칙

> 커밋 로그는 사람이 훑어 읽는다. **제목 한 줄만 읽어도 무엇이 어떻게 달라졌는지** 알 수 있어야 한다.

관련 문서: [[05 쇠맛 줄이기]] (표기), [[00 세션 공통 지침]] §8 (AI 서명 금지)

---

## 1. 형식

```
<종류>(<범위>): <무엇이 어떻게 달라졌는지 한 문장> [WBS : <번호>]

<본문: 필요할 때만. 왜 바꿨는지, 영향이 무엇인지 1~3줄>

refs #<이슈 번호>
```

- **제목 한 줄이 전부인 커밋이 기본이다.** 본문과 꼬리는 필요할 때만 쓴다.
- **범위**는 바뀐 곳이다(`app`, `admin`, `api`, `auth`, `event` 등). 정하기 어려우면 생략한다. 범위 고르는 법은 아래 1-1.
- **이슈 번호는 제목에 넣지 않고 맨 아래 꼬리에** `refs #12`로 붙인다. 여러 개면 `refs #132, #140`.

### 1-1. 범위 고르기

같은 곳을 커밋마다 다른 이름으로 부르면 로그를 범위로 찾을 수 없다(예: `error`와 `errors`, `be`와 `backend`, `운영`과 `ops`, 한글 `자료`).

1. **영어 소문자 한 낱말**로 쓴다. 두 낱말이면 하이픈으로 잇는다(`data-model`). 한글, 대문자, 띄어쓰기, 쉼표는 쓰지 않는다.
2. **그 저장소에서 이미 쓰는 범위에서 고른다.** `git log --all --format=%s | grep -o '^[a-z]*([^)]*)' | sort | uniq -c | sort -rn | head`로 본다. 같은 뜻의 이름이 둘이면 더 많이 쓴 쪽을 쓴다.
3. 맞는 범위가 없으면 **범위를 뺀다**. 새 범위가 꼭 필요하면 사용자에게 묻고 범위 목록 파일에 먼저 적는다.
4. 범위 목록 파일: 저장소 맨 위 `.commit-scopes`(팀과 함께 쓰는 목록, 한 줄에 하나), 저장소를 건드리지 않고 정할 때는 이 Mac의 하네스 설정 폴더 `commit-scopes/<저장소 폴더 이름>`. 목록 파일이 있으면 그 목록만 쓴다.

새 저장소에서 처음 정할 때 참고할 이름:

| 범위 | 쓰는 곳 |
|---|---|
| `app`, `admin`, `web` | 모바일 앱, 관리자 웹, 사용자 웹 |
| `api`, `db`, `auth` | 서버 기능, 데이터베이스와 마이그레이션, 로그인과 권한 |
| `ui`, `i18n` | 공통 화면 부품, 다국어 |
| `ci`, `deps`, `config`, `scripts` | 자동 빌드, 의존성, 설정, 스크립트 |
| `submodule` | 상위 저장소의 서브모듈 포인터 |
| `plan`, `contract`, `design`, `qa`, `release`, `report` | 문서 저장소의 기획, 계약, 디자인, 검수, 출시, 보고 |
| `inbox`, `outbox` | 받은 자료(`_수신함`), 보낼 문서(`_발신함`) |

### 1-2. WBS 번호 (2026-11-17)

WBS가 있는 프로젝트는 **모든 커밋 제목 끝에 그 일이 속한 WBS 작업 번호를 붙인다.** 커밋 기록만 봐도 WBS의 어느 작업이 얼마나 진행됐는지 보이게 하려는 것이다. 문서, 설정, 서브모듈 포인터, 머지 커밋도 예외 없이 어느 WBS 작업에 속한다.

- 꼴: 제목 끝에 그 커밋이 속한 WBS 번호를 모두 쓰고, 본문 맨 아래 꼬리에 번호마다 진행도를 한 줄씩 쓴다. 이 꼬리는 커밋 기록을 읽는 도구(RAG)가 WBS 진척을 뽑는 근거다.

  ```
  feat(app): 2차 인증 뒤 참여 기록을 남김 [WBS : 1.1.1, 1.2.3]

  WBS-Progress: 1.1.1 60%
  WBS-Progress: 1.2.3 100%
  ```
- **진행도:** 이 커밋을 넣은 뒤 그 WBS 작업이 산출물 기준으로 얼마나 끝났는지 0~100 정수와 %로 쓴다. 10~30%는 설계, 조사, 초안. 40~70%는 본 구현 중. 80~90%는 검수, 수정, 시험. 100%는 그 작업의 산출물이 끝나 통합 브랜치에 합쳐짐(문서는 보냄). 판단이 어려우면 사용자에게 묻는다. 이유 없이 지난 값보다 낮추지 않는다(낮추면 본문에 이유).
- 키 이름은 `WBS-Progress` 하나로 고정한다(git 꼬리 형식이라 `git log --format='%(trailers:key=WBS-Progress)'`로 읽힘). 작업별 마지막 진행도 표: `~/.claude/bin/wbs-progress.sh <저장소...>`.
- 번호는 그 프로젝트 WBS에 있는 번호만 쓴다. 맞는 작업이 없으면 지어내지 말고 사용자에게 어느 작업에 넣을지 묻는다(WBS에 새 작업을 넣을 일일 수 있다).
- 제목 길이는 `[WBS : …]`를 빼고 센다.
- **적용 프로젝트:** 이 Mac의 `~/.claude/harness/commit-wbs/<프로젝트 폴더>.txt`(번호 목록)가 있는 프로젝트. 목록은 `~/.claude/harness/commit-wbs/sources.tsv`에 적힌 WBS 파일에서 `python3 ~/.claude/bin/wbs-ids.py`로 뽑는다. WBS가 바뀌면 다시 뽑는다. WBS가 없거나 정확하지 않은 프로젝트는 목록을 두지 않고, 번호 없이 쓴다.
- 커밋 메시지 검사기가 번호가 없거나, 모양이 틀리거나, 목록에 없는 번호이거나, 제목의 번호마다 진행도 줄이 없거나, 진행도 모양이 틀리면 막는다(Claude 세션. 사람이 친 커밋은 경고만). 진행도가 지난 커밋보다 내려가면 경고만 한다.

## 2. 종류

| 종류 | 쓰는 때 |
|---|---|
| `feat` | 사용자가 쓸 수 있는 기능을 새로 넣을 때 |
| `fix` | 잘못 동작하던 것을 고칠 때 |
| `refactor` | 동작은 그대로 두고 코드 구조만 바꿀 때 |
| `style` | 화면 문구, 간격, 색처럼 보이는 것만 바꿀 때 |
| `perf` | 빠르게 하거나 자원을 덜 쓰게 할 때 |
| `test` | 시험만 추가하거나 고칠 때 |
| `docs` | 문서만 바꿀 때 |
| `chore` | 설정, 의존성, 서브모듈 포인터, 빌드 스크립트를 바꿀 때 |
| `revert` | 이전 커밋을 되돌릴 때. 본문에 되돌리는 이유를 쓴다 |
| `merge` | 머지 커밋. `merge: <브랜치> (<무엇이 들어오는지>)` |

## 3. 제목 쓰는 법

1. **한 커밋에는 한 가지 변경만 담는다.** 제목에 쉼표로 여러 가지를 잇게 되면 커밋을 나눈다.
2. **조사와 어미를 살린 문장을 음슴체로 끝낸다**(~함, ~음, ~임, ~됨). 명사만 나열하지 않는다.
   - 좋음: `fix(app): 마감일이 지나면 예상 금액 범위를 숨김`
   - 나쁨: `fix(app): 예상 금액 범위 숨김 처리, 마감 종료` (명사 나열)
   - 나쁨: `fix(app): 마감일이 지나면 예상 금액 범위를 숨긴다` (음슴체가 아님)
3. **무엇이 어떻게 달라지는지를 쓴다.** "리뷰 반영", "수정", "정리", "개선"처럼 내용이 없는 말로 끝내지 않는다.
4. **한글 40자 안팎**으로 쓰고 끝에 마침표를 붙이지 않는다.
5. [[05 쇠맛 줄이기]] 1장 구 단위 4~8번(문장부호 규칙)을 지킨다. 커밋에서는 05가 허용하는 "고치기 전과 고친 뒤" 예시의 화살표 예외도 없다. 가운뎃점(·), 엠대시(—), 꺾쇠 괄호(「」), 겹화살괄호(« »), 화살표(→)로 낱말을 잇지 않는다. 이 목록은 커밋 메시지 검사기가 그대로 막는다.

## 4. 넣지 않는 것

- AI 서명, `Co-Authored-By`, "Generated with Claude Code" 같은 생성 도구 표기
- 사용자와 나눈 대화 인용, 리뷰 등급, 목업 파일 이름 나열
- 비밀값, 내부 계정, 고객 개인정보

## 5. 저장소 관례와 부딪힐 때

**팀이 함께 정한 접두사가 있는 저장소는 그 접두사를 그대로 쓴다**(예: `[REFACTOR]:`, `[STYLE]:` 형식을 쓰는 저장소, `ops:`, `trace:` 형식을 쓰는 저장소). 그런 저장소에서도 3장 제목 쓰는 법과 4장 넣지 않는 것은 똑같이 적용한다. 한 저장소 안에서 형식을 하나로 맞추는 것이, 한 사람의 형식을 맞추는 것보다 중요하다.

## 6. 예시

| 지금 | 규칙대로 |
|---|---|
| `fix: 앱 예상 금액 리뷰 반영 — 마감 뒤 범위 숨김·평균값 없으면 범위 바 없음(#12)` | 두 커밋으로 나눈다. `fix(app): 마감일이 지나면 예상 금액 범위를 숨김`, `fix(app): 평균값이 없으면 범위 막대를 그리지 않음`. 둘 다 꼬리에 `refs #12` |
| `[REFACTOR]: 시계 비공개화, 날짜 읽기 형식 확장, 모르는 시간대 경고 로그, 형식 캐시 키에 locale 포함` | 네 커밋으로 나눈다. 예: `[REFACTOR]: 모르는 시간대가 들어오면 경고 로그를 남김` |
| `fix: 개인정보 파기 스위치 기본값을 dry_run으로` | `fix(retention): 개인정보 파기 스위치를 기본으로 꺼 둠` |
| `서브모듈 포인터 갱신: 설문 문항 변경(app 커밋, backend 커밋)` | `chore(submodule): 설문 문항 변경을 반영한 app, backend 커밋을 가리킴` |

## 7. 지키는 장치

- 규칙 검사는 하네스의 커밋 메시지 검사기 한 곳에 있고, 전역 git 훅의 commit-msg 단계에서 돈다. `-m`, `-F`, 편집기로 쓴 메시지를 모두 검사한다.
- **Claude 세션의 커밋은 막는다.** 사람이 터미널에서 친 커밋은 경고만 하고 진행한다.
- 막는 것: 정해진 종류가 아닌 접두사(그 저장소가 세 번 이상 쓴 영어 접두사와 `[REFACTOR]:` 꼴 팀 접두사는 허용), 영어 소문자가 아닌 범위, 저장소에 없는 새 범위(범위 목록 파일이 있거나 형식을 맞춘 커밋이 30개 이상인 저장소에서), 같은 뜻의 다른 이름, 금지 표기, 제목 안 이슈 번호, 마침표, 쉼표 두 개 이상, 60자 넘는 제목, 음슴체가 아닌 끝맺음, "수정함"처럼 내용 없는 제목, 한국어 저장소(최근 커밋 제목의 절반 이상이 한글이거나 커밋이 없는 저장소)의 영어 제목. 50자를 넘으면 경고만 한다.
- 머지, 되돌리기, `fixup!`, `squash!`, `amend!` 커밋은 검사하지 않는다.
- Claude가 커밋 명령을 치기 전에도 같은 검사기로 미리 알려 준다(알림만, 막는 것은 git 훅). 장치 동작은 [[10 자동 장치]].
- 이미 푸시한 커밋은 고치지 않는다.
- AI 서명은 따로 막는다([[00 세션 공통 지침]] §8).
