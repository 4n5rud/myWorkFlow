# 코딩 규칙

> [[00 세션 공통 지침]] 이 **여럿이 같이 일할 때**의 규칙이라면, 여기는 **코드를 쓸 때**의 규칙이다.
> 새 프로젝트에는 이 문서를 복사하지 않는다. 그 프로젝트에 적용한 결과만 저장소 `CLAUDE.md`에 적는다(사용자가 원할 때, [[04 새 프로젝트에 이식]]).

---

## 1. 마인드셋

**시니어 엔지니어처럼 생각한다.** 추측으로 뛰어들거나 성급히 결론내리지 않는다.

여러 접근을 평가하고 **장점, 단점, 위험을 각각 한 줄로 적은 뒤 가장 단순한 해법**을 고른다.
**적는 것이 핵심이다.** 머릿속으로만 비교하면 처음 떠오른 안이 이긴다.

---

## 2. 코드를 고치기 전에

- **파일을 처음부터 끝까지 읽는다.** 부분만 읽고 고치지 않는다.
- 바꾸기 전에 **정의, 참조, 호출 지점, 관련 테스트, 문서/설정/플래그**를 찾아 읽는다.
- 심볼을 고치기 전에 **전역 검색으로 사전/사후 조건**을 파악하고 영향도를 1~3줄로 남긴다.

> ⚠ 생성물(`*.g.dart`, 락파일, 번들)까지 통독하라는 뜻은 아니다. 그런 파일은 **고치지 않는 것**이
> 규칙이고, 손대야 할 상황이면 그 사실 자체를 먼저 보고한다. 사람이 쓴 소스는 예외 없이 통독한다.

### 코딩 전에 문제 정의 한 장(Problem 1-Pager)

여러 파일이나 API 계약, DB 구조처럼 다른 쪽이 기대는 약속을 건드릴 때는 고치기 전에 아래 다섯 칸을 한 장에 적는다. 한 파일 안의 작은 수정이면 쓰지 않아도 된다.

```
배경    지금 무엇이 있고 어떻게 도는가
문제    무엇이 안 되는가 (증상, 재현 조건)
목표    무엇이 되면 끝인가
비목표  이번에 안 건드리는 것
제약    계약, 명세, 성능, 호환처럼 못 넘는 선
```

## 3. 코딩 한도

넘으면 분리하거나 리팩터링한다. LOC(lines of code)는 빈 줄과 주석을 뺀 코드 줄 수다.

| | 한도 |
|---|---|
| 파일 | ≤ 300 LOC |
| 함수 | ≤ 50 LOC |
| 매개변수 | ≤ 5 |
| 순환 복잡도 | ≤ 10 |

- **명시적인 코드를 선호한다.** 숨겨진 "매직" 금지.
- **DRY(Don't Repeat Yourself, 같은 코드를 되풀이하지 않기)를 따르되 섣부른 추상화는 피한다.** 두 번째 사용처가 나오기 전에 추상화하지 않는다.
- **부수효과(I/O, 네트워크, 전역 상태)는 경계층으로 격리한다.**
- **구체적인 예외만 처리하고** 사용자에게 명확한 메시지를 준다.
- **구조화된 로깅**을 쓰고 **민감한 데이터를 기록하지 않는다.** 가능하면 요청/상관관계 ID 를 전파한다.
- **날짜와 시간대는 [[06 한국 시간 처리 모듈]]로만 다룬다.** 한국 자정의 UTC 시각을 잘라 하루 전 날짜가 되어 4일 일찍 파기할 뻔한 사례가 06 §2에 있다.

## 4. 클린 코드

- 의도를 드러내는 이름
- 함수 하나는 한 가지 일만
- 부수효과는 경계층으로
- 가드절 우선
- **상수는 심볼화한다.** 하드코딩 금지
- 입력을 받고, 처리하고, 반환하는 순서로 짠다
- 실패는 **구체적인 오류와 메시지**로 보고
- 테스트가 **사용 예제로도 읽히게** 쓰고 경계와 실패 사례를 포함한다

---

## 5. 테스트

- **새 코드에는 새 테스트.** 버그 수정에는 **회귀 테스트를 반드시** 넣는다. **먼저 실패하도록 쓴다.**
- 테스트는 **결정적이고 독립적**이어야 한다. 외부 시스템은 가짜나 계약 테스트로 대체한다.
- E2E 에는 **성공 경로 ≥1, 실패 경로 ≥1.**
- 동시성, 락, 재시도에서 올 위험(중복, 데드락)을 **선제적으로** 따진다.
  ([[백엔드 세션 지침]] §3: 코드로 풀지 말고 원자 연산으로 막는다)

### 🔴 규칙 시험으로 안 잡히는 결함이 있다

배치, 성능, 권한처럼 **부품 각각은 옳은데 만나는 자리에서만 틀어지는** 것들이다.
**실제로 띄워서 치수를 재거나 시간을 재야** 잡힌다. [[02 이슈 세션 운영]] §6.

### 🔴 테스트가 빨갛다고 코드부터 고치지 않는다

**기대값이 틀린 경우가 실제로 있었다.** 손으로 검산한다.

> 사례: 한국 날짜 경계를 잘못 자르던 코드를 고쳤더니 테스트가 빨개졌다. 틀린 쪽은 코드가 아니라 옛 동작에 맞춰 적어 둔 테스트 기대값이었다([[06 한국 시간 처리 모듈]] §2의 공휴일 사례).

### 🔴 가드를 만들면 일부러 깨뜨려 본다

안 잡히는 가드는 없는 것보다 나쁘다. **"통과했다" 는 말이 붙기 때문**이다.

### 🔴 로컬 전용 목업은 커밋, 푸시, 빌드에 넣지 않는다 (2026-11-05 추가)

서버 데이터가 비어 있어 화면을 확인하기 어려울 때, API 응답 대신 목업 데이터를 넣어 확인할 수 있다. 다만 그 목업은 **내 컴퓨터에서만** 쓴다.

- **목업 데이터 파일**은 gitignore 대상 경로(예: `mock-data/`, `mocks/`)에 두고, 커밋 전에 `git status`로 빠졌는지 본다.
- **목업을 켜는 설정**은 개발 실행에서만 켜지게 한다(예: `--dart-define=USE_MOCK=true`를 `flutter run`에만 준다). 릴리스와 스테이징 빌드에는 파일도 설정도 들어가지 않게 하고, 빌드 결과물에 포함되지 않았는지 확인한다.
- 로컬에서만 쓰는 줄에는 주석으로 **`// 로컬 전용`** 또는 **`LOCAL-ONLY`** 표시를 붙인다. 그래야 사람과 훅이 알아본다.
- 목업에는 실제 사람의 이름, 회원번호, 연락처를 넣지 않는다. `사용자1`, `90001` 같은 가짜 값을 쓴다.
- 시험 코드(`test/`, `__tests__/` 아래)의 가짜 데이터는 여기에 해당하지 않는다. 그건 커밋한다.

**지키는 장치:** 전역 훅이 다음 세 가지를 막는다.
- 목업 파일, 목업을 켜는 설정(`USE_MOCK=true` 같은 것), `.env.local` 같은 로컬 설정 파일, 로컬 전용 표시가 붙은 줄이 들어간 **커밋**
- 그런 커밋이 섞인 **푸시**
- 목업 설정이나 로컬 설정 파일을 쓴 **빌드 명령**

## 6. 보안

- 입력을 **검증, 정규화, 인코딩**하고 **파라미터화된 접근**을 쓴다(SQL과 명령을 문자열로 이어 붙이지 않는다).
- **최소 권한 원칙.** 코드, 계정, 토큰에는 그 일에 필요한 권한만 준다.
- **로그와 오류 메시지에 비밀값과 민감한 데이터를 남기지 않는다.**
- 비밀값(키, 토큰, 비밀번호)을 저장소에 두지 않는 규칙과 새어 나갔을 때의 순서는 한곳에 있다. 자세한 규칙: [[15 비밀값 커밋 금지]].

---

## 7. 안티 패턴

- 전체 문맥을 읽지 않고 고치지 않는다(§2)
- 비밀값을 노출하지 않는다
- **실패나 경고를 무시하지 않는다**
- 근거 없는 최적화나 추상화를 넣지 않는다
- 광범위한 예외를 남용하지 않는다
