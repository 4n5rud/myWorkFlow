# 화면 QA와 보고서

인자: $ARGUMENTS (점검할 화면이나 기능. 없으면 이번 작업에서 바뀐 화면)

## 0. 먼저 읽을 것
- 보고서 양식: `{{HARNESS_DIR}}/templates/QA 보고서 양식.html` (맨 위 주석과 안내 상자가 쓰는 법)
- 캡처 도구: `{{HARNESS_DIR}}/qa/qa-capture.mjs` (맨 위 주석에 설정 형식)
- 4n5rud-guides 스킬의 `02 이슈 세션 운영.md` §6(캡처는 실패할 때만), `08 보고 지침.md`, `05 쇠맛 줄이기.md`, `17 기술 문서 쓰기.md`(보고서는 읽는 사람이 무엇을 해야 하는 문서)

## 1. 점검 범위 정하기 (추측하지 않는다)
- 인자가 없으면 이번 작업 브랜치에서 바뀐 화면(`git diff`로 바뀐 페이지, 라우트)을 대상으로 한다. 인자가 있으면 그 화면과 기능만 본다.
- 실제 앱 코드(라우트, 화면 컴포넌트, API 호출)와 기획서를 읽고 사용자 흐름을 정한다. 흐름마다 "무엇을 하면 무엇이 보여야 한다"를 적는다. 화면을 돌아다니며 아무 단추나 누르지 않는다.
- 흐름마다 상태를 함께 본다: 처음 상태, 로딩, 빈 결과, 오류, 권한 없음, 두 번 누르기, 성공, 긴 글자와 최대치(전역 메모리 "경계 상황 먼저").
- 창 폭은 기본 1280과 390이다. 프로젝트가 모바일 앱 웹뷰면 390을, 관리자 웹만이면 1280을 앞에 둔다.

## 2. 실행 환경
- **로컬만 기본으로 점검한다.** 사용자가 시험 서버를 지정하면 그 주소만 쓰고(설정의 `"target": "test"`), 운영 서버는 점검하지 않는다.
- 먼저 그 앱 주소에 이미 떠 있는 서버가 있는지 본다(`curl -sI`나 `lsof -i :포트`). 다른 세션이 띄운 서버면 그대로 쓰고, 끄거나 다시 띄우지 않는다.
- 떠 있지 않으면 그 프로젝트의 평소 방법(README, 실행 스크립트)으로 띄우고, 점검이 끝나면 내가 띄운 것만 끈다. 띄우지 못하면 멈추고 이유를 보고한다. 데모 앱이나 가짜 대상을 만들지 않는다.
- 로그인이 필요하면 프로젝트에 있는 시험 계정만 쓴다. 비밀번호는 설정 파일에 쓰지 않고 환경 변수(`"env"`)로 넘긴다. 계정이 없으면 멈추고 묻는다.
- 로컬 DB와 서버 데이터는 바꾸지 않는다. 바꿔야 확인되는 흐름은 6장 "확인하지 못한 것"에 적는다.

## 3. 자동 점검과 캡처
1. 설정 파일을 만든다: 작업 폴더 밖 스크래치 위치에 `qa-spec.json`(형식은 캡처 도구 주석). 문제를 찾기 전에는 `issues` 없이 한 번 돌려 자동 점검(콘솔 오류, 4xx와 5xx 요청, 가로 넘침, 깨진 이미지)을 받는다.
   ```
   node {{HARNESS_DIR}}/qa/qa-capture.mjs --spec qa-spec.json --out <스크래치>/qa-out
   ```
2. 화면을 직접 보고(사진은 Read로 연다) 흐름마다 기대 결과와 대조한다. 배치, 잘림, 겹침, 문구, 색 대비(본문 4.5:1), 빈 상태와 오류 상태, 키보드 초점을 본다.
3. 문제마다 `issues`에 번호, 위치(CSS 선택자), 짧은 설명을 넣는다. 스타일로 흉내 낼 수 있는 해결안은 `fixCss`를 넣는다. 다시 돌리면 빨간 상자와 번호가 붙은 "전" 사진과, 해결안을 덧씌우고 초록 상자를 붙인 "후" 사진이 나온다.
4. 캡처는 문제가 있는 화면만 남긴다. 통과한 화면은 사진 없이 5장에 적는다(눈으로만 판정할 수 있는 시각 확인은 예외).
5. 사진에 아이디, 전화번호, 이메일, 토큰 같은 값이 보이면 `fixCss`나 별도 덧씌우기로 가린 뒤 다시 찍는다.
6. 자동 점검 결과(`results.json`)의 콘솔 문구와 요청 경로에는 토큰이나 개인정보가 섞일 수 있다. 보고서에는 원문을 붙이지 않고 "콘솔 오류 2건(이미지를 불러오지 못함)"처럼 요약해서 쓴다.
7. 원인은 코드에서 확인한다. 확인하지 못하면 (추정)으로 쓴다. 재현하지 못한 문제는 "재현하지 못함"으로 쓰고 지어내지 않는다.

## 4. 보고서 쓰기
- 🔴 양식의 장은 실제로 점검한 결과를 담는 자리일 뿐이다. 점검하지 않은 내용으로 채우지 않는다. 해당 없는 장(예: 해결 후 미리보기를 찍지 못함)은 지우거나 "해당 없음, 이유"로 둔다.
- 양식을 복사해 채운다. 문제 하나에 h3 하나, 육하원칙과 재현 방법, 전과 후 사진 짝. 해결안은 권하는 안(정석안)과 다른 안을 비용과 함께 쓴다.
- 사진은 data URI로 넣어 파일 하나로 만든다: `python3 -c "import base64,sys;print('data:image/png;base64,'+base64.b64encode(open(sys.argv[1],'rb').read()).decode())" <사진>`
- "후" 사진은 브라우저에서 스타일만 덧씌운 흉내라는 것과, 코드는 고치지 않았다는 것을 머리말과 사진 설명에 밝힌다.
- 절대 경로, 개인 노트 위치, 요청 본문과 헤더 값, 쿠키, 계정 정보를 쓰지 않는다.
- 다 쓴 뒤 양식 주석과 안내 상자를 지우고 `grep -n '{{' <파일>`로 남은 자리를 찾는다. 오른쪽 위 화이트, 블랙 단추는 남긴다.

## 5. 저장과 보고
- 저장 위치: 그 프로젝트 문서 저장소의 `_작업/QA_<화면이나 기능 붙여 쓰기>_<YYMMDD>.html`. 같은 이름이 있으면 `.1차`, `.2차`를 붙인다. 커밋은 사용자가 확인한 뒤에만 한다(사진에 내부 화면이 들어 있다).
- 저장한 뒤 `open`으로 연다.
- 사용자 보고(08 보고 지침): 결론 한두 줄(고칠 곳 몇 건, 높음 몇 건), 고칠 곳을 [1], [2] 번호로 한 줄씩, 정할 것, 확인하지 못한 것, 보고서 위치(상대 경로).
- 고칠 곳은 사용자가 "고쳐"라고 하기 전에는 고치지 않는다. 남은 일은 프로젝트 `_할일/할 일.md`에 적는다.
