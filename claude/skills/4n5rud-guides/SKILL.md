# 업무 지침서 길잡이

지침서 원본은 아래 폴더에 있다(설치할 때 harness.conf의 GUIDES_DIR로 정해짐, 2026-11-16부터 하네스 저장소의 `guides/`). 설치하면 이 스킬 폴더의 `guides/`가 그 폴더를 가리키는 링크가 된다. 노트 보관함의 지침서는 사본이라 고치지 않는다.

```
{{GUIDES_DIR}}/
```

이 파일은 **어느 문서를 읽을지만** 정한다. 규칙 내용을 여기에 옮겨 적거나 요약하지 않는다. 옮겨 적은 사본은 원본보다 먼저 낡기 때문이다.

## 2. 읽는 방법 (토큰 아끼기)

1. **고른 문서만 읽는다.** 지침서 폴더 전체를 읽지 않는다.
2. **200줄이 넘는 문서**(00, 01, 02, 05 쇠맛 줄이기, 07, 16 디자인 시작 체크리스트, 디자인 레퍼런스)는 목차부터 본다. Grep 도구(패턴 `^## `, 줄 번호 표시)로 절 위치를 찾고, Read의 offset과 limit으로 **필요한 절만** 읽는다. 셸 `grep`도 쓸 수 있지만 Grep 도구를 쓰면 권한 확인이 덜 걸린다. `🔴` 표시가 붙은 절이 지금 작업과 관련 있으면 빠뜨리지 않고 읽는다.
3. **200줄 이하 문서**는 통째로 읽는다. 05 쇠맛 줄이기는 요약하면 안 되는 문서이므로, 쓸 때는 해당하는 장을 통째로 읽는다(1장은 예시까지). 옛 05 윤문 지침은 `_보관/`으로 옮겨 쓰지 않는다.
4. **이번 세션에서 이미 읽은 절은 다시 읽지 않는다.** 대화가 압축된 뒤에는 지금 필요한 절만 다시 읽는다.

## 3. 지어내지 않기

1. **지침 내용은 이번 세션에서 실제로 읽은 것만 근거로 쓴다.** 기억이나 짐작에 기대어 "지침에 이렇게 적혀 있다"고 말하지 않는다.
2. 지침을 근거로 판단했으면 **문서 이름과 절 번호**를 붙인다. 예: `근거: 03 코딩 규칙 §2`
3. 파일이 없거나 링크가 깨져 있으면 **작업을 멈추고 사용자에게 알린다.** 기억으로 내용을 채우지 않는다.
4. 문서 안에 "바뀌었다"나 "레거시"라는 표시가 있거나 옛 규칙과 새 규칙을 나란히 적은 표가 있으면, **현행 규칙을 따른다.**
5. 지침서는 일하는 방법을 정한 문서다. 코드와 API, 데이터가 지금 어떤 상태인지는 지침서가 아니라 실제 코드와 계약, 응답으로 확인한다.

## 4. 우선순위

1. 사용자의 지금 지시
2. 전역 지침의 안전 규칙(비밀값, 보호 브랜치, 보낼 문서와 발송, 읽기 전용과 커밋 금지 저장소). 프로젝트 지침이 이보다 느슨하게 적었어도 이쪽을 따른다
3. 프로젝트 CLAUDE.md와 메모리
4. 나머지 전역 지침
5. 지침서

서로 부딪히면 앞선 쪽을 따르고, **부딪혔다는 사실을 보고에 적는다.** 아무 말 없이 한쪽을 고르지 않는다.

## 5. 지켰는지 드러내기

- **작업을 시작할 때** 읽은 지침을 한 줄로 밝힌다. 예: `읽은 지침: 02 §2와 §3, 03, 앱 §5`
- **작업을 끝낼 때** 00의 종료 체크리스트와, 읽은 문서에 있는 체크리스트와 "인계 문서에 꼭 담을 것"을 대조한다. 보고에는 지키지 못한 항목만 이유와 함께 적는다. 모두 지켰으면 한 줄로 끝낸다.

## 6. 서브에이전트에게 일을 줄 때

- 지침 본문을 프롬프트에 붙여 넣지 않는다. **읽어야 할 문서 경로와 절 번호를 준다.** 단 지침서가 "배정 프롬프트에 그대로 넣는다"고 정한 짧은 지시(예: 01 §12.1 표, 01 §13.5 문서 갱신 문장)는 붙여 넣는다.
  예: `작업 전에 {{GUIDES_DIR}}/앱 세션 지침.md 의 §5와 §10을 읽고, 따른 항목에는 근거를 붙여 보고하라.`
- 서브에이전트도 이 스킬을 쓸 수 있으면 `4n5rud-guides 스킬을 먼저 써라`라는 한 줄로 충분하다.

## 7. 지침서는 고치지 않는다

지침서는 사용자가 관리하는 원본이다. 고칠 점을 찾으면 보고에 제안으로만 적는다. 사용자가 직접 고치라고 지시한 경우에만 고친다.
