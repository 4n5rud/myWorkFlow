# 주간업무보고 만들기

인자로 프로젝트 이름(옵시디언 `work/` 아래 폴더 이름, 예: `내프로젝트`)을 받는다. 여러 개를 받으면 프로젝트마다 하나씩 만든다.

- **`전체`(또는 자동 실행에서 인자가 없을 때)**: 옵시디언 `work/` 아래에서 **이번 주 주간 폴더가 있는 프로젝트를 모두** 대상으로 한다(`_`로 시작하는 폴더는 제외). 주간 폴더가 없는 프로젝트는 건너뛰고 보고에 적는다.
- 인자가 없고 자동 실행도 아니면 현재 작업 폴더로 짐작하고, 짐작이 안 되면 묻는다.
- **대상이 둘 이상이면 프로젝트마다 서브에이전트를 하나씩 맡긴다. 한 번에 서브에이전트 한도(기본 4명)까지만 돌리고, 나머지 프로젝트는 하나가 끝날 때마다 차례로 맡긴다(전역 지침 "서브에이전트는 한 번에 4명까지").** 각 서브에이전트에게는 "이 스킬 파일(`~/.claude/skills/4n5rud-weekly-report/SKILL.md`)을 읽고 프로젝트 X 하나만 만들라"고 준다. 메인은 결과를 모아 한 번에 보고한다.

### 프로젝트와 저장소

옵시디언 이름과 저장소 폴더의 짝, 제외할 프로젝트는 `{{HARNESS_DIR}}/projects.md`에 있다. 먼저 그 파일을 읽는다. 표에 없는 프로젝트는 저장소 없이 노트만으로 만들고, 보고에 "저장소 연결 필요"로 적는다. 새 프로젝트를 알게 되면 그 파일에 추가하자고 제안한다. 제외 프로젝트는 `전체`로 실행해도 만들지 않는다.

먼저 읽을 것:
- 🔴 **프로젝트 규칙이 공통 양식보다 앞선다.** 저장소에 `docs/weekly_report/` 폴더가 있으면, 그 안의 작성 규칙 문서(예: `작성규칙.md`)와 **가장 최근 보고서**를 먼저 읽는다. 양식, 머리글의 부서와 성명, 칸 구성, 항목 규칙은 그쪽을 따른다(프로젝트마다 작성 규칙과 성명이 따로 있을 수 있다).
- 공통 양식: `{{HARNESS_DIR}}/templates/주간보고 양식.html` (맨 위 주석에 채우는 법이 있다). 프로젝트에 보고서 폴더나 규칙이 없을 때 쓴다.
- 문장 기준: 4n5rud-guides 스킬의 `05 쇠맛 줄이기.md`(1장, 4장, 8장, 9장), `17 기술 문서 쓰기.md`, `08 보고 지침.md`. 보고서는 고객이 읽는 문서다.
- 🔴 **검수 기준: `{{GUIDES_DIR}}/11 주간보고 검수.md`를 처음부터 끝까지 읽는다.** 쓰기 전에 1장(커밋 전수 파악, WBS, 지난주 보고서), 다 쓴 뒤에 2장(열네 가지 확인), 끝에 3장(검수 결과 보고)을 따른다.

## 1. 기간 정하기

- 기준일은 오늘(한국 시간)이다. 금주는 기준일이 속한 주의 월요일부터 금요일, 차주는 그다음 주 월요일부터 금요일이다.
- 표기: 머리글은 `2026.11.02(월) ~ 11.06(금)`, 파일 이름은 `2026.11.02-11.06`, 제목은 `2026.11.02~11.06`.
- 휴일이나 휴무가 있으면 날짜별 노트와 주간목표에서 찾아 참고사항 줄에 쓴다. 없으면 그 줄을 지운다.

## 2. 근거 모으기 (지어내지 않는다)

1. **주간 폴더**: `{{NOTES_DIR}}/work/<프로젝트>/<YYYY-MM-DD> 주간 (MM.DD~MM.DD)/`
   - `주간목표.md`: 이번 주 목표와 체크 상태
   - 날짜별 노트(`YYYY-MM-DD.md`): "오늘 할 것"의 `[x]`(한 일)와 `[ ]`(못 한 일)
   - 폴더가 없으면 멈추고 알린다. 주간 폴더는 이 스킬이 만들지 않는다. 사용자가 직접 만들거나 주간 노트를 만드는 별도 스킬(예: weekly-work-notes)이 만든다.
2. **지난주 보고서**: 같은 저장 위치(4장)에서 가장 최근 보고서를 읽는다. 묶음 제목, 요구사항 번호([4.8] 같은 것), "개발 진행 현황" 줄은 지난주 것을 이어받아 갱신한다.
   - 🔴 **요구사항 번호는 최근 보고서 몇 개에 이미 쓰인 번호만 가져다 쓴다.** 제안서, 일정표(WBS), 계획서 같은 원본 문서를 뒤져 새 번호를 찾지 않는다. 새 묶음에 맞는 번호가 최근 보고서에 없으면 번호 없이 쓰고, 보고에 "번호 확인 필요"로 적는다. (원본 문서를 뒤지면 작업 단계의 절반을 번호 찾기에 쓰게 된다.)
3. 🔴 **이번 주 커밋 전수 파악**: 노트보다 먼저 한다. `11 주간보고 검수.md` 1.1대로 프로젝트의 모든 저장소에서 금주 모든 브랜치의 커밋을 작성자 구분 없이 모으고, 기능 단위로 묶은 "이번 주 변경 목록"을 만든 뒤 노트와 대조한다. 노트와 커밋 어디에도 없는 일은 쓰지 않는다.
4. **WBS**: 묶음 제목과 요구사항 번호는 지난주(최근) 보고서를 우선 따르고, WBS는 진척률 대조와 "WBS 밖 일" 구분에만 쓴다(11 주간보고 검수와 같은 기준). `projects.md`에 적힌 WBS 위치를 읽고 항목이 어느 WBS 작업에 들어가는지 확인한다. WBS가 없거나 불완전하면 지난 보고서 체계를 따르고 "WBS 정리 필요"로 보고한다.

## 3. 쓰기

- **금주 실적**: 한 일(`[x]`)을 4~5개 묶음으로 모아 쓴다. 묶음 제목은 지난주 보고서의 묶음을 우선 따른다.
- 🔴 **금요일 당일 작업**: 오늘이 금요일이면 오늘 날짜 노트의 `[ ]` 항목 중 이번 주 실적에 들어갈 일은 항목 끝에 `<span class="sub">(진행중)</span>`을 붙여 금주 실적에 넣는다. 금요일 노트가 비어 있으면 목요일 노트의 `[ ]` 항목과 주간목표에서 아직 체크되지 않은 이번 주 마무리 항목을 금요일 당일 작업으로 본다. 금요일 이전 날짜의 못 한 일 중 이번 주에 마무리할 계획이 없는 것은 (진행중)으로 쓰지 않고 차주 계획으로 넘긴다. "주간 보고" 작성 항목 자체는 실적에 넣지 않는다.
- **차주 계획**: 주간목표의 남은 `[ ]`, 넘어온 일, 회신을 기다리는 일을 묶어 쓴다. 조건이 걸린 일은 "개발 진행 현황"에 `［조건 후］` 형식으로 쓴다.
- **문장**: 고객이 읽는 문서라 내부 용어(브랜치, 커밋, 파일, 함수 이름, 이슈 번호, 세션, 에이전트)를 쓰지 않는다. 기능 이름과 화면 이름으로 쓴다. 항목은 짧은 명사구로 쓰고 핵심어만 `<b>`로 굵게 한다. 숫자(테스트 개수, 진척률)는 노트나 실제 실행 결과에 있는 것만 쓴다.
- 양식의 `{{...}}` 자리가 하나도 남지 않게 한다.

## 4. 저장

- 🔴 **다른 세션과 같은 파일을 고치지 않는다**: 쓰기 전에 저장할 보고서 파일이 커밋되지 않은 채 바뀌어 있는지(`git status`), 다른 작업 폴더에 같은 주 보고서가 있는지 본다. 프로젝트 세션이 고치는 중이면 손대지 않고, 검수 결과만 그 세션에 넘기거나 사용자에게 보고한다(2026-11-06, 같은 보고서를 두 세션이 동시에 고친 일이 있었음).
- **저장 위치** (노트 보관함에는 저장하지 않는다):
  - 프로젝트 저장소에 `docs/weekly_report/` 폴더가 있으면 거기(저장소가 여러 개로 나뉜 프로젝트는 그 폴더가 있는 저장소).
  - 없으면 **프로젝트 폴더의 `주간보고/`**(예: `<WORK_DIR>/<프로젝트 폴더>/주간보고/`). 폴더가 없으면 만든다.
  - 노트 보관함의 주간 폴더는 근거(주간목표, 날짜별 노트)를 읽는 곳일 뿐 저장하지 않는다.
- **파일 이름**: `주간보고_YYYY.MM.DD-MM.DD.html`, PDF는 `주간업무보고 (YYYY.MM.DD~MM.DD).pdf`
- **PDF 만들기**:
  ```bash
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --no-pdf-header-footer \
    --print-to-pdf="<PDF 경로>" "file://<HTML 경로>"
  ```
  만든 뒤 PDF 쪽수를 확인한다(`mdls -name kMDItemNumberOfPages`). 1쪽이 넘으면 문장을 줄여 1쪽에 맞춘다.
- 같은 이름의 파일이 이미 있으면:
  - **금요일 자동 실행이거나 사용자가 "갱신"이라고 했을 때**: 처음부터 새로 쓰지 않고 기존 보고서를 **오늘 기준으로 갱신**한다. 그사이 끝난 `(진행중)` 항목은 표시를 빼고, 새로 생긴 실적을 더하고, 아직 안 끝난 일만 `(진행중)`으로 남긴다. 사용자가 그사이 손으로 고쳤을 수 있으니, **갱신하기 전에 기존 HTML을 같은 폴더에 `<원래 이름>.이전.html`로 복사해 둔다.** 갱신할 때는 금주 실적과 차주 계획에서 바뀌어야 하는 항목만 고치고 나머지 문장은 그대로 둔다. PDF도 다시 만든다. 보고에 바뀐 줄과 이전 파일 위치를 적는다. `.이전.html`은 커밋하지 않는다.
  - 그 밖에는 덮어쓰지 말고 사용자에게 묻는다.

## 5. 검수

저장하기 전에 `11 주간보고 검수.md` 2장의 열네 가지를 하나씩 확인하고 고친다. 고친 뒤 PDF를 다시 만들고 1쪽인지 확인한다.

## 6. 마무리

- **커밋하지 않는다.** 고객에게 나가는 문서라 사용자가 내용을 확인한 뒤에 커밋한다. 확인받으면 그 파일 두 개만 경로를 지정해 커밋한다(`git add -A` 금지). 푸시는 따로 허락받는다.
- 주간목표의 "금요일 주간 보고" 항목은 사용자가 확인한 뒤에 체크한다.
- **할 일 목록에 확인 항목을 넣는다.** 보고서를 만든 프로젝트의 `_할일/할 일.md` "사용자 확인 기다림" 아래에 `- [ ] 주간보고(MM.DD~MM.DD) 확인하고 보내기: <보고서 상대 경로> (추가 MM.DD)`를 한 줄 넣는다. 같은 주 항목이 이미 있으면 넣지 않는다. 사용자가 보냈다고 하면 `/4n5rud-todo` 절차대로 끝낸 일로 옮긴다(서브에이전트가 만들었으면 메인 세션이 넣는다).
- 사용자에게는 08 보고 지침대로 보고한다: 만든 파일 두 개의 위치, 금주 실적과 차주 계획의 묶음 제목, (진행중)으로 표시한 항목, **검수 결과(고친 것, 판단을 맡길 것, 근거를 못 찾은 것)**.
